# 当前总结与架构审查

审查日期：2026-09-10。范围：README、技术评估、产品蓝图、4 个 Rust crate、演示程序及现有测试。结论来自代码阅读、重新运行检查和独立探针；没有连接物理设备。详细补充见[架构设计 v0.3](architecture.md)。

## 判断

技术方向正确：Rust 掌握工程语义与执行，TypeScript 复用界面与云端业务，Tauri 只作为宿主；专业单机优先，离线运行，后续扩展移动端、Web、ARM 和云端。

上次总结对实现成熟度描述偏高。当前可准确称为 **A0 静态语义验证原型**：一次内存中的配适、编程、Cue 求值、合成和 DMX 数据编码。它尚未构成带时钟、持续输出、持久化和编辑事务的控台内核。已有模块没有循环依赖，但职责与数据契约尚未充分解耦。

先补领域模型、状态归属、命令契约、时间与输出边界，再以代表性节目验证。暂时不把现有 `u16`、平面通道映射或数值快照固化为工程文件和前后端永久接口。

## 上次总结逐项校正

| 原总结要点 | 核查结果 | 应采用的说法 |
| --- | --- | --- |
| Rust 工作区已建立，模块彼此解耦 | 工作区属实；`dmx` 依赖 `engine::OutputSnapshot`，同时持有档案、配适与编码 | 已有初步模块划分，边界仍需调整 |
| 配适到 DMX 已形成闭环 | 能生成一次 512-slot 通道数据；没有物理发送、周期调度或服务进程 | 静态逻辑链路可运行 |
| 固定点值保证确定性 | 缩放／混合整数运算有固定规则；没有时间、随机、跨平台或负载验证 | 局部数值计算可复现，整体确定性待定义和验证 |
| Preset 更新能传播到 Cue | `tracked_state` 再求值时读取新 Preset；运行中的 Playback 保留旧数值 | 引用记录及重新求值有效，现场更新策略未实现 |
| 已有 Tracking | 顺序扫描稀疏 Cue 的 Set／Release；没有 Cue Only、Block、Part 或时间状态 | 基础静态跟踪求值 |
| 已有播放器 | 激活数值集合、设置电平、立即释放 | 静态 Playback 容器；还不是 Cue 播放状态机 |
| 有完整输出来源链 | 只记录 Playback 等贡献标识；Cue／Preset 来源在求值中丢失，默认及被抑制来源不完整 | 有初步贡献记录，完整解释链未实现 |
| 已验证核心 | 10 项测试与演示通过，但独立探针发现未覆盖边界 | 原型中的已测场景通过，不代表专业语义或实时可靠性通过 |

演示修改 Preset 的时机在 `tracked_state` 和 `activate` **之前**。因此演示本身没有测试“播放中更新 Preset”。

## 代码发现

P1 表示应在继续扩大核心能力、固定工程格式之前处理；P2 表示应随边界重构处理。这里不把尚未计划实现的功能一概称为程序缺陷。

### R01 · P1 · 替换 Cue 绕过编号唯一性检查

位置：`crates/stagemaster-show/src/lib.rs:229`，`Sequence::upsert_cue`。

已有同 ID 时直接替换；重复编号只在新增分支检查。探针创建编号 1、2 的两个 Cue，再把第二个 Cue 改成编号 1，返回成功并保留两个相同编号。与方法声明的错误契约冲突，也会影响排序与后续按编号操作。

处理要求：先对“其他 ID”做统一校验，成功后原子提交；失败不能改变已有序列。稳定 ID、显示编号、播放顺序分别建模。补新增碰撞、替换碰撞、失败后状态不变的回归场景。

### R02 · P1 · HTP 将默认值当成输出下限

位置：`crates/stagemaster-engine/src/lib.rs:135`，HTP 分支。

合成从 `descriptor.default` 起算再取最大值。默认 60%、唯一有效贡献 20% 时，输出仍为 60%。若默认值的含义是“无有效控制时回退”，这就是错误；显式下限应另设限制规则。现有测试默认值均为零，未覆盖。

处理要求：无有效贡献时使用默认；有贡献时按已声明的优先级和 HTP 规则求值。记录默认回退原因。推杆为零是否仍持有属性，也需由 Playback 模式明确规定。

### R03 · P1 · 不支持的属性可以被静默丢弃

位置：`crates/stagemaster-show/src/lib.rs:98`；`crates/stagemaster-engine/src/lib.rs:118`。

Programmer 设置字面量不检查灯具能力；Mixer 只遍历 descriptors，剩余贡献无错误、无诊断。提交 Intensity 和 Blue、仅提供 Intensity 描述时，输出只剩 Intensity。纯求值器可以依赖已验证输入，但目前没有承担该前置条件的编译边界。

处理要求：编辑与编译分别验证对象、属性和目标能力；错误携带地址与来源。运行入口只接纳已验证的计划。移动端保留不认识的内容与执行端拒绝不支持的内容，是两种明确行为，不能都做成静默忽略。

### R04 · P1 · 灯具领域与 DMX 映射尚未分离

位置：`crates/stagemaster-domain/src/lib.rs:114`；`crates/stagemaster-dmx/src/lib.rs:61`、`:139`、`:173`。

属性地址只有灯具与属性，档案是一个平面列表，每种属性仅能出现一次；没有子灯／像素／Geometry、功能区间、虚拟属性、条件依赖、档案版本引用。DMX 通道列表反向决定可用领域属性。将来加入多单元灯具、虚拟 Dimmer、换灯或非 DMX 设备时，会同时牵动 Programmer、Preset、效果与编码。

GDTF 官方模型已经区分 Geometry、DMXChannel、LogicalChannel、ChannelFunction、物理值范围和条件关系；当前简单映射不宜成为完整灯具模型。[GDTF 官方 DMX 模型](https://www.gdtf.eu/gdtf/file-spec/dmx-mode-collect/)

处理要求：档案与逻辑属性进入独立领域；编译期生成目标相关的输出映射。GDTF 作为导入导出适配格式，StageMaster 内部语义仍独立维护。

### R05 · P1 · 全部属性归一化为 u16 会限制未来表达

位置：`crates/stagemaster-domain/src/lib.rs:54`。

目前表示亮度比例很方便，但没有表达相对负偏移、带单位的角度、离散功能选择、颜色空间、无值／释放或时间语义的类型。相同数值在不同灯具上的物理含义也可能不同。问题在于把它当作唯一领域值，不在于使用整数本身。

处理要求：定义带类型的值、运算与转换；确定精度、溢出、舍入和限幅位置。DMX 8／16-bit 量化留在目标映射端。保存格式先通过这些实例验证。

### R06 · P1 · 引用、运行版本与来源链没有贯通

位置：`crates/stagemaster-show/src/lib.rs:255`；`crates/stagemaster-engine/src/lib.rs:45`。

`tracked_state` 输出纯数值，Runtime 也只保存纯数值；无法反查 Cue／Preset 或知道数据属于哪个工程修订。探针在激活后把 Preset 从 80% 改成 20%，Runtime 仍输出 80%，重新求值才得到 20%。这可以是合法的冻结播放策略，但当前没有策略契约和“已编辑／已编译／已生效”状态。

处理要求：编译产物携带修订、来源索引、依赖和语义版本；运行层明确何时切换计划、怎样保持播放位置、失败怎样保留旧计划。来源诊断与数值输出分别提供。

### R07 · P1 · 推杆与 LTP 的行为还没有专业语义规范

位置：`crates/stagemaster-engine/src/lib.rs:92`、`:150`。

当前同一 Playback 电平成为所有属性的混合权重，Pan、颜色等都会参与加权；电平为零时所有贡献消失。它可以用作某种交叉淡变模式，但尚未区分亮度推杆、LTP 接管、释放、效果 Size／Rate 和 Master。现有测试只覆盖满权重的简单 LTP。

处理要求：先写输出合成顺序及控制模式表，确定默认行为与显式选项，再实现和测试。不能仅凭“HTP／LTP”两个名字认定已等同成熟控台行为。

### R08 · P1 · 运行模型尚不满足持续稳定输出的设计要求

位置：`crates/stagemaster-engine/src/lib.rs:114`；`crates/stagemaster-dmx/src/lib.rs:249`。

每次求值创建树、向量、排序和完整 trace；尚无时钟、容量上限、命令队列、帧截止时间、线程与内存回收策略。`DmxSink::send` 未实现，接受数据和完成发送的状态也未区分。当前写法适合作为易读的参考求值器，不能据此声称具备持续实时引擎。

处理要求：编译期建立索引和容量预算，运行阶段采用有界数据结构；编辑、解析、媒体解码、存储和诊断离开关键执行路径。PortAudio 官方回调说明明确提醒避免分配、I/O、互斥等无确定上限的操作；这里借鉴其关键路径原则，不代表已经选定音频库或保证硬实时。[官方说明](https://files.portaudio.com/docs/v19-doxydocs/writing_a_callback.html)

### R09 · P2 · 身份与数值有效性约束未封装

位置：`crates/stagemaster-domain/src/lib.rs:7`；`crates/stagemaster-show/src/lib.rs:14`、`:182`。

`u64` 包装 ID 解决类型混用，但没有离线生成、导入重映射、跨工程与客户端冲突规则；未来 JSON 不能把任意 u64 当作普通 JS Number。Group 的公开字段可以绕过构造时的去重约束。CueNumber 对越界整数饱和处理，探针证明两个不同大编号得到相同结果。

处理要求：明确持久身份策略与字符串传输；受约束字段通过命令或验证构造器更新；编号超范围显式报错。不能用静默饱和替代用户编号校验。

### R10 · P2 · 文档层面的宏观边界尚未变成可验证接口

现有蓝图说清了大方向，但没有定义状态所有者、编辑和控制命令、计划激活、时钟跳变、恢复与迁移、设备能力及云端事务状态。后续实现者仍需要各自猜测。补充的[架构设计](architecture.md)给出默认边界、约束和验收场景；尚待验证的格式、库和性能数字保持明确开放。

## 开发顺序调整建议

1. **A0b：架构与契约收敛。** 先处理 R01–R09 中的核心边界；用多单元灯具、物理／相对值、多 Cue 跟踪、播放中编辑和音频跳时验证模型。形成可执行的契约测试，不直接扩大 UI 功能面。
2. **A1：可编辑、可恢复、带时间的单机闭环。** 完成版本化存储、撤销、编译与计划激活、Cue 状态机、基本效果、音频波形与时间线；Tauri／React 通过同一应用接口接入。
3. **A2：目标设备与持续输出验证。** 根据真实适配器测量帧发送、时钟误差、故障恢复与资源上限，形成支持范围。
4. 专业工作流深化及移动／Web／云端按原路线推进。其身份、能力、版本和权限边界在 A0b 定义，重型实现按需进入后续阶段。

架构完整性的验收标准是：新模块能沿着明确的接口接入，能解释失败和状态变化，能独立验证；并且当前代表性节目不需要绕过这些边界才能工作。
