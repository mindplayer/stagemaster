# 实体控台与双向硬件控制面

日期：2026-09-11。状态：用户明确未来要做专业硬件控台；本文件准备模块与伪 API，没有电路、固件、驱动或实机实现。沿用 Rust＋TypeScript 与[架构 v0.5](architecture.md)，实体控台与软件使用同一工程语义和控制服务。

## 1. 产品形态与职责

同一控制面架构覆盖：电脑＋USB 推子翼；带主板和屏幕的一体控台；通过网络连接引擎的分体控制面；多个扩展翼。控制面可以不带舞台预演 GPU，预演机、媒体服务器和音频系统仍可独立部署。

| 部分 | 责任 |
| --- | --- |
| 控制面 MCU／固件 | 采样按键／ADC／编码器、去抖、校准、报告真实状态、执行有期限的反馈；电动推子的本地驱动与触摸仲裁 |
| 传输适配器 | USB HID、MIDI、串行或受验证的网络协议；枚举、会话、收发、热插拔和格式转换 |
| 控制面协调器 | 硬件能力、映射修订、页／层、手势、拾取、控制权和重新同步 |
| 核心控制网关 | 统一校验与执行语义，应用后产生权威状态／回执 |
| 反馈投影器 | 把权威状态变成指示灯、灯环、小屏标签、电动推子目标与诊断 |

硬件输入与 DMX／RS485 输出是不同接口。推子翼不直接写灯具通道；同一个推子可按映射控制灯光 Playback、Programmer 属性或外部系统参数，但都经过相应语义网关与权限校验。CPU 主板、输入 MCU 和物理 DMX 输出板也不要求是同一芯片。

## 2. 接口必须描述的控件

| 控件 | 输入 | 反馈／配置 |
| --- | --- | --- |
| 普通推子 | 绝对位置、原始量程／分辨率、校准与可选触摸 | 当前逻辑值、拾取方向、标签；硬件位置和逻辑值分开 |
| 电动推子 | 位置、触摸、故障状态 | 目标位置、映射代次、有效期限、跟随／暂停；触摸时不得与手争夺位置 |
| 无尽编码器 | 有符号相对增量、可选按压／触摸 | 数值／单位、环形灯、粗细模式；不强行当成绝对电位器 |
| 电位器 | 有量程的绝对值 | 校准、拾取或明确的接管方式 |
| 按键／矩阵 | press、release、当前保持状态与序号 | 颜色、亮灭／闪烁、当前功能；短／长按和组合键由约定的一层识别 |
| 摇杆／轨迹球／触摸条 | 多轴、绝对／相对、触摸状态 | 轴映射与灵敏度，坐标／单位明确 |
| 小屏／标签条／指示灯 | 可选本地交互 | 稳定逻辑标签、值、单位、颜色、状态；屏幕资源传输与低延迟按钮事件分开 |

原始分辨率和校准能力保留到输入层，再转换为核心值；不因为 DMX 常见 8-bit 就把推子／编码器提前压成 0–255。实际有效精度仍取决于电路、机械、采样和校准，不能由接口位数承诺。

## 3. 可选接入协议

| 路线 | 用途 | 选型约束 |
| --- | --- | --- |
| USB HID | 自有控制面、双向输入／输出与能力报告 | 描述符、报告大小、更新率和系统 API 需验证；类支持不等于所有自定义用法都被系统自动理解 |
| MIDI 1.0／2.0 | 接入已有推子、键盘和编码器设备 | MIDI 1.0 各消息分辨率不同，2.0 的高分辨率／能力协商需两端支持；相对旋钮编码也需档案映射 |
| MCU 串行／网络协议 | 自有板卡、分体面板或扩展翼 | 明确版本、帧边界、校验、心跳、序号、时钟与重连；网络控制面必须有独立认证和控制权 |
| 机内 GPIO／ADC／编码器接口 | 一体控台内部 | 经控制面固件／平台驱动封装；不把电路扫描塞进灯光实时循环 |

依据：[USB-IF HID](https://www.usb.org/hid)、[MIDI 2.0 与能力协商](https://midi.org/details-about-midi-2-0-midi-ci-profiles-and-property-exchange-updated-june-2023)、[MIDI 2.0 实际兼容差异](https://midi.org/the-state-of-midi-2-0-high-resolution-performance-and-the-rise-of-profiles-update-feb-2026)。现阶段准备可替换适配，不同时实现全部协议，不要求新增一种主业务语言；固件语言按 MCU 工具链另定。

## 4. 提前固定的交互规则

### 推子接管与翻页

非电动推子默认采用软拾取：新页逻辑值为 20%、物理推子在 80% 时，显示拾取方向，在满足阈值／跨越规则前不把逻辑值跳到 80%。跳变和比例接管可作为明确配置；拾取阈值、噪声过滤与当前状态变化后的行为写入映射策略。

电动推子翻页后按权威值跟随，但触摸期间暂停电机；松开后的继续跟随／接管策略必须明确。旧反馈不能驱动新页推子。失联或反馈期限到期时由固件停止电机跟随，不能默认回零。限位、校准和本地电机控制属于固件能力，不通过 UI 定时器实现。

旋钮增量由适配器统一正负方向和单位；加速曲线、粗细切换只在约定层计算一次。旋钮按下与旋转可组成手势，但不会因为灯环反馈再生成一次旋转输入。

### 按键、手势与丢事件

按下／松开必须成对管理，Flash／临时覆盖使用有期限的手势／贡献身份。翻页、断开或会话取消时，释放原手势作用范围，不对新页同位置按钮发 Release，也不把所有 Playback 停掉。缺少 release 时通过断连／手势超时政策收回临时贡献。

设备初次连接或重新同步时的“某按钮仍按下”只是状态快照，不是新 press；不能因此重放 Go。离散事件有序处理，队列溢出或序号缺口进入 resync；连续绝对位置可合并，旋钮增量应累加并计溢出，不能简单丢到只剩最后一个增量。

合并与增量累加不能越过 Record、Go、模式切换或释放屏障，也不能跨控制权和映射代次；否则可能改变已记录的值或动作次序。

### 版本、控制权与反馈

输入带 SurfaceSessionId／连接代次、序号、当前映射代次及观测时刻。固件不能携带映射代次时，驱动与协调器必须在翻页时设置输入屏障、清理旧队列并重新取得基准，不凭接收时刻猜旧事件属于新页。驱动通过 `rebaseInput(context)` 安装新上下文并返回带序号的基准；不能确认旧输入已经排空的协议，应暂停该映射并要求重新同步，不能保证按收到的时间分辨所有在途事件。

映射绑定逻辑对象 ID，不绑定数组下标。硬件配置版本、页／层映射代次、运行计划和控制租约分开管理；清楚规定同时操作触屏、鼠标、推子和远端平板时的控制权。不能因为输入来自物理 USB 就绕过授权。

软件先登记请求，再显示接纳／应用／外部反馈状态。指示灯和电动推子从权威状态派生，不拿“最后发出的值”冒充外部已执行值。反馈标记来源与代次，设备位置回报须区分用户操作和电机回声，防止双向回授循环。

Blackout、停止序列、释放临时贡献、关闭端口和设备停机分别映射到明确命令；它们不共用一个含义模糊的 Stop，也不把普通软件按钮定义成所有设备的物理急停。

## 5. 类／接口怎样调用

数据草案见 [surface-contracts.ts](module-api/surface-contracts.ts)。这是宿主内部接口，原始输入和反馈不注册为任意客户端可调用的 StageClient RPC；将来网络面板须先通过专用认证入口再进入同一协调器。

1. `SurfaceDriver.describe()`：读取控制面身份、协议／固件版本和控件能力。
2. `SurfaceCoordinator.attach(driver, profile, operatorSession)`：通过宿主操作会话连接面板，取得基准快照；开机未载入节目也可连接，后续映射目标分别申请业务授权。
3. `SurfaceCoordinator.applyMapping(expectedContext, bindings)`：检查对象、控件兼容性与能力，通过 `driver.rebaseInput(newContext)` 完成屏障和基准，再启用新映射，初始化拾取／手势状态；失败时保持输入禁用并报告待同步。
4. 宿主从驱动读 `SurfaceInput`，调用 `ingest`：去重、顺序与代次校验后，转换为现有 ControlCommand 或 ExternalAction。此处不执行硬件输出系统调用。
5. 反馈投影器读取已应用状态，调用 `feedback`：驱动发送灯、标签和有期限的电机目标；不能让反馈失败反向阻塞灯光运行。
6. `detach`：停输入、终止临时手势、停止电机跟随并回收控制面资源。现场节目继续遵守自己的运行政策。

连接 token 不等于 ControlLease；协调器对每个映射目标从现有控制权服务取得并维护授权。暂不支持的 Flash、Masters 或外部参数语义应禁用映射并报告，不用驱动层临时模拟未实现业务。

播放目标在启用映射时解析到对应 ActiveRun；盲编、系统设置和手动外部操作不要求 ActiveRun。SurfaceBinding 是临时解析结果，持久映射只保存逻辑控件／目标 ID；节目卸载可禁用播放映射，面板连接和其他有效映射继续。

`validUntil` 属于明确时钟域。适配器须将剩余有效期保守转换成设备本地看门狗期限；不能把主机时间戳直接当 MCU 时间。电机反馈过期只停止跟随，不隐含回零或强行保持扭矩。描述符、数值范围、映射组合和反馈目标都需要运行时校验，TypeScript 类型不能代替设备能力检查。

## 6. 一体控台的宿主准备

引擎可无界面启动；UI、控制面驱动、监听模块分别管理生命周期。绑定配置和校准与 Show 内容分开保存，换主板重新探测设备能力，再绑定稳定控件身份。扩展翼顺序、USB 插口或屏幕枚举变化不自动改变逻辑执行器。

专业主机需验证启动顺序、独立进程崩溃、USB／网络热插拔、存储满、负载和恢复；恢复时从权威快照重建标签与位置，已播放节目不因为控制面重启被重新 Go。固件升级、硬件自检和校准是独立维护流程，不在演出中自动执行。

跨设备复用目标是相同语义、映射和协议；MCU 只做控制面可以运行较小固件，不要求它承载整个控台引擎。新的硬件类别通过描述符、适配器和能力测试接入，不能在 Cue／Effect 中散布主板型号判断。

## 7. 首个原型与验收

先用虚拟控制面与录制输入验证 4 个推子、4 个编码器、若干按键、指示灯和标签；再接一个已有 USB／MIDI 设备验证真实收发。电动推子另做受控实机测试；这些数量是验证样例，不是产品上限或最终面板布局。

必须覆盖：20%／80% 跨页拾取；编码器增量与粗细模式；长按中翻页；Flash 松开丢失；Go 重复／重连不重放；旧映射输入和旧反馈拒绝；触摸时电机暂停；无触摸检测设备的降级；灯环反馈不回授；多翼重连不串位；反馈／屏幕堵塞不阻塞输入与 DMX。测量输入到核心应用及反馈的延迟、抖动、丢事件、采样噪声和资源预算。

当前仅完成接口准备，无硬件实时性或可靠性结论。
