# 开发语言与跨平台技术评估

> 本文记录早期评估过程。随后完成了[开源框架对比](open-framework-comparison.md)与[最终技术评估](final-technology-assessment.md)。用户于 2026-09-10 已确认 Tauri 2＋Rust＋TypeScript、React＋Vite 界面，以及 Fastify＋PostgreSQL＋对象存储服务器端。当前以最终评估记录的框架为开发基线；下文的早期优先级与当时状态仅供追溯，均不是已验证的实现结论。

早期评估日期：2026-09-10。当时状态：资料核查与架构建议，尚未冻结选型，未进行性能基准或真实设备测试；最新确认状态见上方说明。

当前目标是对标 MA3／老虎控台的专业单机灯光系统。用户目前使用 macOS，未来需要适配多种平台；此前提出 C++26，但本次明确要求开放评估其他语言。下文的优先级是本项目的工程判断，不是语言性能排行榜，也不推断 MA3／老虎的内部实现。

**当前建议：Rust 承担无界面的领域规则与播放核心，Qt 6／QML 和 Tauri／TypeScript 均作为专业桌面界面的第一梯队候选，硬件适配按 SDK 和平台单独选型。** macOS 作为首个开发与验证平台，Windows、Linux 纳入桌面目标；平板、浏览器和微控制器分阶段适配。Qt 的初始优先级来自对专业桌面交互的判断，尚无本项目实测证明其优于 Tauri；补充评估后，不再要求 Tauri 等 Qt 验证失败才进入原型阶段。C++／Qt 是减少 Rust 与 C++ 集成工作的备选，Rust／Avalonia 也是界面备选。

**评估依据**

重点考察五件事：播放时序是否可控；复杂工程和并发状态是否容易维护；专业桌面交互是否容易实现；平台与设备 SDK 是否可接入；构建、发布和商业许可成本是否可承担。吞吐量、内存安全、时序正确性、界面流畅度是不同维度，不能相互替代。

**核心语言比较**

| 语言 | 本项目适用位置 | 优势与代价 | 当前判断 |
| --- | --- | --- | --- |
| Rust | 工程与领域规则、校验、Cue／效果计算、播放与输出适配 | 无垃圾回收，所有权和类型系统帮助约束内存及并发使用；复杂可变对象关系需要认真设计，原生 SDK 可能需要绑定 | 新项目核心首选候选 |
| C++ | 核心引擎、Qt 界面适配、音频与硬件库接入 | 与 Qt 和 C／C++ 库直接集成，资源控制明确；生命周期、并发与未定义行为需要额外审查和检测 | 与 Rust 同属第一梯队，整体集成成本较低 |
| C | 固件、底层驱动、跨语言边界 | 接口直接，适合小而稳定的底层模块；复杂工程模型与编辑业务的维护工作量较大 | 局部使用，不建议作为整个应用的主语言 |
| C# | Avalonia 桌面界面、工程管理、工具 | 可作为专业桌面应用语言；托管运行时的 GC 行为需要单独预算 | 界面强候选，关键播放循环仍优先考虑独立原生核心 |
| TypeScript | Tauri／Electron 界面、未来浏览器控制端 | 便于复用网页交互与工具；运行时、渲染和消息传递需要管理 | 界面候选，不用界面事件循环承担输出主时钟 |
| Dart | Flutter 桌面／平板界面 | 官方支持三大桌面平台；多窗口、输入、图形与原生插件需要用实际控台交互验证 | 多端界面备选，当前不优先于 Qt |
| Go | 后续设备管理、网关或服务工具 | 适合独立服务模块；标准运行时含 GC，本项目暂时没有足够理由为核心再引入它 | 有对应需求再选，不用于首期关键播放循环 |
| Python | 灯具档案转换、测试数据、分析、开发工具 | 适合短脚本与离线流程 | 工具语言，不承担本项目的实时播放责任 |
| Zig | 小型原生模块、底层探索 | 显式控制流和内存分配有吸引力；需要额外验证我们所需 GUI、音频、驱动的集成路径 | 暂不作为主线，可在具体模块有收益时重新评估 |

Rust 的官方说明列出无 GC、所有权和类型系统等能力；这些机制不保证业务逻辑、截止时间、第三方 unsafe 代码或驱动没有问题。[Rust 官方说明](https://rust-lang.org/)。C# 与 Go 的 GC 是需要纳入时序分析的运行时行为，并不代表它们不能制作灯控软件；本项目优先原生播放核心是为了减少关键路径中的变量。[.NET 延迟模式](https://learn.microsoft.com/en-us/dotnet/standard/garbage-collection/latency)、[Go GC 指南](https://go.dev/doc/gc-guide)。Dart／Flutter 与 Zig 的相关能力依据其官方资料。[Flutter 桌面支持](https://docs.flutter.dev/platform-integration/desktop)、[Zig 语言概览](https://ziglang.org/learn/overview/)。

**Rust 与 C++ 的实际取舍**

在没有必须复用的旧 C++ 核心时，我更倾向 Rust：先把配适、属性、预设、Cue、播放状态和合成规则放进可独立测试的核心，减少长期迭代中的内存与并发错误面。这里的依据是可维护性，尚无本项目证据说明 Rust 的运行速度高于 C++。

如果原型表明大量关键依赖只能通过 C++ 接入，或者跨语言构建与调试成本明显影响交付，选择 C++ 核心同样合理。即使界面和核心都用 C++，也仍需独立模块、明确依赖方向和可替换接口。

C++ 语言与 C++26 标准版本需要分别决定。本次核查时，Clang 的官方列表仍存在未实现的 C++26 特性，GCC 仍将其支持标为实验性。若采用 C++，建议先以目标工具链共同支持的 C++20／23 特性为基线，按需引入经过验证的 C++26 特性；不把完整 C++26 支持作为跨平台产品的前置条件。[Clang 支持表](https://clang.llvm.org/cxx_status.html)、[GCC 支持表](https://gcc.gnu.org/projects/cxx-status.html)。

**专业桌面界面比较**

| 路线 | 对本项目的价值 | 需要承担的成本 | 建议 |
| --- | --- | --- | --- |
| Qt 6／QML＋少量 C++ | QML 负责界面表达，C++ 接入原生能力；适合列入多窗口、触摸、表格、执行器和时间线的原型验证 | Qt 部分模块有不同许可；Rust 核心需要桥接或本机通信；专业控台控件仍需自建 | 第一梯队候选 |
| C#／Avalonia | 跨平台桌面路线，主框架 MIT 许可；不必因为当前在 macOS 开发而排除 C# | 自定义绘制、输入、多屏与设备接入仍要验证；与 Rust 组合需要接口层 | 第二候选，尤其在 Qt 许可条件不合适时 |
| TypeScript／Tauri | Rust 与 WebView 界面组合，便于未来扩展浏览器控制端 | 不同平台 WebView 与桌面交互差异需要测试；大量状态更新应批量传输、按界面需要降频 | 第一梯队候选，可直接进入原型验证 |
| Dart／Flutter | 同时考虑桌面和平板时值得评估 | 复杂桌面控台交互与原生插件适配需验证，不能只按移动端体验判断 | 后续多端权重提高时重新比较 |
| Rust／Slint | 可与 Rust 直接集成，支持声明式界面与多种宿主语言 | 需要验证实际专业控台控件、桌面交互及目标产品许可条件 | 有界面原型证据后再提升优先级 |

Qt Quick 提供 QML 与 C++ 接入面，Qt 官方列出 Windows、macOS、Linux 的支持配置；这些事实支持把它列入候选，不能证明我们的控台界面已经达到流畅性或可靠性要求。[Qt Quick](https://doc.qt.io/qt-6/qtquick-index.html)、[Qt 平台支持](https://doc.qt.io/qt-6/supported-platforms.html)。Avalonia 支持三大桌面平台，但支持等级随系统版本变化；主仓库采用 MIT，不能自动推及所有扩展包。[Avalonia 平台支持](https://docs.avaloniaui.net/docs/supported-platforms)、[Avalonia 许可证](https://github.com/AvaloniaUI/Avalonia/blob/main/licence.md)。Tauri 的组合方式来自其架构文档，Slint 的语言接口及许可需要依据实际产品范围确认。[Tauri 架构](https://v2.tauri.app/concept/architecture/)、[Slint 官方说明](https://slint.dev/)。

Qt 的 LGPL 部分可以在满足条款的前提下用于闭源应用，也有仅提供 GPL 或商业许可的模块。应在选定模块时确认，例如不能默认 Qt Quick 3D、Qt Quick Timeline 或 Qt Virtual Keyboard 都可按 LGPL 使用。自研音频时间线并不要求依赖同名 Qt 模块。当前未购买许可证，也未对产品发布作出许可合规结论。[Qt 许可与模块列表](https://doc.qt.io/qt-6/licensing.html)。

**建议的语言分工**

| 模块 | 建议实现 | 边界要求 |
| --- | --- | --- |
| 工程模型、领域规则与编辑命令 | Rust | 规则只有一个权威实现；界面不重复实现 Cue、预设、合成等语义 |
| 播放时钟、调度、效果与输出合成 | Rust | 与工程文件读写、界面刷新分离，关键循环使用预先准备的数据 |
| 桌面界面 | Qt 的 QML／C++，或 Tauri 的 TypeScript／Rust 适配层 | 提交命令、显示状态、处理交互，不持有输出主时钟 |
| 音频与 DMX 平台适配 | Rust 或 SDK 所需的 C／C++ | 向核心提供一致接口，隔离系统 API、驱动和第三方库 |
| 后续浏览器／简化控制端 | 按届时需求考虑 TypeScript | 使用控制协议，避免复制完整编程与播放规则 |
| 后续 MCU 固件 | 按芯片 SDK 评估 C／C++／Rust | 不强行编译桌面全部代码；支持能力由发布契约校验 |

模块化不要求跨进程，但进程隔离可以作为防止界面崩溃直接结束播放的方案评估。若采用它，保持一个桌面程序加一个本机引擎进程，由启动器管理；需要设计连接中断、版本兼容、状态重取、队列上限和关闭行为。若使用同进程 Rust／C++ 桥接，则应封装所有权和线程边界；CXX 是可调查的具体工具，但它不提供进程故障隔离，也不能保证任意第三方 C++ 实现安全。[CXX 官方文档](https://cxx.rs/)。

**如何实现通用性**

macOS 是先验证的平台；工程格式、领域语义和引擎接口从第一天按跨平台设计。核心尽早在 Windows、Linux 编译和跑一致性测试，桌面界面与驱动逐平台验收。Rust 官方支持矩阵覆盖相应桌面及 ARM Linux 目标，但支持等级、最低系统与依赖条件需要按所选目标核对。[Rust 平台支持](https://doc.rust-lang.org/rustc/platform-support.html)。

跨平台需要可移植的文件路径、时间与设备接口，不让 macOS 的系统对象进入核心数据模型。同一工程在不同平台应遵守相同的控制语义；数值误差容限或逐位一致要求要单独定义，不能假定跨 CPU 浮点运算天然逐位一致。

平板和浏览器可以使用适合触摸与远程操作的界面，复用工程契约、控制协议和能够移植的核心。是否本机运行完整引擎，要结合各平台能力决定，不预先承诺所有终端运行完全相同的程序。

ARM Linux 与 ESP32-S3 不能作为同一种目标处理。后者涉及独立资源限制和 Xtensa 工具链；Espressif 的 Rust 文档要求为 Xtensa 配置相应工具链，所以当前不承诺桌面 Rust 核心可直接完整运行在 ESP32-S3 上。[Espressif 工具链说明](https://docs.espressif.com/projects/rust/book/getting-started/toolchain.html)。

**稳定性必须覆盖完整输出链路**

建议将工程解析与编辑、时刻对应的属性计算、DMX 帧输出、物理信号生成分开。输入界面的重绘、自动保存、波形生成和后台日志不应占用关键播放路径。音频回调中避免耗时无上界的操作也有明确实践依据；PortAudio 文档特别指出内存分配、文件 I/O 和互斥操作等风险。[PortAudio 回调说明](https://portaudio.com/docs/v19-doxydocs/writing_a_callback.html)。这不等于已选择 PortAudio。

Rust 或 C++ 都不能仅凭语言保证在通用桌面系统上按时输出。建议使用具备明确时序责任的 DMX 接口硬件或网络节点。作为机制示例，ENTTEC DMX USB Pro 使用内部缓冲与定时器维持输出，但其文档也明确软件发出的每个包并不保证与一个实际 DMX 帧一一对应；稳定刷新和节目事件精确落到输出上是两项不同验证。[ENTTEC API 说明](https://support.enttec.com/dmx/usbdmx-dmx-usb-pro-70304/dmx-usb-pro-api)。这只是架构证据，不是设备采购决定。

**冻结选型前的最小验证**

1. 由用户提供一个熟悉的代表性节目，明确灯具、Universe、并发播放、效果、音频同步和操作要求；以此确定负载与验收阈值。
2. 在首选 Rust 核心上实现有限的播放链路，用同一组数据验证 Cue 切换、淡入淡出、合成、停止与释放等约定语义；只有发现具体障碍时才做对应 C++ 对照，不并行开发两套完整系统。
3. 从 Qt／Tauri 中选择一个制作包含密集选灯、属性编辑、执行器、波形时间线和多窗口的代表性界面原型；测量交互与绘制成本，不必先开发两套完整界面。若结果暴露具体障碍，再用相同场景验证另一候选或 Avalonia。
4. 在编辑、保存与界面高负载并发时记录引擎计算耗时、调度抖动、队列积压、内存增长及音频偏差；平均帧率不能替代尾部延迟和漏期统计。
5. 逐平台验证构建、安装、输入法、多屏、系统休眠恢复、设备断连与输出恢复。实际信号时序需要授权后用真实接口与测量设备验证，模拟输出不算硬件验收。

当前结论足以选择原型方向，不能作为商业稳定性证明。最可能改变建议的因素是首批硬件 SDK、专业界面原型结果、Qt 模块许可条件和代表性节目测量结果。

**Tauri 专项补充评估**

Tauri 是应用框架，不是另一种开发语言。它组合 WebView 界面与 Rust 主进程，桌面窗口、系统集成和前后端通信由框架提供；灯光领域与播放语义仍由独立核心负责。对于希望跨平台、允许多语言、强调解耦的本项目，这是一条适合直接验证的路线。[Tauri 进程模型](https://v2.tauri.app/concept/process-model/)。

建议使用 TypeScript 编写选灯、属性面板、执行器与时间线交互；Tauri 的 Rust 层只处理窗口、命令入口和系统适配；灯光引擎保持为不依赖 Tauri、DOM 或前端框架的 Rust 模块。界面选择 React、Vue 或 Svelte 是下一层决策，不与灯光核心绑定。串口／USB 访问由原生适配层承担，不依赖浏览器串口接口。

Tauri 提供多窗口 API，官方也支持 macOS、Windows、Linux、Android 和 iOS，但各平台输入、图形、原生插件与后台运行行为仍需分别验证；支持移动端不代表桌面引擎、进程模型与硬件驱动可以原样搬到手机上。未来浏览器控制端可复用部分界面代码，通过替换宿主接口连接引擎。[Tauri 平台范围](https://tauri.app/)、[多窗口 API](https://v2.tauri.app/reference/javascript/api/namespacewebviewwindow/)。

界面性能的重点验证是灯具表格、密集执行器、波形缩放拖动、多屏与高 DPI。建议用虚拟列表控制可见元素数量，波形峰值在后台准备，复杂绘制按场景采用 Canvas／GPU 路线；这些是待测设计，不是已证明的性能结果。音频播放和节目时钟应由引擎的音频适配负责，界面只显示波形与播放位置。

命令、确认和状态流应分开：GO、STOP 等操作不能与普通显示状态采用同样的丢弃策略；状态预览可以按界面订阅范围合并、限频。Tauri 官方明确通用事件系统不针对低延迟或高吞吐，较大的连续数据应评估 Channels 或其他适当传输方式；Channels 本身也不等于实时调度器。[Tauri 通信说明](https://v2.tauri.app/develop/calling-frontend/)。

Tauri 已有 WebView 与主进程分离，但这不意味着灯光引擎自动与 Tauri 主进程故障隔离。若要求重启整个界面仍持续播放，可以评估独立引擎进程：与桌面软件一起打包，通过本机协议连接。Tauri 支持随应用附带外部程序，但每个平台需要相应二进制，启动、关闭、重连和失联输出策略必须自行设计；不能默认 sidecar 在宿主退出后会按我们的业务要求继续运行。[外部程序打包](https://v2.tauri.app/develop/sidecar/)。

另一个实际代价是 WebView 差异：Windows 使用 WebView2，macOS 使用 WKWebView，Linux 使用 WebKitGTK。应选择共同可用的前端能力，并分别验证图形、字体、输入法与多屏交互。核心一致性与界面兼容性要分开验收。[WebView 差异](https://v2.tauri.app/reference/webview-versions/)。

**手机、平板编排与代码复用**

用户进一步明确：后续手机、平板 App 需要具备简单编排能力，并尽量一次开发、多端适配。这提升了共享界面与移动端本地核心的重要性，进一步支持将 Tauri 作为主方案候选；当前仍先实现专业单机系统。

建议采用同一代码库、共享业务模块、按平台构建的方式。Rust 的工程规则、编辑命令、Cue／效果语义尽量复用；TypeScript 的控件、状态展示和编辑交互复用，桌面、平板和手机分别组织布局。Tauri 支持将 Web 前端与 Rust 结合，并在移动端通过 Swift／Kotlin 插件接入需要的平台能力，因此不能把共享代码理解为所有系统完全不需要适配。[Tauri 框架说明](https://v2.tauri.app/start/)、[移动端插件](https://v2.tauri.app/develop/plugins/develop-mobile/)。

桌面提供多面板、多窗口和完整工作流程；平板提供适合触摸的选灯、属性、Cue 和基础时间线编辑；手机通过分步操作完成小范围编排与修改。这些是界面组织建议，最终范围由实际使用流程确定，不把桌面界面简单缩小到手机。

移动端简单编排建议支持本地打开、修改与保存工程，不以电脑在线或云服务为前提。核心按移动目标编译为可嵌入模块，通过宿主接口使用；不把桌面引擎独立进程或 sidecar 机制设为移动端必需条件。工程与媒体传递另设接口，云同步是可选扩展；如果未来需要并发编辑，再单独设计版本冲突处理。

共同工程格式需要保证往返编辑：手机不能编辑的高级内容应明确展示其状态并保留，不能保存后静默丢失。应以“桌面工程在移动端修改一个 Cue 后，未编辑部分仍完整”为一致性测试用例；无法安全保留的版本或结构应限制写入并说明原因。

本地编排、前台预览和锁屏后持续输出分别评估。移动系统会限制后台执行，不能仅凭 Tauri 支持移动端就承诺锁屏后稳定持续发 DMX。持续现场播放优先由适合该任务的电脑或盒子承担；移动端直接输出是否支持，再按系统、连接方式与实测结果确认。[Apple 后台执行](https://developer.apple.com/documentation/uikit/extending-your-app-s-background-execution-time?changes=_6)、[Android 后台任务](https://developer.android.com/develop/background-work/background-tasks)。

原型阶段尽早验证同一基础工程与编辑命令在桌面和至少一个移动目标上可编译、运行和保存，暴露依赖问题；这属于验证代码可移植性，不代表提前完整开发手机和平板产品。复用比例需要依据实际模块统计，不预先承诺百分比。
