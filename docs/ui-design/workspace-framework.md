# 编排工作区总体框架与共同指向

## UX-016：演出编排与剪映式区域布局

2026-09-30；基线 `a14411a`。用户明确整体布局参考剪映，日常创作同时大量依据剧本／演出脚本。本节优先于旧版默认时间线的表述；这是设计约束；UX-017 已接通下面的固定区域布局，完整剧本功能仍未实现。

产品围绕演出组织。音乐、台词、演员动作、导演提示都是编排依据，不能全部归约成音乐上的秒数。借鉴 [CapCut 官方桌面界面](https://www.capcut.com/resource/how-to-use-capcut-on-pc) 的资源、预览、属性和下方编排分区；国内剪映页面本次抓取超时，使用官方海外产品示例参考布局，不声称核对了当前国内版全部界面。参考 [QLab 5 步骤衔接](https://reference.qlab.app/docs/v5/fundamentals/cue-sequences/) 的人工启动、开始后衔接、完成后衔接与段落时间编排，按本项目运行契约逐步吸收。

| 区域 | 职责 |
| --- | --- |
| 顶栏 | 工程、保存／撤销、编排／排练和设备状态；常用操作集中，减少多行大按钮 |
| 左侧 | 剧目段落、场景、灯组、效果与媒体资源，按类别展示；剧本文档接通后定位幕／场及提示 |
| 中央 | 唯一舞台画布，二维布置或内嵌三维；切任务保留相机／选择，不再上下叠两块大画布 |
| 右侧 | 当前步骤、场景、灯具或空间的属性；位置固定，内容随对象变化 |
| 底部 | 执行步骤表或时间线；选择、查找、排序、定位及相应播放控制就近组织 |

**剧本／执行步骤**按幕、场或段落组织，显示步骤编号、名称、台词／动作提示、关联场景、渐变／延时和推进方式。人工等待没有固定结束时间；突出当前／下一步骤。文档修订及步骤关联采用稳定 ID，不能只依靠易变的行号或页码；完整剧本导入、锚点与修订追踪后续另定契约。

**定时段落**使用段落相对时间安排灯光及已接通媒体，可以有音乐也可以没有音乐。播放头、进度条和时基属于当前定时段落，不能自动代表整场演出进度。

**混合演出**的目标流程为：台词提示后人工执行蓝色侧光；下一次人工执行启动预编的音乐灯光段落；段落结束再等待演员。须明确段落开始、完成、取消和人工接管，不能把“等待一句台词”硬填为全场某秒。文本提示先由操作人员判断，不自动当成语音识别或传感器触发。

两种组织方式引用同一场景、灯具、媒体和工程事务，保持各自真实的排序／时基语义；切换展示不执行、不重载声音、不自动互转数据。编辑选择、预演位置和现场执行位置分别持有；选中下一步骤仅用于编辑，明确执行才改变运行。人工段落显示步骤与等待原因，定时段落显示局部时间，控制栏明确当前控制对象。

当前 [场景列表](../module-api/sequence-preview.md) 已支持人工推进、渐变结束后计时等待，`waitMs: null` 为人工；不等同于 QLab 所有衔接方式。当前 [音频卡点](../module-api/audio-editing.md) 已支持单音乐范围内灯光定位。完整剧本对象、无音乐任意时间线、混合段落调度与外部触发仍待实现，需在 Rust 契约中增量落实，不在 TS 或 UE 中另造执行语义。

实施先将既有场景／列表／音频能力放入共同区域，再补剧本提示关联与执行步骤工作流，最后扩展混合段落调度。分隔条、侧栏折叠和恢复布局属于界面偏好，不进入演出领域文件。验收覆盖无音乐人工演出、定时段落和混合演出；每项以实际接通能力为准，不把后续功能提前点亮。

MacBook 布局验收同时检查中央画布与下方编排可见、侧栏各自滚动、窄窗可恢复；选择／搜索、精确输入、排序复制、取消、撤销、保存和返回上下文分别验证。只读视觉审查及限制见 [UX-016](../development/tasks/UX-016-performance-workspace.md)。

## 总体结构

以“舞台看空间、时间线看过程、属性区改内容”为稳定骨架。日常创作留在一个工作区，避免为了改一个参数离开正在编辑的节目。

| 区域 | 内容与职责 | 扩展方式 |
| --- | --- | --- |
| 顶栏 | 工程名、保存状态、撤销／重做、编排／现场入口 | 文件菜单承接新建／打开；工程设置和设备管理按需打开，不挤占创作区 |
| 左侧资源区 | 灯具／灯组、场景／效果、预设／目标点 | 当前类别用紧凑列表；素材接通后在此管理音视频资源，不新增独立软件式首页 |
| 中央舞台区 | 二维／三维视图、点选／框选灯具、空间摆位、光束指向 | 可放大；保留观察视角和编辑对象。专业预演后端接同一对象和选择体系 |
| 右侧属性区 | 正在编辑的场景／片段、作用灯组、亮度／颜色／指向及效果参数 | 位置固定、内容随对象变化；高级曲线／灯具顺序在同一上下文展开 |
| 下方编排区 | 时间线、片段、标记、属性曲线；另可切到场景列表 | 时间线与场景列表是不同组织方式，切换不会自动转换数据或启动节目 |
| 编排区工具条 | 唯一的离线预览控制、当前时间、缩放 | 现场运行状态与编辑预览分别表达；音视频监听／监看后续在舞台旁按需展开 |

桌面初始比例：资源区约 200–240 像素、属性区约 280–320 像素，中间保留主要空间；下方编排约占内容高度的 25%–35%。这些是实际 MacBook 视口的待测起点，不是固定宽度门槛。侧栏可折叠、分隔条可调整、布局可恢复；较窄窗口先收起资源，不能把舞台挤成不可操作的小窗。

现场模式以后提供固定执行区、推子、当前／待选场景及输出状态；不复制一套工程编辑器。未接通能力不出现在正式软件中充当可执行按钮。音视频监看、投影定位、机构状态未来用相同资源／舞台／时间／属性关系接入；机构不复用灯具指向命令或安全规则。

## 舞台工具只区分三种意图

| 工具 | 拖动对象 | 改变的内容 |
| --- | --- | --- |
| 选择 | 灯具／框选区域 | 选中集合；不改变安装位置或灯光输出 |
| 布置 | 灯具、桁架、舞台物体的空间把手 | 安装位置与姿态；对已有编排的影响须由应用层处理 |
| 指向 | 灯具光束的目标点／目标平面 | 所选编辑对象的空间指向；灯具安装位置保持不动 |

镜头旋转／平移／缩放属于观察操作，三种工具下均可使用，不混入工程撤销历史。把“聚焦所选”留给镜头操作，把“光学调焦”留给光学清晰度；不把光束指向命名为含糊的“对焦”。

“布置”中的场地、舞台与观众区创建详见 [UX-007](venue-layout-design.md)：先在平面定轮廓／尺寸，再同步生成三维；观众区按规则排布，独立过道自动排除相交座位。舞台与观众区是场地中的并列对象，普通舞台移动不会带走整个观众席。该方案尚未实施。

UX-011 补充：布置须容纳不同轮廓、地面标高和净高的多个室内房间，房间／可选楼层列表承担定位与隔离查看；全场共享工程坐标。中央视口保留“查看全场”，空间切换与隐藏屋顶不改变输出；房间归属不替代灯组、时间编排或输出分配。详见 [ADR-010](../development/decisions/PRODUCT-ADR-010-composable-spaces.md)，当前单空间交互稿不代表此能力已实现。

## 核心操作：共同指向并拖动跟随

用户的完整要求是：一组摇头灯共同照向一个空间点，拖动这个点时，整组光束持续跟随。不能只在松手后更新，也不能只让模型中的光锥转动。

1. 在舞台或资源区选中灯组，属性区显示参与数量与支持情况。
2. 进入“共同指向”，点击舞台地面／明确表面，或选择已有目标点。点击空白天空不能猜测一个深度。
3. 显示带名称的目标点和水平拖动把手；沿目标当前高度的水平面拖动。单独垂直把手／“高度”字段改变高度，横向／纵深字段允许精确输入米数。后续贴合模型表面为显式模式，普通拖动不跳到遮挡物上。
4. 拖动期间所有参与灯具持续更新各自的水平／俯仰角；属性区显示当前目标坐标。选中灯组的绑定在该手势中固定，不因指针穿过其他灯具改变。
5. 松手提交一次编辑，撤销一次回到拖动前；Esc、指针取消或视图断连取消临时手势。拖动不自动改亮度、不自动执行现场输出。
6. 编辑既有片段时，修改属于该片段；无片段时先形成编程器草稿，再明确“记录场景”或“加入时间线”。“保存工程”仅负责文件持久化。

每台灯安装位置不同，因此同一目标对应不同的水平／俯仰角。界面表达空间目标，核心处理每台灯的运动学与取值；不能给整组复制一个相同角度。亮度为零时，可用辅助指向线展示方向，不为了看清方向而改亮度。

默认使用当前片段独立的目标；用户显式保存为命名目标点／位置预设时才形成共享引用。编辑共享目标必须看见引用范围，已有设备运行版本不会因一次界面拖动被暗中改写。具体引用、覆盖、删除和版本规则须在正式契约工单中定案。

## 手动跟随与轨迹编排

“拖动时跟随”是上述工具的基本反馈，不代表自动录制运动。

- 普通拖动：修改当前空间目标，不创建动画。
- 关键帧编排：在明确的时间点记录目标位置，再在两个点之间定义路径及缓入缓出。
- 手势录制：未来显式开启“录制路径”后，才把拖动轨迹及时间写入当前片段；需要单独定义采样、平滑与撤销，不在首个指向闭环里顺带实现。
- 人员追踪：外部追踪源驱动同类空间目标，是后续适配能力；不是当前手动拖动的前提。

路径应先在空间中求目标位置，再分别求每台灯的角度。只插值两端的灯具角度，并不保证光束始终汇聚，也不保证走直线。目标运动过快、转轴限位、水平角跨周或翻转时，必须有连续性和可达性处理；真实灯具不能被假定能够瞬时跟随任意路径。

## 三维与核心的边界

以下为职责说明，不是已实现的新 API：

| 边界 | 负责 | 不承担 |
| --- | --- | --- |
| 界面／舞台交互 | 选择、拾取目标平面、拖动意图、临时把手、编辑范围和错误提示 | 不独立生成权威灯具角度或 DMX |
| 应用层 | 编辑上下文、事务、撤销、版本校验、预览与现场控制权 | 不把每次指针事件变成一次磁盘保存 |
| Rust 核心 | 坐标变换、灯具安装与校准、空间路径、角度求解、连续性／可达性及最终参数 | 不依赖 React、UE 对象或某块控制板 |
| 轻量／专业三维后端 | 以核心结果显示灯头姿态、光束和场地，返回稳定对象身份及拾取结果 | 不形成第二套节目时钟、角度解算或工程保存体系 |
| 播放包／硬件适配 | 接收编译后适合设备能力的角度／通道程序，稳定执行 | ESP32 不携带整个三维舞台或 UE，不以渲染刷新率作为输出时序 |

需要提前保留：目标与灯具稳定身份、明确坐标系和米制单位、安装姿态／校准版本、目标引用、临时拖动与已提交工程的区别。现有 `StageNode` 仅描述变换，不能据此声称目标关系、运动学或编译已支持；本轮不添加 JSON 字段或公共接口。

若某灯不支持指向、校准缺失或目标不可达，按灯具标记并在属性区给出数量／原因；不能把所有光锥强行画向目标并显示“成功”。预览必须区分理想指向辅助线与设备可达姿态。求解滞后时采用最新输入、丢弃过时响应，松手后不得继续消化拖动积压。预览后端丢失不改变现场输出控制权。

## 交互设计稿与验证范围

同目录 [workspace-target-follow.html](workspace-target-follow.html) 是对话内设计稿，沿用已选的舞台与时间线结构；八个灯具点位仅用于验证共同指向的空间关系。可拖目标、更改坐标／高度、切换俯视、取消和撤销；不是产品入口、真实工程、灯库运动学、UE 预演或硬件测试。光束是理想指向关系，未计算光学能量、遮挡或轴限位。

首轮产品实施按依赖拆开：先做主工作区与已有真实数据联动，再验证空间观察／摆位，随后为目标点、校准和指向求解单独建契约与实施工单；共同指向是三维设计的首要验收任务，不能后期临时拼接。先固定目标和持续拖动，再扩展路径、关键帧和外部追踪。UE 接入不阻塞共享指向语义的建立。

验收必须观察拖动中的结果：多台不同位置灯具跟随同一点、安装位置不变；俯视／透视切换目标不漂移；一次撤销、取消和精确数值一致；校准错误与不可达目标不伪装成功。后续真实测试还须测核心求解延迟、负载、路径连续性及灯具实际追随误差，不能用本设计稿的流畅度替代。
