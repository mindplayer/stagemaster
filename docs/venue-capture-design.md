# 真实场地采集与混合预演场景

日期：2026-09-11。状态：用户提出用照片／扫描快速重建现场并接入 UE5 专业预演；本文为产品与模块设计建议，没有采集、重建或渲染实现。与 [UE5 预演方向](ue5-professional-previsualization.md)配套，不预先选定扫描软件、插件或云厂商。

## 1. 产品流程与价值

目标是让灯光师采集一次真实场馆，建立可重复使用的场地版本，再在其中放置灯具、屏幕和舞台设施、编排节目、切换视点与分享方案。价值以准备场景所需时间、空间匹配程度和排练可用性验证。

建议流程：多角度拍摄或扫描 → 导入素材与采集信息 → 后台重建 → 质量检查与尺寸／坐标校准 → 建立关键几何／设备 → 创建场地版本 → UE 预演。再次扫描先生成新修订，经对齐与检查后更新，不无提示移动已有灯位。

3D Gaussian Splatting（3D 高斯泼溅，3DGS）以高斯基元表达采集场景的外观，可从多视角图像重建并渲染新视点。它与传统三角网格的表示不同；可观看的重建结果不代表已有可编辑 CAD、材质或灯具业务对象。[原始研究](https://repo-sam.inria.fr/fungraph/3d-gaussian-splatting/)

现成工具可作为入口：Scaniverse 支持移动采集、Gaussian Splats 和网格输出；摄影测量／激光扫描生成网格也是候选。素材覆盖和质量影响结果，具体工具的格式、平台、可集成接口仍须核查。[Niantic 官方采集说明](https://www.nianticspatial.com/products/capture)、[RealityScan](https://www.realityscan.com/)

## 2. 场景分成三层

| 层 | 保存什么 | 预演作用 |
| --- | --- | --- |
| 真实外观 | 高斯场景、采集光照、来源、覆盖与质量说明 | 表现场馆背景、座椅、装饰及远处环境 |
| 几何与材质 | 校准后的地板、墙面、舞台、桁架、遮挡体；代理网格及独立受光材质 | 空间定位、选择、遮挡和可验证的受光／阴影表现 |
| 舞台业务对象 | 灯具与子灯、灯位、屏幕、安装点、视点、配适引用 | 由 StageMaster 编辑、编排和驱动，保有稳定 ID |

三层共享坐标基准，但分别有版本、来源和质量。关键受光区域可用摄影测量／深度扫描辅助几何，再配置适当材质；不能假定扫描贴图已去掉原始阴影。代理网格仅提供几何时，也不能认定高斯外观已被正确重新照亮。

采集中的原有灯具、屏幕内容、人和临时设施可能与虚拟对象重复，需要遮罩、裁剪、补拍或局部重建。自动识别只提供候选；FixtureId、型号、模式和 DMX 配适仍经明确的编辑／导入流程确定。

## 3. 重新布光与可信度

普通高斯场景保留拍摄光照。白天拍下的亮墙、阴影和反射，不会仅因关闭 UE 虚拟灯而自动还原为正确暗场。重新布光需要额外的光照／材质分解或近似处理；已有专门研究，不能据此推断通用插件已实现。[可重光照高斯研究](https://arxiv.org/abs/2311.16043)

Volinga 文档给出 UE 灯光叠加和代理网格法线方案，并明确保留原采集光照。这是可调查路线；影子、体积光、混合透明和黑场效果需要按版本实测。[插件设置](https://docs.volinga.ai/en/home/volinga-plugin/settings)

首期分别标识三种用途：真实场地观看／方案展示；使用关键受光模型的编排排练；另需标定的测光／准确重光照。前两者不作为真实照度、材质反射或声学预测。背景外观与可重新布光区域应可辨认，不能用“专业模式”名称掩盖近似。

## 4. 采集与空间校准

采集需有足够视角重叠和覆盖；未拍到的背面、顶棚或遮挡区不能当作已准确重建。稳定拍摄光照、清晰图像和较静态场景作为基准条件；闪烁屏幕、人员、镜面及暗部列为检查区域。不承诺随手几张照片完整恢复场馆。[采集实践](https://web.volinga.ai/capturing-gaussian-splats-blog/)

现场保留已知尺寸／控制点，校核尺度、地面、原点和方向。照片重建不能默认具有可靠绝对尺度；辅助 LiDAR／定位数据也需验证误差。[尺度校准说明](https://rshelp.capturingreality.com/en-US/tutorials/scaling.htm)

每份场地修订记录采集日期／区域、输入与重建器版本、坐标变换、量测依据、检查点残差、未覆盖区域及几何／光照质量。未知质量明确记为“未验证”，不伪造统一精度百分比。

## 5. 模块与伪调用职责

| 模块／方法草案 | 输入 → 输出 | 边界 |
| --- | --- | --- |
| CaptureImport.import | 素材访问授权、照片／视频／传感器信息 → 不可变 CaptureAsset | 实际传输并校验资源；不假定手机 App 提供 SDK |
| ReconstructionService.submit | CaptureAsset、重建器版本、输出类型、预算 → JobRef | 后台任务；可先手工导入第三方结果，再按已有 CLI／SDK 自动化 |
| ReconstructionService.inspect | JobRef → 进度、失败、产物与覆盖报告 | 保留源素材，产物可追溯；不占用演出线程 |
| VenueScene.prepareRevision | 重建产物、控制点、几何／对象映射 → 候选修订及影响报告 | 不移动正在使用的灯位；检查坐标、来源和缺失项 |
| VenueScene.commitRevision | 基准修订、已检查候选 → 新场地修订 | 权限与乐观并发校验；工程显式更新场地引用 |
| PreviewRenderer.prepare | 场地与节目快照、资源授权 → 已准备渲染场景 | 沿用 UE 预演边界，不获得物理输出权限 |

方法仅为职责示意，未加入 `contracts.ts`，还需定义具体类型。后台任务的幂等、超时、取消确认、资源持有与回收沿用[公共调用规则](module-api/README.md)。不把外部重建算法重写进 Rust 核心，也不强制所有客户端携带训练工具、Python／CUDA 或 UE。

场地为独立实体与不可变修订。工程固定引用一个修订，不自动跟随最新；更新前校验灯位、屏幕、坐标和删除对象。高斯／网格文件经有版本的导入适配，不能只看 `.ply` 扩展名就假定字段、坐标、颜色和压缩布局相同。

## 6. 多端与云端

采集端、重建节点、编辑端和预演主机可分别部署，通过资源与任务协议协作。Mac 可先承担工程与场地管理；具体本地重建和 UE splat 渲染能力逐工具验证。当前调查的 Volinga 插件要求 Windows＋NVIDIA，UE 支持 macOS 不代表该插件也支持。[Volinga 系统要求](https://docs.volinga.ai/en/home/volinga-plugin/product-overview)

对象存储按内容哈希保存原始采集、重建外观、网格与代理；PostgreSQL 保存场地修订、权限、依赖和任务状态。GPU 工作节点独立于 Fastify 请求处理，可替换为本机节点或其他重建器。是否上传原始素材由具体工作流选择，打开场地不隐含上传或公开分享。

专业端按需下载高质量资源，轻量端使用简化网格／压缩代理或远端串流。产物记录来源、版本、目标能力和质量；仅有缩略图不能报告可离线专业预演。各变体复用坐标和业务对象身份，重新裁剪／压缩不改变 FixtureId 或灯位坐标。

## 7. 首个验证

选择静态、可量测的小场地，先导入现成工具结果，不先开发手机扫描 App。目标是完成“实际场地 → 有校准依据的混合场景 → 两台虚拟灯具与一块屏幕 → 一个可回放节目”。

记录采集／处理／人工修整时间、安装与素材体积、量测误差、关键遮挡、暗场与新增灯光表现、镜头移动伪影、帧时间和恢复行为。对原始高斯场景与混合场景采用相同视点和输入，判断补几何／材质的价值。

依次验证场地外观复现、关键区域编排排练、实物对照校准。在手机、Mac 或指定预演主机分别实测后，才确定端侧支持、质量档和容量。当前没有模型、测量或性能结果。
