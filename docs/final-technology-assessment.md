## 为什么收敛到这条路线

| 路线 | 本项目中的价值 | 最终取舍 |

Tauri 提供桌面与移动宿主，采用原生 Rust 程序和系统 WebView。React＋Vite 是本次为前端收敛的默认选择，便于共享组件与独立 Web 构建；不意味着 React 已被证明比其他前端框架更快。Vite 等属于构建工具，桌面／移动安装包不需要捆绑 Node.js 服务；后续 Fastify 云端 API 在服务器使用 Node.js。[Tauri 平台与架构](https://tauri.app/)、[Tauri 进程模型](https://v2.tauri.app/concept/process-model/)、[React 构建指南](https://react.dev/learn/build-a-react-app-from-scratch)、[Tauri 的 Vite 集成](https://v2.tauri.app/start/frontend/vite/)。

## 语言与模块分工

| 模块 | 主要实现 | 共享范围与边界 |
| --- | --- | --- |
| 工程领域与编辑规则 | Rust | 配适、属性、预设、Cue／序列、编辑命令、校验及版本迁移有一个权威实现；不依赖 Tauri、数据库或设备驱动 |
| 发布转换 | Rust | 将可编辑工程转换为目标可执行节目；与实时执行分开，可在桌面或后续云端使用 |
| 播放与效果核心 | Rust | 时钟、调度、效果计算与输出合成；桌面和符合能力要求的 ARM Linux 盒子共享 |
| 音频与设备适配 | Rust 接口，按需接入原生库 | 隔离系统音频、网络协议、USB／RS485 驱动；具体 SDK 必须使用其他语言时才增加局部绑定 |
| 界面与交互 | TypeScript＋React，HTML／CSS | 共享组件、交互流程、状态展示和客户端接口；不同屏幕与输入方式适配布局 |
| 应用宿主与连接入口 | Rust＋薄 TypeScript 适配 | Tauri 本机接口和 Web 网络接口调用相同的应用命令；组件不直接依赖宿主 API |
| 云端业务服务 | TypeScript＋Fastify | 账号、权限、工程版本记录、素材引用、发布流程与设备分发；需要工程语义校验或转换时调用共享 Rust 模块 |
| 存储与同步适配 | 客户端 Rust；服务端 TypeScript | 本地存储独立于云端 PostgreSQL 与对象存储；共享同步契约，数据库驱动与云 SDK 不进入播放核心 |

“两种主要语言”不表示第三方库只能用两种语言，也不表示移动端永远不需要平台代码。Tauri 的移动插件可以涉及 Swift／Kotlin；只在具体系统能力要求时引入，并限制在适配层。[Tauri 移动插件](https://v2.tauri.app/develop/plugins/develop-mobile/)。

模块通过显式接口协作，依赖指向核心规则；避免循环依赖和共享全局状态。同一种语言也不直接读写其他模块内部数据。每类接口有一份权威契约：Rust 工程／引擎接口生成对应 TypeScript 类型；云端 API 的 schema 与客户端类型共享。配合运行时校验、协议版本和兼容性检查，减少手工维护两套类型造成的偏差。客户端共享包只包含可公开的契约与纯函数，不导入服务端权限实现、数据库代码或密钥。

同仓库共享源码，但各端只构建所需模块：云服务不包含桌面 UI 和 USB 驱动；普通客户端不包含云服务端 SDK；盒子不携带编排界面。减少体积应控制依赖树、平台功能和素材打包，不能只数语言。

## 各端如何复用

| 产品形态 | 复用内容 | 必须适配的部分 |
| --- | --- | --- |
| macOS／Windows／Linux 桌面 | React 界面、Rust 编辑服务和执行核心、工程格式 | 系统 WebView、多窗口、快捷键、音频及设备驱动，分别构建测试 |
| 手机／平板 App | React 组件与简单编排流程、Rust 工程和编辑模块 | 触摸布局、文件权限、系统生命周期及具体插件；不默认承担长期后台现场输出 |
| Web 页面 | 共享前端组件、客户端契约与交互逻辑 | 使用网络接口连接现场 Rust 服务或云端 Fastify API；浏览器中没有 Tauri 原生后端 |
| ARM Linux 盒子 | Rust 执行、目标校验、下载与存储模块 | 资源预算、外部控制／可选监看及输出接口；无界面盒子不装桌面壳 |
| ESP32 等受限目标 | 共同语义、支持的执行子集、可提取的 Rust 算法及契约样例 | 按[独立 Cue 播放盒评估](standalone-cue-player.md)优先验证 Rust 受限播放器；不承诺完整桌面核心或任意原始工程直接运行 |

目标是共享同一来源的代码并分别适配，不能承诺所有平台零修改或固定复用百分比。移动端简化的是可编辑功能与布局：它不支持编辑的高级内容需要保留；无法保证无损保存时，应阻止覆盖并明确说明。Web 若将来需要完全离线编辑，再评估把纯 Rust 模块编译为 WebAssembly；这不是当前远程控制的前置条件。[Tauri 前端边界](https://v2.tauri.app/start/frontend/)。

## 稳定输出与解耦边界

编排命令进入应用层，经过校验与准备后交给现场执行器。执行器拥有播放状态和主时钟，负责持续计算与输出；UI 接收必要的状态更新。文件解析、素材下载、数据库写入、云同步与日志 I/O 不进入关键播放循环。引擎内部高频数据不经由界面往返。

桌面建议将现场引擎部署为可独立启动的本机进程，界面通过本机接口连接；同一台电脑仍可完成全部操作。这样可以独立测试、重启界面和接入后续 Web 客户端，但必须设计引擎退出、单实例、控制权与异常恢复。Tauri 自身的多进程模型并不会自动保证“关闭界面仍持续播放”。移动端可以直接集成共享库，不强行套用桌面进程部署方式。[Tauri 进程模型](https://v2.tauri.app/concept/process-model/)。

Rust 的无 GC 和所有权检查有利于控制内存与并发错误，但不能保证截止时间。普通 macOS／Windows／Linux、USB 和驱动仍可能带来抖动；需要结合带缓冲和独立时序的输出设备验证 DMX 链路。音频回调和输出关键路径避免阻塞操作、无界分配及不可控锁等待。模拟输出不能代替真实设备测试。[Rust](https://rust-lang.org/)、[实时音频回调约束](https://portaudio.com/docs/v19-doxydocs/writing_a_callback.html)、[ENTTEC DMX USB Pro 缓冲机制](https://support.enttec.com/dmx/usbdmx-dmx-usb-pro-70304/dmx-usb-pro-api)。

Web 控制可先走局域网。互联网控制后续增加身份、设备授权与控制权管理，命令应处理重复、过期和断连。网页、网络或云端不可用时，现场执行按已配置的节目和设备策略处理；不能把所有设备统一置零或统一保持最后值。精确同步由现场时钟与相应同步机制负责，不承诺互联网即时操作零延迟。

## 云端存储与分发

**已确认服务器端：TypeScript＋Fastify＋PostgreSQL，配合对象存储。** 补充评估将此前“云端业务优先 Rust”的建议调整为 Fastify：账号、权限、版本目录、上传授权和分发状态主要是业务 API 与存储交互，使用现有 TypeScript 技术栈、共享 API 契约更符合当前需求。整套云服务用 Rust 仍可行，它能减少 Node.js 运行时及跨进程边界；但不应仅为统一核心语言而要求所有云端业务用 Rust。这里没有项目实测数据证明哪种后端性能更高。

Fastify 提供 TypeScript 支持、基于 schema 的请求校验与响应序列化，以及可限定插件和钩子作用范围的封装机制。这些能力适合按账号、工程、素材、发布和设备划分模块；初期作为一个模块化服务部署，业务规则与数据访问通过明确接口组织，不将全部逻辑放进路由或预拆成多个微服务。[TypeScript 支持](https://fastify.dev/docs/latest/Reference/TypeScript/)、[校验与序列化](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/)、[插件封装](https://fastify.dev/docs/latest/Reference/Encapsulation/)。

服务器增加 Node.js 运行环境，查询和数据库迁移还需要 SQL，但主要业务语言仍为 Rust 与 TypeScript。Node.js、PostgreSQL、Fastify 插件和云 SDK 只在服务器部署，不进入桌面／移动安装包，也不成为单机离线运行的依赖。具体 Node.js／Fastify／PostgreSQL 版本在实施时选择相互兼容且受支持的版本，云厂商、区域和 CDN 后续再定。

### Fastify、PostgreSQL 与 Rust 的职责

| 部分 | 拥有的职责 | 复用方式 |
| --- | --- | --- |
| Fastify 业务 API | 身份与资源授权、工程版本记录、素材上传授权、发布流程、设备分发与状态查询 | 与前端共享 API schema、类型、客户端 SDK 和适合公开的纯工具函数；权限由服务器执行 |
| PostgreSQL | 用户与工程关系、修订历史、素材索引、发布记录、设备与分发任务等结构化数据 | 关系字段、约束与事务管理一致性；扩展配置按需使用 JSONB |
| 对象存储 | 音频、工程原始快照、灯具档案文件、不可变节目包 | 数据库保存对象标识、校验值、大小与引用关系；内容通过授权上传／下载 |
| Rust 工程模块 | Cue／效果语义、工程迁移、目标能力校验、节目转换 | 桌面与设备直接复用；云端需要同类处理时，通过有版本的任务接口调用 Rust 执行程序 |
| Rust 现场引擎 | 主时钟、播放调度、效果计算和连续输出 | 独立于 Fastify、数据库和云端可用性；接收有权限且有效的控制命令 |

PostgreSQL 的事务适合把相关数据库修改一并提交或回滚；修订提交仍需配合基于版本的并发检查，发布／分发操作需设计幂等键，不能认为“用了事务就自动解决同步冲突”。JSONB 可查询并建立索引，适合扩展配置或清单摘要；工程的可验证原始字节保留在对象存储，不依赖 JSONB 重建后计算原文件校验值。[PostgreSQL 事务](https://www.postgresql.org/docs/current/tutorial-transactions.html)、[JSONB 行为与索引](https://www.postgresql.org/docs/current/datatype-json.html)。

数据访问可从 `pg`＋`@fastify/postgres` 的连接池与显式参数化查询起步，加上版本化迁移；先不叠加多个 ORM。Fastify 官方组织维护的 PostgreSQL 插件提供连接池和事务接口，但模块的表所有权、事务边界和连接上限仍由应用设计。[PostgreSQL 插件](https://github.com/fastify/fastify-postgres)。

初期云端可以接收桌面生成的工程和发布包，执行授权、协议结构、文件完整性检查及存储分发；目标执行器加载前使用 Rust 模块做实际能力与语义校验。上传成功不等于节目已验证可执行。未来若需要云端编辑、完整语义校验或生成节目包，再增加复用 Rust 核心的后台任务入口，不在 TypeScript 中重写 Cue 和效果规则。

Rust 后台任务可先是同机受控的独立执行程序，由任务接口调度，不必另做一套常驻 HTTP 业务服务或立刻引入原生 Node.js 绑定。长时间工程计算与转换采用有并发上限、超时和状态记录的后台执行，避免占用 Fastify 请求线程的事件循环；这也是 Node.js 官方针对耗时计算的基本约束。[Node.js 事件循环说明](https://nodejs.org/learn/asynchronous-work/dont-block-the-event-loop)。

### 云端数据与版本流程

现在就保留三个不同对象：

- **可编辑工程版本**：灯具、配适、编组、预设、Cue、效果和音频引用；具有稳定工程 ID、格式版本与修订 ID。
- **不可变的发布包**：由某次工程修订生成，包含目标能力要求、兼容引擎版本、素材清单和内容校验值；发布后通过新版本修改，不覆盖原包。
- **设备执行状态**：分别记录期望下发、已经下载和正在运行的版本。下载完成不等于已生效，云端也不能把过期回报当作当前在线状态。

建议用对象存储保存工程快照、灯具档案、音频和发布包；PostgreSQL 记录用户、权限、版本关系、素材引用及设备状态。通过存储适配器隔离厂商接口，采用兼容协议也仍需验证实际支持的功能。数据库事务不能覆盖对象存储操作：先上传和校验，再通过数据库事务提交可见的版本与任务；用准备／就绪状态、幂等重试和孤立文件清理处理失败。

同步与分发应按以下流程设计：

1. **先本地保存，再后台同步。** 编辑和已准备好的现场播放不依赖云端可用性；本地任务队列记录待同步内容。首次使用某份云端素材仍需先下载齐全。
2. **版本冲突保留双方。** 上传携带所基于的修订 ID；多人或多设备离线修改发生冲突时，保留分支／副本并明确处理，不按最后上传者静默覆盖。首期不引入实时协同编辑系统。
3. **素材独立上传、可复用。** 用稳定引用和内容校验值避免每次小改动都重传全部音频；大文件按需分块上传、失败重试。只有完整上传并验证后，才提交可见的工程修订或发布记录。
4. **下载权限与存储密钥分开。** 服务端授权后提供限时上传／下载地址，客户端不持有云存储管理密钥；不同工程和设备有各自访问范围。采用唯一版本对象名，避免重试覆盖已发布内容。
5. **先准备，再切换。** 设备下载到暂存区，验证内容、发布来源、目标能力和资源，再将版本标记为可激活；由明确的操作者动作或预设调度在允许时机切换。保留上一可用版本用于恢复，更新失败不覆盖当前节目。

限时访问、上传授权和校验能力可参照[对象存储预签名 URL](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)；分块上传可参照[官方 multipart 文档](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html)。上述业务版本、冲突处理和激活流程需要由本产品实现，对象存储不会自动提供它们。

节目／素材分发与软件／固件更新使用不同清单、版本和生效流程。桌面软件可评估 Tauri 的签名更新机制；手机应用和盒子固件按各自发布路径设计，不能把一个更新插件当作所有终端的统一升级器。[Tauri Updater](https://v2.tauri.app/plugin/updater/)。

## 落地顺序与必须取得的证据

1. **专业单机闭环。** 在 macOS 验证代表性配适、选灯编组、属性／预设、Cue／效果、播放合成、音频波形和本地保存；使用独立 Rust 核心与薄 Tauri 宿主。具体首版功能顺序围绕灯光师工作流程细化。
2. **尽早验证复用边界。** 用同一组件和命令在第二个桌面平台、一个移动目标和普通浏览器完成一小段编排／控制流程；检查工程往返不丢高级内容，避免等完整桌面做完才发现边界错误。
3. **扩展云端与盒子。** 使用既有工程、素材和发布契约，实现离线同步、版本管理、目标下载与激活；之后再考虑互联网控制与更多设备形态。

在正式承诺可靠性与体积前，需要取得以下证据：

- 代表性工程下，中文输入、多窗口、密集灯具表格、波形缩放和触摸操作可用；界面忙碌时持续记录引擎计算耗时、漏期、控制延迟和内存变化。
- 对每个目标平台记录 Release 包下载量、安装占用、系统运行组件和运行内存；单架构与通用架构包分开比较，不采用框架空壳宣传数字。
- 验证保存／迁移／撤销恢复、移动往返、界面重启、睡眠恢复和设备重连；现场输出另做获授权的真实硬件测试。
- 云端阶段验证离线双端冲突、上传中断、素材缺失、损坏包、版本不兼容、越权访问、重复提交、数据库事务失败、切换失败和恢复；检查数据库与对象存储的备份恢复一致性，已经下载且可用的节目不因云服务故障失效。
