# UE5 专业舞台预演方向

日期：2026-09-10。状态：根据用户对 UE5 专业预演价值的判断，列为优先原型候选；没有安装 UE、实现接入或完成性能／灯具实测。主技术框架仍为 Rust＋TypeScript。本文补充[声光视频设计](audiovisual-stage-design.md)和[模块伪 API](module-api/README.md)，不表示专业预演已经可用。

2026-09-11 补充：[真实场地采集与混合预演](venue-capture-design.md)将高斯外观、可受光几何和舞台业务对象分层，定义重建任务、尺度校准、场地修订与云端资源边界；工具尚未选定或接入。

同日补充：[Depence R4 对照](depence-r4-assessment.md)将已求值状态到画面之间的设备响应明确为仿真职责；复杂设备由独立模型处理历史、依赖与回放，UE 可承载具体后端实现，但不接管节目语义。

同日边界修订：按用户最新要求，音视频正式播放、处理、映射与输出由外部系统承担。UE 消费监听／监看返回或明确标记的离线参考；预演画面与方案录像属于设计交付，不作为现场媒体服务器输出。

2026-09-23：用户在重新定义效果编辑界面时再次提出 UE 灯光预演及空间建模。已将其接入位置补入 [UX-006 界面设计](ui-design/effect-editor-design.md)：UE 可作为可交互的舞台空间后端，承担搭建、拾取、变换、视点和渲染；工程数据、撤销、效果求值和现场输出仍有独立权威模块。舞台搭建与通用网格建模分开，前者优先。独立进程先验证，嵌入 Tauri 和运行时编辑工具需另行实现；不将 UE 编辑器原样交给用户，也不认为 React 可直接嵌入原生 UE 视口。未安装或运行引擎。

本轮重新核对 Epic 的 [DMX 概览](https://dev.epicgames.com/documentation/en-us/unreal-engine/dmx-overview)和 [MVR 导入／导出](https://dev.epicgames.com/documentation/en-us/unreal-engine/dmx-mvr-import-and-export-in-unreal-engine)：UE 已提供 Art-Net／sACN 与专业预演相关能力；普通 MVR 导入只包含 DMX 灯具／配适，场景几何另需 Datasmith 路径。插件可用不代表本产品已完成灯具覆盖、模型编辑、协议桥接或渲染精度验证。后续按目标版本实测，不从网页标题推定本机已具备某版本能力。

## 1. 产品价值

专业预演应帮助灯光师在进场前判断节目，并向客户、导演和其他工种表达设计。UE5 值得验证的价值集中在以下场景：

| 工作场景 | 拟提供的能力 | 判断依据 |
| --- | --- | --- |
| 编排灯光 | 在舞台空间里观察光束、图案、遮挡、运动与灯组关系 | Cue／效果仍由 StageMaster 求值，比较同一节目在不同灯位和视点下的表现 |
| 声光视频排练 | 虚拟屏幕显示外部返回或参考画面，本地监听，灯光跟随节目位置 | 检查构图、卡点与内容配合，同时显示来源、预览时间和延迟 |
| 沟通方案 | 保存观众席、导演、摄影机等视点，录制方案视频 | 镜头位置与预演配置可保存、可复现；不把录像当作现场性能证明 |
| 现场调整前检查 | 在独立预演上下文试改 Cue、灯位和效果，再走正常编辑／激活流程 | 预演修改不直接改变正在播放的节目 |

UE 的 DMX 插件支持 Art-Net／sACN、预演与像素映射；MVR／GDTF 相关流程可作为导入入口。普通 MVR 导入与包含场景几何的 Datasmith 流程有区别，具体档案和几何覆盖必须逐项验证。[DMX 官方概览](https://dev.epicgames.com/documentation/unreal-engine/dmx-overview)、[MVR 官方说明](https://dev.epicgames.com/documentation/unreal-engine/dmx-mvr-import-and-export-in-unreal-engine)

定位为“优先验证专业预演”。现场 LED／投影的节目画面交由外部媒体服务器输出；UE 的 nDisplay 多屏渲染能力不改变本系统边界，也不证明整个声光视频系统已经同步。[nDisplay 官方说明](https://dev.epicgames.com/documentation/en-us/unreal-engine/rendering-to-multiple-displays-with-ndisplay-in-unreal-engine)

## 2. 模块边界

| 模块 | 拥有的职责 | 交接数据 |
| --- | --- | --- |
| 工程／场景服务 | 版本化灯具、灯位、几何、屏幕、视点和校准引用 | 不依赖 UE 的场景快照、资源清单和修订 |
| Rust 预演运行上下文 | 跟踪、效果、合成、节目位置与虚拟时钟 | 已求值的灯具属性及来源、同步组状态 |
| PreviewService／渲染桥接 | 后端能力、场景准备、会话、订阅与恢复 | 只读状态流、资源访问授权、时钟映射 |
| UE 预演后端 | 场景资源、虚拟灯具、材质、光束、镜头和渲染 | 就绪、缺失能力、已渲染来源、延迟及诊断 |
| 监听／监看服务 | 外部返回接收、编辑参考、本地呈现与耳机监听 | 带来源、取点、时间戳及新鲜度的媒体通路 |

首个原型采用独立 UE 应用／进程，先验证窗口间协作；嵌入 Tauri 窗口留到必要时评估。UE 适配所需的 C++／蓝图限定在这个可选模块，核心不依赖 UE SDK。普通控制端和无界面执行设备不携带 UE 运行时。UE 的主要编程方式是 C++ 与蓝图。[官方编程说明](https://dev.epicgames.com/documentation/en-us/unreal-engine/coding-in-unreal-engine-blueprint-vs-cplusplus)

StageMaster 工程是语义来源；UE 工程和 cooked 资源属于后端资源或派生产物。核心格式不保存 UObject 指针、Actor 类名或仅 UE 能理解的场景结构。UE 特有视觉扩展使用带 schema／版本的命名空间保存；其他端原样保留，并明确显示无法预览的部分。

同机进程隔离只隔离部分故障，仍存在 CPU／GPU／磁盘／驱动争用。预演不得反向阻塞灯光求值和输出；原型必须验证预演卡顿、退出与资源压力的影响，必要时支持独立预演主机。

## 3. 先固定的交接契约

| 契约 | 必需信息与约束 |
| --- | --- |
| SceneSnapshot | 工程与场景修订、稳定对象 ID、父子结构、变换、灯具档案／校准版本、屏幕绑定及资源哈希；在解码后采用受校验的中立类型 |
| 坐标和灯具轴 | 明确长度／角度单位、坐标轴／手性、矩阵约定及 pan／tilt 零位与正方向；到 UE 的转换只在适配器，不能散布在业务代码 |
| ResolvedFixtureState | FixtureId＋ElementId＋属性语义、物理单位／功能范围和最终值；来源包含执行上下文、计划与场景修订、帧序号、时间和同步组代次 |
| MediaPreviewBinding | VideoSurfaceId、MonitorSourceRef 或编辑参考身份、内容版本、取点及节目时间映射；音频仅绑定本客户端 MonitorOutput，大帧与 PCM 不经普通 JSON RPC |
| RendererCapabilities | 支持的灯具功能、预览格式、资源限制、质量档与未验证项；必须返回不支持或降级的具体原因 |
| RenderObservation | 收到／应用／渲染分别报告，关联源帧及时间；画面完成不代表真实灯具动作完成，更不代表远端屏幕已显示 |

以上渲染契约族尚未加入 `contracts.ts`；通用监看身份与会话已有 [external-contracts.ts](module-api/external-contracts.ts) 草案，UE 绑定仍待细化。既有 `PreviewApi.open/seek/close` 管理预演执行上下文；不能把它误当成已经包含 UE 的创建、资源准备或渲染流接口。

内部 `PreviewRenderer` 类／接口拟提供以下生命周期，具体 DTO 在原型前细化：

1. `describe()`：读取后端版本、渲染能力与限制。
2. `prepare(sceneSnapshot, resourceAccess)`：异步加载并校验场景，返回有期限的已准备场景和功能覆盖报告；不接入现场输出。
3. `attach(preparedScene, readOnlySource)`：绑定已授权的独立预演或现场只读源，取得渲染会话；两种源用区分类型表示。
4. `observe(session)`：查询就绪、源帧、延迟与异常；状态帧由桥接器通过有界数据通路送入，不逐属性调用 RPC。
5. `detach(session)`／`release(preparedScene)`：取消订阅并释放持有资源；不会关闭现场运行上下文。重复关闭应幂等，超时结果通过操作 ID 查询，失败后由租约／宿主回收兜底。

`prepare/attach` 按公共操作协议处理后台任务、幂等、版本和超时；调用者无权伪造资源 token 或只读源授权。跨设备先传输并校验资源，再在目标端准备，不能直接传本机路径作为可访问资源。会话权限由服务端校验，渲染模块不获得 OutputLease 或物理输出端口。

## 4. 状态、时间与交互

优先接入 Rust 已求值状态，保留属性语义和来源。Art-Net／sACN 接入可用于外部控台互操作验证；它只带协议层信息，不能直接替代完整场景、修订与来源契约。两种输入模式必须显式选择，同一虚拟灯具不得被两条来源同时更新。

状态订阅采用“快照＋有序增量＋缺口重同步”。桥接器可丢弃过时的完整连续状态帧；若增量依赖缺失基准，必须重取快照，不能直接丢掉中间增量继续套用。离散模拟事件有独立序号与重放政策，不能被当作连续属性合并掉。

现场观察不推进现场时钟；独立预演的暂停／Seek 只影响对应预演同步组。UE 按输入时间渲染，帧率降低时允许显示质量下降或跳帧，并标记状态过期；不在 UE 里重新实现 Cue 跟踪与效果计算。显示插值限于已声明的连续属性，离散功能与事件不能任意插值。

场景修订、运行计划、播放位置和时钟 epoch 分别校验。场景热更新先准备再切换；加载失败保留旧场景并显示修订不匹配，不暗中把新灯光状态套在错误灯位上。

在 UE 画面中点选灯具只产生带稳定 ID 的选择请求；改变灯位／属性仍经应用编辑接口检查修订和权限。3D 交互与移动端编辑共享同一权威命令，不直接改 Rust 内部对象。

音频仅启用明确选定的本地监听来源，默认静音。离线排练可使用明确标记的编辑参考，不为试听而启动、定位或改变外部现场节目。虚拟屏幕使用外部节目返回、采集画面或参考代理，标明取点、来源及延迟；只有对应证据才能声称看到现场实物。离线方案视频导出使用独立虚拟时钟逐帧推进，实时返回不能冒充可任意 Seek 的离线素材，也不能为了导出拉慢现场播放。

## 5. 预演可信度

给灯具功能标记“已校准／近似模拟／未支持”，并记录档案与校准来源。支持导入、能发光或画面逼真，均不足以证明真实灯具匹配。首批比对至少覆盖调光曲线、pan／tilt 方向与范围、光束／变焦、Gobo 方向、色彩混合和动作延迟。

固定曝光、色调映射、屏幕颜色配置与雾参数，保存为预演配置；检查调光或 Cue 间亮度差时，自动曝光会影响可比性。效果表现、测光预测和声学预测分别声明精度。没有标定与测量时，不提供“真实照度／色彩／声场已准确”的结论。

## 6. 多端与云端

桌面专业端可按需运行 UE；轻量端继续评估 Three.js 并共享中立场景与属性契约。共用对象和节目语义不要求共用渲染实现，也不保证两个后端的图像一致。

手机／平板可选观看 Pixel Streaming，以查看远端 UE 画面；这需要渲染主机和连接，不能取代本地编排与离线保存。记录渲染端与客户端显示延迟，不把串流画面用于判断现场精确同步。[Pixel Streaming 官方说明](https://dev.epicgames.com/documentation/unreal-engine/overview-of-pixel-streaming-in-unreal-engine)

云端保存中立工程、原始／获准分发的场景资源和内容哈希，按目标按需分发。UE 派生产物另记引擎／插件版本、平台、质量配置及构建来源，不能把某平台 cooked 产物当作全端通用源。普通设备发布包不因项目有专业预演资源就自动下载整套 UE 内容。

## 7. 首个原型与验收

建议以一段约一分钟的节目和受控场景验证：4 台摇头灯、4 台染色灯、1 块虚拟屏幕、1 段音乐，以及灯位遮挡和多个视点。这是测试工作负载，不是产品数量上限或已承诺性能。

| 验证项 | 要取得的证据 |
| --- | --- |
| 同一节目 | 固定输入与时刻，比较核心最终值与 UE 接收／应用记录；改变渲染帧率不改变核心求值 |
| 场景和灯具 | 单位、方向、子灯、配适与屏幕引用正确；不支持功能明确列出 |
| 排练 | 连续播放、暂停、循环、Seek、慢速排练；跨代次旧状态不回灌，音频不重复 |
| 故障恢复 | 断开后重连、增量缺口、场景加载失败、UE 退出；输出侧不等待渲染恢复 |
| 性能与体积 | 指定 Mac 型号／系统／UE 版本，记录冷启动、加载、帧时间、内存／GPU 开销、预览延迟与安装体积 |
| 真实输出隔离 | 后续在获准设备测试中，增加渲染压力，测量灯光输出间隔与截止时间超限；没有设备测量时只报告模拟结果 |
| 实物匹配 | 使用对应真实灯具比对关键功能和动态响应，保存误差与校准记录 |

macOS 支持及渲染特性限制应按选择的 UE 版本和机器核查；不以其他平台的视频演示推断当前 Mac 的效果或容量。[官方 macOS 要求](https://dev.epicgames.com/documentation/unreal-engine/macos-development-requirements-for-unreal-engine)

采用和分发前按实际产品形态核查 UE 与素材许可；源码可访问不等于可任意授权或分发。[Epic 官方许可说明](https://www.unrealengine.com/license)

下一步的决策依据是：是否显著改善灯光师排练与表达、关键灯具功能是否可信、是否满足选定机器预算，以及适配维护成本。通过后再固定后端版本与交付方案。
