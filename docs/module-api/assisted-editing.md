# AI 辅助编辑与自动化调用

状态：`assisted-editing-draft-1`，2026-09-24。依据 [ADR-011](../development/decisions/PRODUCT-ADR-011-assisted-editing.md)；这是独立的可类型检查扩展，没有可调用服务或模型接入，不把主接口 draft-0.3 宣称为已经升级。

用户可以逐步获得这样的操作：“把选中的灯调暗一点，只改这个场景”“沿灯组顺序生成亮度变化”“把这一段改成暖色”。AI 先看实际对象与支持能力，再调用与手工编辑相同的命令。编完的节目仍是普通工程内容，播放盒不运行语言模型。

## 接口组成

| 入口 | 调用者／用途 |
| --- | --- |
| [AutomationToolsApi](automation-contracts.ts) | 模型工具适配器：发现能力、搜索、读取局部上下文、生成提案、查询状态；已有连续授权时应用提案 |
| [AutomationHostApi](automation-contracts.ts) | 可信界面／宿主：建立或关闭授权会话、人工应用、撤销、打开隔离候选预演；不注册为模型工具 |
| [调用例子](automation-examples.ts) | 修改选中场景中指定灯具的亮度，区分提案、人工应用、授权内自动应用、撤销 |
| [编译期反例](automation-checks.ts) | 拒绝模型自行授权、原始控制、任意补丁、缺修订和上下文／提案混用 |

TS 定义的是调用契约，不是第二套引擎。实现时 Rust 提供权威命令、范围／依赖校验、差异和事务；TS 宿主组织对话、注册工具与模型调用。模型既可以通过内置适配，也可以通过后续 MCP 适配使用此窄入口；无需因此增加主业务语言或安装所有模型 SDK。

状态归属：模型适配只拥有对话任务；编辑自动化应用层拥有授权会话、上下文与候选提案；ProjectService 仍是唯一工程写入者，提交时在同一事务内验证自动化授权并关联回执。适配器不能拿宿主的宽权限替模型盲提交。候选预演交给不含输出适配器的 PreviewService；宿主持有人工操作入口，模型代理只拿受限工具。以上职责可在同一进程内组合，不要求新增微服务。

MCP 工具发现和输入／输出 Schema 可直接借鉴[官方工具规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)。注册的工具只映射上述方法；Schema 必须来自与 `schemaHash` 一致的受信注册表，由宿主解析完整定义后提供给工具调用端。不能让模型自行下载任意 schema URL、猜灯具能力或用文字注解代替授权。此次只预留适配位置，没有对外开放端口。

## 一次编辑如何完成

1. 用户在当前工程中选择灯具／场景和任务。可信宿主根据用户已经授予的权限调用 `openSession`，限定可读对象、可编辑对象、目标灯具、属性、操作、可创建类型、批次数量与有效期。默认“先看方案”；用户可一次选择“在此范围内连续编辑”，之后范围内无需每步确认。
2. 模型通过 `capabilities` 获取实际能力，再 `search`／`readContext`。上下文固定工程修订、档案修订、Schema 和授权代次；查询只返回获准数据，分页不能越权。名称和备注是数据，不是系统指令。
3. 模型调用 `propose`。服务对完整批次做同一套 Rust 校验，合法则保存不可变提案和服务生成的前后差异，返回 `ready`；非法则返回问题列表。此步不修改当前工程，也不激活计划。修订、上下文与授权失效属于调用错误，不能仅当作可忽略提示。
4. 界面展示提案改变了什么、影响哪些对象；有能力时宿主通过 `openCandidatePreview` 在候选只读快照上调用 PreviewService。此候选不成为工程当前修订，不能冒充正常编辑基准或可部署产物；预演无输出端口。当前仅定义入口，视觉预演尚未实现。
5. 用户应用时调用宿主 `applyReviewed`；已有连续授权时模型工具可调用 `applyScoped`。两者提交**同一份已校验提案**，提交时再次检查修订、有效权限、能力和依赖；成功复用 `EditReceipt`，一次事务、一次撤销。连续授权不是每次请求里的布尔开关。
6. 界面沿用正常编辑历史与保存流程。`undoApplied` 只接受与该提案回执匹配的撤销记录，并校验当前修订／历史位置；不能越过其他编辑静默回退。编辑回执不表示工程文件已经保存，按 `durability` 和正常保存回执显示状态。

例子中的 `proposeSelectedIntensity` 接收服务解析出来的灯具 ID、场景 ID 与亮度属性键，提交现有 `update-cue`／`cue-only` 操作。它不会把“选中”理解成此刻可能已经改变的 UI 全局选择；多单元亮度目标不明确时中止并要求明确单元。数值与通道映射仍由领域服务核验。

## 范围检查与生命周期

- `editableObjectIds` 限定实际数据写入；`targetFixtureIds` 与 `attributes` 进一步限定参数目标。新增对象须满足类型、数量与引用约束，成功创建的对象只在服务检查后纳入本会话后续范围；模型不能通过 upsert 把已有对象当新对象绕过限制。
- 用户选择灯组时，授权记录解析出的灯具 ID 集合；后续灯组成员变化不能自动扩大授权，须按当前修订重新核验。
- `cue-only` 可能产生后续补偿写入，预设／配方可能影响引用链。服务必须计算隐式修改及间接影响，不能只看请求里显式的场景 ID。越过允许写入／灯具范围或缺少必要可读依赖时拒绝，并向宿主给出可解释的扩围理由，不泄漏未授权对象内容。
- 提案摘要由服务对基准、操作、解析依赖和语义版本计算；校验值不相信模型声称的结果。对象视图只作受限显示投影，不作为完整工程序列化；差异与摘要以权威完整语义为依据。
- 上下文、提案、候选预演有大小／数量／有效期限制；推理取消或关闭会话释放未提交资源，已应用的工程修改和审计回执继续保留。过期／关闭会话不能继续写入；操作者仍可通过普通编辑历史撤销自己的修改。
- `commandId` 在同一身份／会话作用域内幂等；重试不得修改原负载。应用记录与编辑事务须有一致的恢复日志；工程文件的保存仍单独进行。提案的已应用标记至少保留到任何旧授权都不可重放，不能先清回执再让旧提案二次应用。
- 应用超时先查 `applicationOutcome`／`inspect`，成功则使用既有回执；处理中继续对账；保留期外不得换一个 ID 盲目重放。已关闭会话的回执由有权宿主读取，不因此恢复模型的写权限。提案提交超时也用同一命令重试，不能反复生成重复候选。
- `discard` 与应用按服务提交顺序竞争；已应用提案不能丢弃，须显式撤销。撤销后该提案仍是已应用的历史记录，再次做相同内容必须针对新修订生成新提案。关闭窗口或停止生成不等于撤销。

原子提交涉及的校验、授权、修订与回执必须在同一可信边界完成。TS 的窄接口仅帮助避免误用，运行时仍需独立鉴权与 Schema／大小校验；品牌 ID 不是安全措施。

## 错误与调用边界

| 情况 | 返回／处理 |
| --- | --- |
| 没有权限、试图自动应用待审核提案 | `UNAUTHORIZED`；模型无扩大授权方法 |
| 当前工程已被人工或其他编辑修改 | `REVISION_CONFLICT`；重新读取，生成新提案 |
| 上下文、授权代次或提案失效 | `STALE_CONTEXT`；刷新上下文，不静默改基线 |
| 不支持的属性／效果／候选预演 | `UNSUPPORTED_CAPABILITY`；显示实际限制 |
| 数值、操作数量、字节预算或类型不合法 | `INVALID_INPUT`；整体不应用 |
| 隐式写入冲突、提案已应用而要求丢弃、撤销历史不匹配 | `DEPENDENCY_CONFLICT`；定位实际冲突 |
| 超时／结果不明 | 沿用 `OUTCOME_UNKNOWN` 和对账策略；已提交结果不能当失败重做 |
| 回执超过保留期 | `not-retained`；由宿主核查工程／历史，不能宣称未执行 |

模型工具没有文件系统路径、任意脚本、完整 StageClient、外部设备控制、原始帧发送、包激活或现场开始命令。授权编辑不赋予现场控制权。未来现场助手另行设计，不能用修改工程的接口暗中实现。

## 从预留到实际接入

首批类型子集是创建灯组／预设、修改已有场景、分步效果与配方；服务只有在对应真实能力完成后才对模型声明可用。现有草案不包含完整颜色空间、指向求解、任意曲线、可播放片段插入或 AI 新建场景的全套输入，不能据此声称“输入一句话已能生成整场节目”。

先实现上述亮度任务，验证实际事务／撤销和范围控制；再接一种可替换模型适配，比较人工和 AI 生成同一命令的结果；随后依核心能力扩展场景生成、时间线、音乐分析与空间效果。音乐可优先提供波形、节拍、段落等派生信息；发送原媒体需服从用户对该模型的已授权数据范围。

必须通过的运行验收：目标缺属性／重名、多单元选择、越界／隐式越权、批次部分非法、并发修订冲突、同命令重试、同提案不同命令、应用超时、应用与取消竞争、候选预演零输出、撤销历史冲突、会话撤销／服务重启和文本诱导扩权。这些现在均未实现，类型检查只证明调用形状和列出的隔离反例。
