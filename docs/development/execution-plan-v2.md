# 执行计划 v2：Sol 直接开发，Astra 高级调度

2026-09-11。当前有效；依据 [DEV-ADR-001](decisions/DEV-ADR-001-sol-astra.md)替代 v1 的开发工具路线。

## 当前范围

G0 按调整后的范围结项：Git 基础、交付方法和两项已验收核心修复保留；Qwen／工作器退出，DEV-004 剩余补修取消，未解决问题保留为历史记录。
下一步是 Astra 整理 G1 依赖与固定第一批产品契约。当前没有已发布的 G1 实施工单，Sol 不把旧工作器任务作为默认下一项。

## 工作方式

1. Astra 给出阶段目标、模块边界、依赖顺序与小批工单。每张工单至少包含行为、修改范围、接口／错误、验收和完成条件。
2. Sol 从就绪工单开始，核对基线与现有改动，在项目内 `.worktrees/<task-id>/` 中直接实现；先确定契约验收，缺陷修复先复现再修复。
3. Sol 执行格式化、编译、测试与适用检查，审查完整 diff，集成后验证准确版本。常规任务自主完成，不逐步索要确认。
4. 公共契约、数据所有权、持久格式、时钟／控制权等重大变化交 Astra；其他独立且已授权的工作可以继续。
5. Sol 汇总一页以内的交付；Astra 在关键边界与阶段出口审查，并发布下一批。阶段审查不替代日常测试，也不要求每次小修都回到 Astra。

没有 Qwen 中间执行层，不建设本地编码代理，不再统计模型委派成功率或要求补足样本。
旧 4096 token、三次请求和 360／900 秒限制是已停用工具的参数，不是 Sol 的开发预算。

## 产品主线与进入条件

| 阶段 | Astra 固定什么 | Sol 交付什么 | 出口证据 |
| --- | --- | --- | --- |
| G1：核心领域边界 | R03–R09 的依赖、稳定身份、属性能力／类型值、逻辑灯具与 DMX 配适分离、来源／版本语义 | 依照分批工单逐步实现与迁移 | 领域契约及失败场景测试，依赖方向清楚；不提前冻结持久格式 |
| G2：可编辑、可恢复、可播放 | 编辑事务、撤销、编译／激活、虚拟时钟、Cue 状态机与恢复策略 | 无 UI／无真实设备的节目重放与恢复闭环 | 代表性节目、错误引用、版本切换、恢复及时间推进行为可复现 |
| G3：专业单机工作流 | 应用边界与操作流程 | Tauri／React 下配适、选灯、编程器、Preset、Cue／Sequence、基础效果及参考时间线 | 灯光师能完成代表性编排与播放操作 |
| G4：真实输出与控台硬件 | 输出时序、资源与故障语义、推子旋钮接口 | 协议／设备适配与负载验证 | 指定硬件的实际输出、时序、故障与恢复证据 |
| 后续 | 目标能力与分发契约 | ARM／ESP32、移动／Web、云端、预演及 AV 监听分别接入 | 各端能力单独验证，核心不绑定具体硬件或界面 |

上表是路线，不是整批实现授权。G3／G4 可在接口稳定后交错验证；具体实施以已发布工单为准。
产品继续使用 Rust 核心、TypeScript 界面与云端业务；既有 Fastify／PostgreSQL 等选型不因开发模型变化而重选。

## 交付要求

- 记录基线、结果及集成提交，实际测试、关键取舍和剩余问题。
- 测试由工具运行，验收按行为定义，不为通过测试而改变契约。
- 用量和耗时有真实数据才记录；不要求为采集指标额外搭平台。
- 独立 worktree 保持单一写入负责人；Sol 负责主线集成与 STATE.md，Astra 以独立文档交付决策。
- 本机软件通过、真实设备通过与完整产品能力分别记录。
- 工程及开发产物按[项目文件规则](project-files.md)保存到本项目内，不使用共享 AI 目录保存项目试验、日志或配置。
