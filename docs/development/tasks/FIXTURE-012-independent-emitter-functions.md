## 全量回归暴露的只读等待缺陷

`logs/fixture-012-workspace-final.log` 原命令退出 101：桌面 125 通过／1 失败，`background_audio_tests.rs:72` 在播放之后 `Client::refresh` 得到 503。`server.rs::observation` 将有界非阻塞 observer.read 的繁忙映射为 503，既有 execution-host 的 `support/client_audio.rs` 已明确只读查询可在原期限内等待；该桌面循环却直接 unwrap。此证据说明查询等待前提缺失，不证明音频播放失败或历史锁根因。

本单仅补测试等待 helper：只对准确 503 的只读 refresh 响应在原 5 秒截止内等待，其他错误立即失败；所有现有最终断言、截止和控制命令保持。不增加生产重试／不重发写操作，也不串行全量或跳过原测试；增加 helper 错误分类的确定性验证后恢复原全量出口。原失败保留，独立诊断通过不能冒充修复完成。

首次恢复全量中，上述测试通过，但另一旧音乐所有权测试在 `media_tests.rs:59` 的 apply_media 返回 503（`workspace-corrected.log`）。Client::send 在 POST 接纳后还有最终 refresh，因此单一返回错误不能推出未执行。仅修正该测试 helper：准确 503 时继续原回执查询，绝不重发控制；仍须得到同一提交的有效 accepted 回执，以及相同 request 的 Applied，原所有权断言／6 秒截止保持。若 POST 未接纳，原回执查询不能成立，仍必须失败；不把未知结果忽略为成功。生产宿主／客户端行为未改，其他音频历史问题未宣称修复。
