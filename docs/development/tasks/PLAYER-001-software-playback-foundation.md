## 目标与边界

当前 A0 能做一次静态求值与 DMX 编码，界面另有模拟播放状态；两者尚未组成持续播放器。本任务先在电脑上贯通“最小工程输入 → 校验／编译 → 受限执行计划 → 虚拟时间运行 → 512 通道输出记录”，让软件语义和硬件接口有可检查的依据。

首批覆盖一条物理输出的逻辑数据、一个活动节目、多个场景，以及选择／执行、渐变、延时、中断／跳转、列表循环与释放。选择范围须闭合依赖，明确片段进入与结束状态。先验证 RGB／调光等声明支持的档案。复杂效果、多播放合成、完整专业编排、音视频、云端和所有 R03–R09 问题不在本任务一次解决。

本任务不实现 USB／无线协议、持久播放包、固件刷写、实际 DMX 时序或新界面。内存中的计划不能直接被宣布为长期兼容的文件格式。

## 分步实施

1. **精确契约与最小参考执行。** 先记录架构变更说明，确定时间单位、命令生效顺序、选择／执行区分、渐变中断和释放、入口状态、输出所有权及错误语义；用手写最小计划建立虚拟时钟下可核对的参考结果。
2. **受限主机编译。** 接入 PROJECT-001 的已校验工程快照，固定输入工程修订、灯具档案／配适及目标能力；将声明支持的内容编译成自包含计划。未知属性、缺失依赖、不可确定的片段入口和不支持行为都应有明确诊断，不能默默略过。核对保存重开前后编译播放结果一致。
3. **有界执行与模拟承接。** 用相同测试向量验证拟供设备复用的执行路径；明确内存与每次推进的工作上限。模拟适配器记录输出、命令回执及故障，形成 PLAYER-002／003 的对照基准。

每一步保留可运行结果，不为所有未来设备预建空壳模块。优先共享受限执行算法；参考求值及手工期望值用于独立验收，不能只让同一实现与自己比较。是否提取新 crate、现有模块如何依赖，在第一步明确后实施。

## 必须明确的接口与不变量

- 编译输入只读，编译结果与来源修订、配适和能力版本关联；UI 编辑不会直接改动当前计划。编译失败不替换可用结果。
- 执行器接收明确的单调时间，不读取墙上时间、不自行休眠；回退时间、相同时间、多命令顺序、长时间跳进和循环边界均有定义。不得在一次推进中无界补跑所有错过的帧。
- 静态选择不产生执行；重复控制命令在声明的身份／去重范围内不能多执行一次。重连、计划更换及重启后的边界由后续安装／控制契约继续落实，不能宣称本任务已覆盖持久去重。
- 灯具默认状态、场景释放与停用输出分别定义；不能统一把全零视为所有设备的安全状态。
- 播放关键路径与文件、网络、日志及板卡驱动分离。所需缓存与运行状态有明确上限；报告区分已确定的计划／缓冲占用、估计的运行预算和待板卡测量项。
- 逻辑帧必须完整交接，模拟记录可区分交给适配器与适配器报告完成；模拟完成不能证明物理总线发送完成。存储、时钟、通信和输出适配分别承接，不设计一个包办全部职责的硬件接口。

## 出口验收

- 小型代表性节目可在没有界面和硬件的环境中编译并持续模拟播放；同一输入、时间和命令得到一致结果。
- 用独立预期检查渐变起点／中点／终点、延时、同刻命令、渐变中断、直接跳转、循环边界与释放；对连续推进和跨时间推进的等价点做比较。
- 缺失预设、未知属性、不支持的操作、越界配适、超限计划明确拒绝；导出局部范围能得到规定的独立入口状态，不能依赖未安装的前序场景。
- 检查陈旧计划命令、重复命令以及模拟输出故障；记录哪些安装／重启与故障情形留给后续任务。
- 资源报告可解释其计算依据；不能将桌面运行成功等同可在 ESP32 运行。工具链与物理输出探针按 PLAYER-002 尽早交错验证。
- Rust 实施验证使用项目规定的 `cargo fmt --all -- --check`、`cargo test --workspace --locked --offline` 和严格 Clippy；测试方案在实现前具体化。
