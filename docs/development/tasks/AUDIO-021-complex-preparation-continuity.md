# AUDIO-021：复杂音乐准备与消费连续性

状态：限定软件消费／零位恢复增量完成、自审通过（2026-10-05）；普通复杂工程软件出口恢复，完整 H1／听音仍未关闭。实际基线 main `36149b571e04eeb8cb43099b2b977bdd564d2642`（EXEC-016），计划在该版本先发布，基线记录 `c270d64`、ADR `587d655`／恢复决定 `0e07d61` 先提交；结果为本次 `fix(audio): keep software callbacks alive during preparation` 提交。主工作区单写者，用户未跟踪 output/ 保持。

## 问题与实际证据

EXEC-016 正式 `.app` 在隔离静音预演输出中载入字节相同的 AUDIO-020 工程（80 灯／20 场景／4 循环／30 秒真实 MP3）。停止状态明确定位 10 秒一次，网络接纳后媒体 request 1 Failed，音频“软件音频消费超过 500 毫秒未运行”；一次明确重新准备 request 2 TimedOut，音频“音乐操作准备超时”。无文件故障注入，无 UE／设备，原文件哈希保持。见 `data/EXEC-016/native-seek-failed.state.json`／`native-recovery-final.state.json` 和对应 AX／PNG；EXEC-016 分类矩阵／全 Rust 通过不覆盖这个真实失败。

尚未测定根因。同步灯光编译、媒体准备、消费驱动和期限竞争都是待排除假设，不将这一失败当成 FIXTURE-012 旧循环 rejected 的已证明原因。

后继实测：同工程灯光编译 2787 ms、定位音源准备 633 ms、PCM 首次准备 897 ms；旧单线程消费在所有者 650 ms 工作期间确定性触发 500 ms 保护，红灯 0 通过／1 失败。依 [ADR-163](../decisions/PRODUCT-ADR-163-software-audio-consumer.md)先独立原软件 Mixer 的消费职责，保留保护与期限。恢复超时是否由同一机制导致仍待正式复核。

第一轮独立消费的正式定位／循环／暂停通过，但受控私有损坏媒体后的 request 5 恢复仍 TimedOut。后继测量载入新缓存及零位音源 1545 ms、重复零位 seek 639 ms、编译 2807 ms，合计 4991 ms 未含确认开销。依 ADR-163 后继顺序决定，仅明确零位恢复复用刚载入的新暂停音源，非零与普通定位保持原 seek，所有 guard／callback／激活及 5 秒期限仍保持；不把第一轮超时擦成通过。

## 最小范围与失败行为

1. 读现有媒体任务、准备器和软件消费实现；记录执行位置、耗时、请求／消费代次与实际帧，先真实复现与确定性保护测试。不重写播放器／计时器，不改动 UI 完成定义。
2. 复用 MediaPreparer／PerformanceAudio／LoopSchedule／权威音频观察／单在途回执。若耗时准备阻塞同一消费路径，在已存在职责内隔离慢工作或调整合理准备顺序；公共时间／控制权／依赖边界变化先记录 ADR。
3. 不取消或延长 500 毫秒保护来迁就实现，不把读取当新消费、不伪造帧／Applied、不自动重发控制／重启后台，不用无限等待／反复重试掩盖失败。错误、取消、过期／陈旧代次和准备失败保持明确，旧运行不能被迟到结果覆盖。
4. 原项目／资源／默认最近目录只读，验收使用项目 data/ 独立副本与 tmp/ 隔离实例；软件输出，不调用真实声卡／听音、UE、灯具、刷机或部署。仅普通必要源码与保护测试，非整个平台重构。

## 实际实施与验证

- 原软件消费者提取为独立所属线程，只消费原 Mixer；Transport、工程、准备器和媒体端口仍归媒体所有者。创建失败／消费停顿／线程停止明确失败，原 OutputBinding 同步失效；Drop 取消并 join，恢复先回收旧输出。删除操作级墙钟重置，48 kHz／双声道及 500 ms 保护保留，无第二节目时钟、播放器或 DMX 权威。
- 提取私有 `activate_prepared`，仅零位 Recover 复用刚载入的新健康暂停音源；普通定位与非零恢复仍 seek。原摘要校验、递增提供方代次、真实暂停 callback、灯光编译／staging、guard、5 秒期限和同一 request 完成不省略。
- 5 项消费保护（慢所有者期间暂停健康／实际播放／暂停保持、500 ms 拒绝不补拉、所属 Drop、同绑定失败）和 1 项真实宿主零位恢复新增。红灯先 0 通过／1 失败；原非零恢复、重复／陈旧代次、循环、接纳／失败、管理锁／声音占用保护仍实际通过。新并行测试超过原解码预算及只读快照 Busy 失败保留，测试改为共享真实预算并只在 1 秒内重读明确更新状态，不重发或放宽产品限制；严格时间减法警告修正。
- 最终原工作区全量 **1275 Rust＋2 文档**、严格 Clippy／fmt、引用／严格 JSON／差异检查和正式 `.app` 构建通过。3 个 ignored 仍为父测试实际调用的子进程入口；没有 UI／UE 源码变化，不冒记重复 UI／听音／GPU 检查。手写文件按职责组织，最大相关文件低于 300 行。
- 原复杂工程字节相同副本在第一轮独立消费后：10 秒定位 request 1 Applied，实例 2 正式循环至第 9 遍，暂停 request 3 Applied，后续位置／消费帧保持。私有损坏媒体的 request 4 Failed，恢复 request 5 TimedOut **仍保留为失败**，不写成第一轮通过。
- 最终包同一副本最近重开，新后台普通 10 秒定位 request 1 Applied；仅所属私有媒体故障注入后 request 2 Failed，恢复原字节后单次 request 3 **Applied／零位 Paused／frames 0／新实例 4／组代次 3**，UI 仅此时清除旧 25 秒草稿。明确播放 request 4、暂停 request 5、停止 request 6 均 Applied；同实例实际重复 PCM，暂停位置 6752 ms／frames 826998 后续保持，最后停止归零。不是声卡发声验收，没有 UE／设备输出。
- 两轮后台均通过界面明确关闭、所属窗口退出；无 current／发现文件／拥有进程，私有媒体均已恢复摘要。工程及副本／源 MP3／默认最近目录／FIXTURE-012 哈希保持，用户 output/ 未触碰。原生和测量证据 `data/AUDIO-021/`，日志 `logs/audio-021-*`；诊断脚本参数及备份重名错误如实记录，不冒充产品故障。
