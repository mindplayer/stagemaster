# AUDIO-021：复杂音乐准备与消费连续性

状态：实施中（2026-10-05）；优先于接续 H3。实际基线 main `36149b571e04eeb8cb43099b2b977bdd564d2642`（EXEC-016），主工作区单写者，仅用户未跟踪 output/ 保持。本计划随 EXEC-016 交付先纳入版本，再实施；先测量既有同线程软件消费／准备顺序，不能仅凭代码路径认定根因。

## 问题与实际证据

EXEC-016 正式 `.app` 在隔离静音预演输出中载入字节相同的 AUDIO-020 工程（80 灯／20 场景／4 循环／30 秒真实 MP3）。停止状态明确定位 10 秒一次，网络接纳后媒体 request 1 Failed，音频“软件音频消费超过 500 毫秒未运行”；一次明确重新准备 request 2 TimedOut，音频“音乐操作准备超时”。无文件故障注入，无 UE／设备，原文件哈希保持。见 `data/EXEC-016/native-seek-failed.state.json`／`native-recovery-final.state.json` 和对应 AX／PNG；EXEC-016 分类矩阵／全 Rust 通过不覆盖这个真实失败。

尚未测定根因。同步灯光编译、媒体准备、消费驱动和期限竞争都是待排除假设，不将这一失败当成 FIXTURE-012 旧循环 rejected 的已证明原因。

后继实测：同工程灯光编译 2787 ms、定位音源准备 633 ms、PCM 首次准备 897 ms；旧单线程消费在所有者 650 ms 工作期间确定性触发 500 ms 保护，红灯 0 通过／1 失败。依 [ADR-163](../decisions/PRODUCT-ADR-163-software-audio-consumer.md)先独立原软件 Mixer 的消费职责，保留保护与期限。恢复超时是否由同一机制导致仍待正式复核。

## 最小范围与失败行为

1. 读现有媒体任务、准备器和软件消费实现；记录执行位置、耗时、请求／消费代次与实际帧，先真实复现与确定性保护测试。不重写播放器／计时器，不改动 UI 完成定义。
2. 复用 MediaPreparer／PerformanceAudio／LoopSchedule／权威音频观察／单在途回执。若耗时准备阻塞同一消费路径，在已存在职责内隔离慢工作或调整合理准备顺序；公共时间／控制权／依赖边界变化先记录 ADR。
3. 不取消或延长 500 毫秒保护来迁就实现，不把读取当新消费、不伪造帧／Applied、不自动重发控制／重启后台，不用无限等待／反复重试掩盖失败。错误、取消、过期／陈旧代次和准备失败保持明确，旧运行不能被迟到结果覆盖。
4. 原项目／资源／默认最近目录只读，验收使用项目 data/ 独立副本与 tmp/ 隔离实例；软件输出，不调用真实声卡／听音、UE、灯具、刷机或部署。仅普通必要源码与保护测试，非整个平台重构。
