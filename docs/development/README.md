## 分工

| 角色 | 负责 | 交付 |
| --- | --- | --- |
| Astra 高级调度 | 产品与架构方向、模块契约、优先级、依赖拆分、关键疑难和阶段审查 | 可执行工单、决策、阶段结论 |
| Sol 日常开发 | 直接实现、测试、排错、局部重构、自审、集成与状态维护 | 可验证代码、精确提交和简短交付记录 |
| 确定性工具 | 格式化、编译、测试、差异及版本检查 | 实际结果与可追溯证据 |

Sol 在工单范围内持续完成工作，不把普通编译错误和实现细节交回 Astra。Astra 的投入集中在模块边界、长期取舍和关键审查。

## 日常循环

1. Astra 发布小批就绪工单，明确行为、修改范围、依赖、接口与错误、验收和完成条件。
2. Sol 核对代码基线及用户改动，在任务 worktree 中直接实现。缺陷先复现；契约验收应能独立于具体实现判断行为。
3. 自动格式化，运行适用测试与静态检查，审查完整 diff，再集成并验证合并后的版本。
4. 常规任务由 Sol 自行验收并更新状态；关键接口变化、跨模块风险及阶段出口交 Astra 审查。
5. Astra 根据交付决定后续顺序；不要求每个小改动都经过新一轮确认。

任务状态：`planned → ready → running → verifying → review（需要时）→ done`。
`needs-decision`、`failed`、`cancelled` 单独标记；因路线取消不能写成实现通过。只有集成并满足本任务验收才标 done。

## 升级给 Astra 的条件

公共 API 或模块依赖方向变化；工程／发布包格式；数据和线程间所有权；时钟、时间、控制权、跨设备一致性及输出故障语义；契约冲突或无法收敛的跨模块问题。
提交简短的[架构变更说明](templates/architecture-change.md)，说明复现、影响、可选方案与建议。只暂停依赖该决定的部分，其他已授权且独立的工作继续。

## 交接与成本

- `STATE.md` 由 Sol 维护，记录当前任务、准确版本、下一步和待决项。Astra 用独立决策文档交接。
- 工单采用[任务模板](templates/task.md)，结果采用[交付模板](templates/delivery.md)。跨 worktree 交接必须带分支、基线与结果／集成提交。
- 同一模块保持一个写入负责人；已验证的实现和历史记录不因换模型而重做。
- 默认只传当前工单和相关契约。Astra 先看一页交付、接口差异和关键证据，按风险决定是否深入实现。
- 用量、耗时可取得才记录；不设想当然的节省比例，不要求构建新的统计或路由平台。
- 不自动创建会话、切换用户模型或启动额外云端子代理；跨会话派发依照用户授权执行。
