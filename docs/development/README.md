## 决定

采用“云端负责判断，本地完成有边界的实现，工具执行验证，文件保存交接”的方式。
Codex 保持现有云端模型和登录方式，本地 Qwen 通过一个可替换的工作器接入。
初期沿用已验证的本地 API；先把候选改动工作器的命令行入口做可靠，再视需要加一个薄的 MCP 接口。
不同时引入多个代理框架、模型路由器、向量记忆库或新模型。

## 三个角色

| 角色 | 负责 | 交付物 |
| --- | --- | --- |
| Astra 架构会话 | 总体边界、当前阶段契约、关键取舍、阶段审查 | 可执行工单、架构决定、审查结论 |
| Sol 开发会话 | 领取工单、细化实施、选择执行者、验证和集成、记录进度 | 可审查变更、实际测试记录、简短交接 |
| 本地 Qwen | 在明确文件和接口范围内实现、补测试、修复具体错误 | 候选补丁及未解决问题；不自行合并或宣布验收通过 |

Sol 有能力直接开发和排错，不要求所有代码都经 Qwen。Astra 不逐行监督每项普通实现。
日常问题由 Sol 在契约内解决；会影响系统语义的决定才进入架构会话。

## 一次任务怎样完成

1. **就绪**：工单写明目标、非目标、读取／修改范围、接口、错误条件、验收和基线版本。未决定的接口先解决，不能让执行者猜测。
2. **领取**：Sol 更新状态，建立独立工作区。该模块已有任务写入时先排队。
3. **路由**：工具可以确定性完成的直接运行工具；简单零碎修改由 Sol 做；局部、规模适中的实现交 Qwen。
4. **实施**：只提供所需上下文。输出过长、接口不清或范围扩大时重新拆分，不静默截断文件或放宽写入范围。
5. **验证**：先自动格式化，再编译、独立验收和相关静态检查；把真实失败的有限诊断反馈给执行者。
6. **审查**：Sol 审查完整变更和边界，常规任务可以自行验收。需要架构判断时提交简短审查包，其他无依赖任务可继续。
7. **集成**：验证合并后的确切版本，记录提交与结果，更新状态。生成成功、测试通过、集成完成分别标记。

状态流：`ready → running → verifying → review → done`；另有 `needs-decision`、`failed`、`cancelled`。
只有实际集成并满足验收条件才能标记 done。

## 两个会话如何不失联

长期事实放在仓库内，不靠一条不断增长的聊天记录，也不要求两个模型记住彼此全部对话。

- `STATE.md`：Sol 单一维护当前任务、下一步和待决事项；架构计划通过独立文档交接，由 Sol 同步队列。
- `tasks/`：每项工单及依赖，接口变更要更新版本。
- `deliveries/`：以后按工单保存交付记录，采用[模板](templates/delivery.md)。
- `decisions/`：以后按编号保存重要决定；旧决定被替代时保留原因及替代编号。
- 大段终端日志和模型响应存放本机 AI 输出目录，仓库记录摘要、文件位置和必要哈希，不把它们塞进每次提示词。

不同 worktree 有各自文件副本。交接必须带**分支、基线提交、结果提交／补丁哈希**。
接收方通过指定版本读取和审查，再正常合并；只写“见最新 STATE.md”不足以完成跨 worktree 交接。
初期由 Sol 负责集成分支写入；Astra 形成独立的文档／决策变更，避免双方同时改状态表或实现文件。
DEV-001 已建立本地 Git 基线并验证 worktree，见[交付记录](deliveries/DEV-001-delivery.md)。后续任务从包含当前工单和契约的提交开始。

会话之间不会因这些文件自动互发消息。本轮不创建 Sol 会话、不注册自动轮询；用户创建会话后可从下面的交接提示开始。

## 什么时候回到 Astra

以下变化提交[架构变更说明](templates/architecture-change.md)：模块公共 API、依赖方向、工程／发布包格式、时间和时钟含义、控制权、跨设备一致性、线程间状态所有权、硬件输出故障语义。

在既定接口内部选数据结构、增加局部测试、修复实现错误、常规重构由 Sol 判断。
Qwen 失败先由 Sol 诊断；只有暴露契约缺口或 Sol 仍无法解决的关键问题才升级。
已授权实施范围内的流程审查不需要反复向用户请求许可。

## 控制时间和 token

- Astra 看工单、接口差异、关键实现和短交付包；默认不读取全部生成过程或每条测试日志。
- 在 Sol 已经读完整个模块并形成实现后，再转交 Qwen 通常难以减少前面的消耗。应在边界确定、细读实现之前判断是否委派。
- 每次传递相关契约和少量文件；输入初始目标不超过约 8k token、输出约 4k，属于起始预算，不是已验证的长上下文上限。
- 本地 Qwen 初期只处理一个生成任务，其他任务由 Sol 排序，不实现持久队列、不并发加载多份 27B 模型。云端 Sol 可在等待时处理独立的轻量任务。
- 默认最多三次模型请求：首次实现加两次针对性修复。每次超时初值 360 秒、任务总时限 900 秒；达到上限后返回实际状态，由 Sol 决定接管或拆分。
- 模型无输出、截断、格式错误、编译失败和契约歧义分开记录。格式化不消耗模型轮次。
- 不预设节省比例。记录本地和云端用量、耗时、审查返工与最终通过率，按一组真实任务比较。

## 持续几个月的节奏

采用小阶段迭代，不提前把几个月的实现细节全部锁死。

1. **D0 开发基础**：DEV-001 版本控制与验证基线；DEV-002 可取消、可追溯的候选改动工作器。
2. **D1 资格验证**：G0 先记录工作器的新模块试验及 CORE-001／002 两项真实修复；DEV-003 汇总结果。约 10 个样本在后续有价值的任务中累积，逐步覆盖多文件改动，不为凑数延迟产品开发。记录成功率、人工修改和总耗时；样本不足时不宣称稳定收益。
3. **D2 正常开发**：Sol 按当前阶段工单推进；每完成一个可验证能力簇，或出现重大接口变化，向 Astra 提交阶段审查包。
4. **持续维护**：每周收敛状态和待决事项；按需检查工具升级，在隔离环境复跑资格用例后再换版本。长对话需要更换时从仓库状态续接。

版本、模型权重、运行时和验证命令都需要记录。中途切换模型可以继续同一工单，但必须留下执行者和测试结果；不把不同模型的记忆当成统一事实来源。
