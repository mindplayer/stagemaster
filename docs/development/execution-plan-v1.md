# Sol 执行计划 v1：先建立可验收的交付链路

2026-09-11，Astra 制定。用户已授权 Sol 在本计划范围内自主实施。
本计划细化开发方法，第一批执行到 G0 阶段交付；后续阶段为方向和进入条件，不是一次性施工单。

## 1. 最终目标与本批边界

长期目标仍是专业单机灯光编排与控制系统，未来接入硬件控台、ARM／ESP32 播放端、移动／Web、云端与专业预演。
产品核心 Rust、界面与云端业务 TypeScript 的方向不变。开发工具独立于产品模块。

本批要证明：Sol 可以依照契约，将局部实现交给本地 Qwen，取得候选改动，执行独立验收，审查后集成，准确记录结果。
同时修复现有原型中 R01、R02 两个已确认的问题，让试验产生真实项目收益。

本批不实现 UI、持久工程格式、时钟调度、外部音视频接入、云端、物理 DMX、固件或 UE5；不创建远程仓库和云端资源。
不安装新模型，不变更 Astra／Sol 的 provider、订阅、模型设置和现有 MLX 版本。

## 3. 谁做什么

- **Astra**：本计划、架构和接口边界、G0 阶段审查。默认不参加每轮格式修复、测试日志整理和局部编码。
- **Sol**：主执行者。编写独立验收，给 Qwen 裁剪上下文，审查完整候选变更，运行工具，处理普通失败，负责集成和状态。
- **Qwen**：只执行有范围的局部工单。首批 CORE-001／002 优先委派，用于真实代码资格验证；如果工作器或模型未能完成，Sol 可以接管，但必须记录接管，不能计为 Qwen 独立完成。
- **确定性工具**：格式化、编译、测试、差异检查和哈希，避免用模型重新生成正确代码来解决格式问题。

将验收问题交回模型之前，Sol 先区分：实现错误、测试错误、任务歧义、工具故障和格式问题。
独立验收由 Sol 按固定契约编写；发现验收本身错误可修正，但必须保留原因和前后差异，不能迁就错误实现。

## 4. 工具建设的取舍已经确定

第一版采用已有 Python 3.12 的标准库实现薄工作器，源码放 `tools/local-worker/` 并纳入本项目 Git。
这只是开发辅助工具，不加入 Cargo workspace、不打包进 StageMaster，不新增产品业务语言或模型运行时。
任务、日志和中间产物放 `/Users/sunqi/ai/outputs/local-worker/`；本机可变配置按 AI 管理目录规则保存，不写入可分享工程。
Python 路径、AI 根目录可配置；文档中的绝对路径是当前主机配置，不成为协议字段的固定值。

复用临时试验中已经验证的 API 和工具调用方式，但不直接复制其不完整的进程／失败处理。
社区插件仅作参考；首批不安装插件、不改全局 MCP 配置、不引入 Aider／pi／自动路由器。
暂不做后台守护进程、持久队列、Web 管理台、多模型调度或向量记忆库。CLI 可由 Codex 现有 shell 工具调用。

工作器只生成并校验候选文本改动，**不执行模型提供的命令，也不负责运行生成代码**。
Sol 在实际可用的 Codex 执行权限下运行验收；worktree 不宣称是 OS 沙箱。
把“模型建议代码”和“宿主运行代码”分开，避免第一批演变成自研完整代理平台。

## 5. 版本、文件和并发

1. 若目录仍没有 Git，DEV-001 先建立原状基线；已有 Git 就沿用。不要覆盖他人当前改动。
2. 每项候选实现使用独立任务 worktree；先确定 base commit，再由 Sol 准备验收并记录 acceptance commit。
3. 保护验收文件；工作器不获得主 checkout 的写入能力。输出带来源哈希、操作和差异文件，Sol 在指定任务工作区检查并接纳。
4. 每项任务交付一个小而完整的版本；基线、验收、结果、集成提交分别记录，避免“最后一个提交”指向错误代码。
5. 同一时刻只有 Sol 写集成分支／STATE.md。Astra 审查指定提交并形成独立文档决定，不同时修改实现。
6. 集成时若有其他改动，正常解决冲突并验证合并后的版本，不强推、不硬重置、不覆盖用户文件。

角色指定不依赖模型猜测自己的身份。用户给 Sol 的启动提示明确其角色；切换模型后仍以该会话任务和仓库记录为准。

## 6. 防止无效投入

- CORE-001／002 是资格样本，不代表这种很小的修复始终适合委派。正常开发中，Sol 可直接完成零碎改动。
- 工作器先用合成响应验证解析、路径、来源过期、状态和失败行为；真实 Qwen 调用只用于必要的端到端验证。
- 初次实现加最多两次修复。达到上限，Sol 决定接管、拆分或提报契约问题，不让模型互相转交。
- 不在 G0 前补齐长期目标的所有自动化。约 10 个任务的统计样本在后续真实开发中逐步积累，不专门制造无价值的“跑分任务”。
- 不重新下载模型、扩大上下文或升级依赖来掩盖任务拆分问题。先查输入、诊断和预算。
- 云端用量不可获得时标记 unknown；不得用本地 token 数推算节省了多少 Codex 额度。

## 7. 暂停与继续规则

普通代码、格式、构建和工单内实现问题由 Sol 自行处理。
下列情况形成架构问题说明：固定公共契约无法成立、需要引入新业务语义、必须改变持久格式／数据所有权／时间语义、需要扩大执行权限或触及现有全局模型服务。

确需决定时，仅暂停依赖该决定的部分，先给出已完成结果、复现证据和建议。其他独立工作可继续。
不要为了继续运行而删除测试、放宽路径、伪造使用量、清空用户改动或把尚未完成的任务标为完成。

## 8. G0 阶段结束时必须交付

- DEV-001／002／003 与 CORE-001／002 的状态；任何未完成项与原因。
- 工作器实际可运行的命令、源码版本、允许的范围和已验证限制。
- 三类证据：模拟故障验证、真实本地模型任务、产品回归及集成验证。
- 一页以内的阶段报告：结果、基线／结果提交、实际用量、失败与接管、下一步建议；完整日志留盘。
- 更新 STATE.md、交付记录和实现状态。不要改写历史审查以假装问题从未存在，可追加已解决状态及证据。
- 重型模型恢复按需状态，保留当前网关的既有行为。

完成 G0 后结束本批执行并向用户报告，等待本架构会话进行阶段审查。**不要自行扩展到下一阶段的大规模核心重构。**

## 9. 几个月的产品主线

以下按依赖推进，不承诺固定周数；每阶段进入前补齐其工单和契约。

| 阶段 | 重点 | 可验证的出口 |
| --- | --- | --- |
| G0（本批） | 开发交付链路与两项明确缺陷 | 可追溯小任务交付，知道本地模型适用范围 |
| G1 | 领域、能力校验、身份、属性值、来源与运行版本；解决 R03–R09 的结构性问题 | 多单元灯具、类型值、引用、编译接纳通过契约测试；未定永久格式不提前固化 |
| G2 | 编辑事务、撤销、本地恢复、编译／激活、虚拟时钟、Cue 状态机 | 无 UI、无真实设备时能重放并恢复代表性节目，错版与失效引用可解释 |
| G3 | Tauri／React 专业单机工作流 | 配适、选灯、编程器、Preset、Cue／Sequence、基础效果与参考时间线形成可用操作闭环 |
| G4 | 持续输出、真实接口、时序、负载、故障恢复和控制面 | 指定硬件组合的实测记录与支持范围；软件预演与真实发送状态分清 |
| 后续独立演进 | ARM／ESP32 发布包、移动／Web、云端分发、专业预演与 AV 监听 | 通过稳定契约接入，分别验证设备能力，不倒逼主核心绑定某个端 |

G3／G4 在对应接口稳定后可以局部交错验证。每个阶段同时维护“已经实现”“自动化已测”“真实设备已测”三种状态。
