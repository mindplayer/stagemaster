## 软件先行与硬件承接

先建立独立于界面和板卡的软件规则，以可运行结果确定接口。这里的软件核心包括主机编译器和设备将要复用的受限播放内核，不能只完成电脑端，再由固件另写一套场景语义。既有 A0 保持静态混合原型；DESKTOP-003 / PLAYER-001A 新增独立、有界的单列表时间执行与主机编译。现有代码仍不能未经测量即视为适合 MCU。

| 边界 | 软件负责 | 硬件／宿主适配负责 |
| --- | --- | --- |
| 工程与编译 | 解析工程、闭合依赖、生成受限计划；按目标能力拒绝未知功能及超限内容 | 提供版本化的目标能力和可用预算；首轮可用明确标记的模拟能力 |
| 播放内核 | 场景状态、渐变、延时、跳转与循环；接收显式单调时间和命令，生成确定的输出快照 | 提供单调时钟和调度唤醒；满足已声明的刷新与处理预算 |
| 设备应用层 | 校验／安装／激活分开；维护当前节目、命令回执及运行状态；本地面板和远程控制进入同一控制入口 | 持久存储、连接和面板输入；掉电、断线及设备故障上报 |
| 物理输出 | 生成完整逻辑 DMX 帧；规定帧交接、运行状态及故障处理契约 | UART／RS485、电气接口及协议时序；明确报告接收、发送完成和故障 |

第一项可运行结果为“最小工程保存／重开 → 已校验快照 → 编译计划 → 虚拟时间驱动的模拟播放器 → 可核对的 512 通道输出”。编辑操作内存模型，JSON 只在存储／交换边界编解码；先支持明确的小范围灯具与场景行为，再接已有界面。界面原型的模拟状态不作为正式播放规则。

硬件提供能力反馈，软件据此编译和验证；实际容量由固件、存储布局、运行内存及实测共同决定。16 MB 是现有板卡的标称闪存，不能等同可用节目空间。软件通过不代表电气与时序合格，必须尽早让同一组软件用例进入板卡验证。此次只细化开发顺序，精确类型、时间规则、内存布局及持久包格式仍在相应实施任务中审查后确定。

## 实施规则

1. 先明确小批任务的行为、修改范围、接口／错误、依赖和验收，再实现。
2. 核对基线与现有改动，保持同模块单一写入负责人；隔离工作区限定在项目 `.worktrees/`。
3. 工具执行格式化、编译、测试与静态检查，审查差异并验证集成版本。
4. 公共契约、持久格式、所有权、时钟／控制权的变化先记录架构决定；普通实现自主完成。
5. 更新工单、STATE 和交付，区分设计、软件验证和真实设备验证。
6. 重要能力开工前对照[能力总表](../product-capability-plan.md)和对应成熟经验，补齐必要的依赖、失败／恢复及界面落位；不重复全套研究，也不以扩充清单代替本次实现。
