## 首次交付顺序

以下 PLAYER 编号为计划任务，尚未实施或验证。每项开工前形成精确契约、写入范围和独立验收工单；不把接口草案当作已冻结协议。

| 顺序／任务 | 最小结果 | 出口证据 |
| --- | --- | --- |
| PLAYER-001：受限执行计划与参考执行器 | Rust 权威语义；单个活动节目、多 Cue；选择／GO／跳转／Fade／Delay／循环／释放；有界资源和明确拒绝 | 虚拟时间下的 Cue 切换、Fade 中断、重复命令、释放和超限测试；相同输入可重放；无 UI／I/O 依赖 |
| PLAYER-002：板卡固件与单路输出探针 | 锁定 Xtensa 工具链与固件依赖；GPIO17／18／21 板级适配；UART DMX 发送及帧完成状态 | 可重复交叉构建与资源报告；获授权后在受控测试负载上测启动首帧、Break／MAB、512 槽与持续刷新；补齐隔离公共地／接口方案 |
| PLAYER-003：执行包、USB 和设备自主播放 | 主机编译、版本化包、USB 能力查询和控制；盒子持久安装／校验／激活；共享小型执行器 | 主机与设备同语义比较；断开控制连接继续本地运行；坏包、超限和重连不重放 GO；写入掉电仍有完整可用版本 |
| PLAYER-004：软件完整操作链与本地面板 | 工程真实保存／重开；Rust 编译与 UI 接入；显示设备状态；本地选择／GO／状态显示 | 从编辑到导出／安装／播放；预览不控制现场；独立供电、无电脑／网络仍可本地选择并执行 Cue |
| PLAYER-005：整机验收与交付 | 指定灯具／模式、连接器与供电、故障策略、版本与操作说明 | 至少一次 8 小时工程压力运行的时序／内存记录；真实 Fade／跳转、掉电恢复、断线与重复命令测试；问题关闭后才声明可交付 |

PLAYER-002 的工具链和输出风险验证不必等待 PLAYER-001 全部完成，但由当前会话交错执行，不启动其他代理。PLAYER-003 必须依赖已验证的执行语义与板级路径；正式接灯须先完成接口审查与相应授权。8 小时是工程起始门槛，不是寿命认证；其他容量和时序容差在测试前明确，不能事后迁就实现。

首版范围见 ADR；先验证 RGB／Dimmer 等明确支持的灯具档案，未知属性、未支持效果和资源超限都应拒绝发布。复杂控台能力继续保留目标，不作为这条最小闭环的前置条件。

## 实施规则

1. 先明确小批任务的行为、修改范围、接口／错误、依赖和验收，再实现。
2. 核对基线与现有改动，保持同模块单一写入负责人；隔离工作区限定在项目 `.worktrees/`。
3. 工具执行格式化、编译、测试与静态检查，审查差异并验证集成版本。
4. 公共契约、持久格式、所有权、时钟／控制权的变化先记录架构决定；普通实现自主完成。
5. 更新工单、STATE 和交付，区分设计、软件验证和真实设备验证。

## 长期能力主线

以下 G1–G4 保留为能力分层；首次交付从各层取需要的部分纵向贯通，不要求依次做完整层。R03–R09 仍按依赖收敛，不因缩小首版范围自动视为修复。

| 阶段 | 契约与实施目标 | 出口证据 |
| --- | --- | --- |
| G1：核心领域边界 | R03–R09 的依赖、稳定身份、属性能力／类型值、逻辑灯具与 DMX 配适分离、来源／版本语义 | 领域契约和失败场景测试；依赖方向清楚；不提前冻结持久格式 |
| G2：可编辑、可恢复、可播放 | 编辑事务、撤销、编译／激活、虚拟时钟、Cue 状态机与恢复 | 无 UI／无真实设备的节目重放、版本切换及恢复闭环 |
| G3：专业单机工作流 | Tauri／React 下配适、选灯、编程器、Preset、Cue／Sequence、基础效果和参考时间线 | 灯光师能完成代表性编排与播放操作 |
| G4：真实输出与控台硬件 | 输出时序、资源与故障语义、协议／设备适配、推子旋钮接口 | 指定硬件的输出、时序、故障和恢复实测 |
| 后续 | ARM、更多 ESP32 能力档位、移动／Web、云端、预演和 AV 监听分别接入 | 各端能力单独验证，核心不绑定具体硬件或界面 |

以上是产品路线，不宣称功能已实现，也不自动授权设备操作或部署。G3／G4 可在接口稳定后交错验证，具体实现仍先落到任务及契约。
沿用 Rust 核心、TypeScript 界面／云端、Tauri／React 和 Fastify／PostgreSQL 的既定技术框架，不因开发方法变化重新选型。
