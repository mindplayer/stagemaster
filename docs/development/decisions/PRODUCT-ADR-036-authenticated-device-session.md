# PRODUCT-ADR-036：受限设备会话的认证依据

日期：2026-09-28；状态：候选验证中，不能据此开放节目安装。工作区主仓库，验证基线 `c8613c7`。

2026-09-29 更新：已取得用户本次配对确认，macOS 正向已认证配对及同启动加密重连通过，原确认阻塞解除；首轮主机 20 秒读取超时已定位并修正，详见[正向验收](../tasks/DEVICE-002B-pairing-acceptance.md)。持久绑定／撤销、失败生命周期及正式业务协议仍待实施；下面保留候选最初验证记录。

## 问题与候选

安装接口已有 `AuthorizedLink { principal, session }`，但诊断会话与设备描述均不能产生它。必须验证密钥持有／配对依据，并把已认证的连接事实传给传输层；设备不能相信无线请求自报的主体。

优先验证 Bluetooth LE Secure Connections 的 Passkey Entry，复用锁定的 `trouble-host 0.8.0` 与 macOS CoreBluetooth。协议栈实现 P-256、安全管理、加密与已认证等级；产品层只负责准入、权限、生命周期和存储。启用 `security`，不启用 `legacy-pairing`。`Encrypted`（Just Works）不足以开放业务，仅允许 `EncryptedAuthenticated`。不会自己实现 ECDH／AES 协议。

对照 [Espressif Protocomm](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-reference/provisioning/protocomm.html)：其安全会话独立于传输，Security 2 使用 SRP6a／AES-GCM。值得复用职责划分，但当前 esp-hal 裸机不能直接链接 ESP-IDF 组件；本轮不迁移运行时或另写密码协议。若原生配对跨端／资源不可行，再评估现成的应用层协议实现。

参考 [trouble 官方仓库](https://github.com/embassy-rs/trouble) 与项目锁定 0.8.0 源码：`security_manager`、`connection`、`gatt`、`host::ControlRunner`、派生宏权限。当前实现通过 HCI `LeRand` 为安全管理器提供 32 字节种子，配对与重新加密产生独立事件；读取公开描述不证明已认证。此处结论以锁定源码和后续实测为准，不以不同版本网页 API 替代本地接口。

## 验证边界与下一步

先加入独立 `security-readiness` 固件特性，在单独 GATT 服务提供一个**只读且要求认证**的探针，验证 macOS 配对提示、错误／取消／未认证读取拒绝、诊断保活并存、重连加密恢复及实际资源。使用动态验证码，经开发板 USB 本地呈现，不使用写死通用密码。探针不授予安装或播放权限，不改变 0.2.0 正式诊断能力声明；默认构建不含它。

正式 B 必须另明确：物理准入窗口与尝试限制、绑定主体与持久化／撤销、连接级随机业务会话、断开／过期清除、重连重新证明密钥持有、认证失败不降级、配对独立期限与认证后恢复保活、取消／超时晚到结果不授权。绑定密钥不得输出到日志或写入 Git。具体受限会话格式在候选验证后冻结。

开发配对只授权本地设备管理，不替代生产商业授权、文件加密、24 小时离线期限、可信时钟或防逆向。真实安装写入口须等上述边界和 C 的 Flash 调度验证完成后接入。

## 第一轮实板发现

`security-readiness` 及默认构建／严格 Clippy 均通过。新增依赖从官方 crates.io 单独取得并锁定；首次缺 `aes` 的离线失败没有以放宽验收命令绕过。探针使用独立服务 `f889ed70-0100-4e83-968e-799ab99558fa`、只读特征 `...71...`，派生宏配置 `permissions(read = authenticated)`。没有无线写节目路径。

首次先做诊断握手再读受保护特征的尝试失败：系统产生验证码事件，但等待配对期间诊断通信未能续约，设备在 6 秒期限断开，主机返回加密不足。未完成系统绑定，不能声称已通过安全配对。日志 `logs/device-002b-secure-probe.log` 保留失败；验证码仅在当次 USB 控制台显示，未保存绑定密钥。

因此候选流程改为先配对、后 HELLO。实验固件在首次有效 HELLO 前提供固定 90 秒准入窗口；错误报文不续期。首次有效 HELLO 后恢复原 6 秒诊断规则，已建立会话不延长或暂停时钟。`admission_probe.py` 验证这一边界；`secure_link_probe.py` 的正向配对／重连验证仍待系统配对确认，不能拿准入期限检查替代。

准入实板检查已通过：先等待 10 秒再 HELLO 成功，建立会话后的无保活断开为 6.035 秒；另一次连接连续发送 18 个无效 PING，仍在连接后约 90 秒关闭（主机从连接回调计时 89.463 秒）。测量差异包含原生连接完成回调与设备接受连接的先后，不用于改变 90 秒配置。日志 `logs/device-002b-admission-probe.log`。最新候选 ELF SHA-256 `5a110ac55137a1cd484d7c54362cfb052411f51ff4da4b22d09d3053b1554261`；首次安全镜像应用 586,112 B，最新镜像大小见 `logs/device-002b-admission-flash.log`。

最新镜像应用为 588,016 B；原生产品 `Service<Ble>` 在候选镜像上重新通过诊断与身份读取、五次保活、断开清除（`logs/device-002b-native-diagnostic.log`）。堆 41,044 已用／90,028 空闲；这不包括尚未成功配对的完整峰值，也不证明安装／播放器同时存在的预算。

电脑操作工具要求建立新的安全绑定前在操作时确认，已向用户请求当前 Mac 与当前 ESP32 的测试绑定确认。等待期间不完成绑定，继续无配对的构建和故障边界验证。后续正式接入还需原生授权中状态、期限、明确取消及配对结果核验；不能让 90 秒等待表现成“已连接可下发”。
