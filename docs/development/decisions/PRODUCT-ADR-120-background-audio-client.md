## 现状与决定

ADR-119 的真实进程已可运行音乐，但共享客户端的 Selection 尚不认识 audioTimeline，普通 Client 与只读 Reader 都不能连接它。直接给界面添加按钮会绕过既有控制会话，或把已接纳误显示成实际完成。先扩展同一客户端／只读适配，再接桌面资源准备与操作，不创建另一套 HTTP 服务或音频播放器。

1. 客户端解析明确的音频能力、输出类型、组身份、播放代次、原生位置和异步控制状态；普通灯光目录仍兼容。音乐来源与描述必须成对，组与代次／计数受校验，不默默忽略未知音频能力或状态。
2. `apply_media` 复用原会话、修订、请求序号及回执恢复。`View.pending` 仍仅表示 HTTP 操作结果未确认；媒体请求接纳后，实际完成从同一请求标识的媒体控制状态读取，不能据此阻断显式停止或更新意图。读取／重连均不自动接管、不重发播放。
3. Reader 继续只读同一固定工程和采样帧；带音乐的后台可以供原专业预演观察，不给渲染器控制权。未知、错身份或不兼容的音频状态拒绝，不能继续显示为可信执行。
4. 后续桌面准备复用现有不可变运行目录，携带经校验的随附音乐副本，显式输出选择；音乐正式后台与编辑试听的操作必须协调，慢准备／取消期间也不能绕过所有权。关闭编辑器不能停止已准备的正式后台，后台未退出时不擅自重建。
5. 后续界面使用中文音乐操作、位置、已接纳／准备中／已完成／失败，保持精确输入、取消、状态关联及上下文；单独音频组件复用现有后台执行视图。演出循环／末尾定位／重启继续 TIME-001，不把首个普通音乐入口作为完整工单出口。

## 验收顺序

第一增量用原 Client／Reader 连接真实音乐子进程，验证只读不抢权、受控播放／暂停／定位／停止、接纳与完成区分、回执重试／失联、旧代次和旧控制者拒绝、真实软件帧及普通灯光兼容。随后以桌面资源准备和真实产品入口验证声音所有权、编辑与后台隔离、重开接管及唯一三维观察。所有自动音频验收选择软件输出，不打开物理声卡或设备。

首个增量验收：4 项新增专项、126 项相关 Rust 回归及拆分测试后的 3 项最终专项通过，全工作区严格 Clippy／fmt 通过；17 组破坏数据用例、真实丢失回复及仅音乐来源的原桌面投影已验证。标准桌面音乐准备／操作界面和试听协调仍待实现，未重跑全工作区测试或启动用户窗口／物理设备。日志及审查见 TIME-001。
