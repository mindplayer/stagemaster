# PRODUCT-ADR-009：可复用灯具能力与自定义灯具档案

2026-09-24；基线 `9c76803`／main；工作区 `/Users/sunqi/projects/stagemaster`，开始时干净。状态：当前会话完成方向评估；具体持久化结构、公共 API 与执行语义仍需实施前审查，本次不修改它们。

## 需求与判断

用户在实际使用中遇到外形相似、型号相近但不同年份的灯具有不同通道、色盘和图案盘。要求把亮度、颜色、图案、频闪等能力统一抽象，把 RGB 等功能复用于不同种类灯具；能根据说明书或逐步实测自行建立档案，并借鉴成熟控台的有效方法。

这是灯具档案／灯库编辑能力，应当成为核心数据与配适的基础。不能仅给现有通道列表加中文名字：当前一属性映射一组粗细通道的线性编码，不能完整表达档位、区间、条件功能和虚拟属性。也不能根据外形或年份自动认定两个设备兼容。

## 决定

1. **分开标准能力、具体档案、工程实例。** 标准能力描述含义和合法值；具体档案描述硬件变体、模式、通道及功能映射；工程实例引用固定修订，保存配适、安装和校准。多台灯复用同一档案，不共享实例身份或起始地址。
2. **能力组合可复用，但展开后版本固定。** RGB 混色、总亮度、快门、水平／俯仰、色盘和图案盘可作为建档组件。组件更新不能自动改动已有档案；子灯、多组发光单元、多个图案盘必须有独立身份和属性作用域。
3. **编排与通道编码解耦。** 日常编排使用亮度、颜色、位置和档位等类型化属性；Rust 按档案生成通道值。保留通道诊断入口，但原始测试值不自动写入场景。离散档位、连续值、触发命令分别处理，不能将所有值都当成可线性渐变的 0–100%。
4. **硬件变体、设备模式、档案修订分开。** 同名不同硬件／固件、同设备不同通道模式、同一映射的修正各有身份；用户可复制相近档案只改差异。日期、照片和实测记录帮助辨识，不能替代通道核对。更换色盘／图案盘的实物采用独立变体，不静默修改整组灯。
5. **工程固定档案快照。** 私人灯库与外部来源分开管理；工程保存使用中的档案修订和必要资源，离线重开不跟随云端最新版。更新须展示属性、地址占用、默认值、档位和场景引用影响，原子提交且可撤销；不得自动改变已激活播放计划。
6. **借鉴标准，导入独立实现。** 对齐 GDTF 的属性、粗细通道、功能区间、档位、条件及物理信息思想；GDTF／OFL 通过独立适配器接入。识别不支持语义时给出具体缺口，必需功能不允许悄悄丢失后继续编译。不承诺当前格式已兼容完整 GDTF，也不直接复制第三方灯库。
7. **建档与输出控制分开。** 离线创建、校验、数值预览不取得现场控制权。将来的实灯测试通过独立、限范围、可终止的测试会话接入既有控制权和输出仲裁；UI 不能绕过核心直接发整帧。当前讨论未授权操作已连接设备。
8. **控制描述与预演精度分开。** DMX 映射正确不等于三维光学准确。共同指向还需要物理角度、方向、安装姿态与校准；色盘／图案可附资源，几何、配光等按需要完善。完整灯库和预演图片不下发 ESP32，只编译目标节目必需的数据。

## 交互与实施边界

交互采用“搜索／导入或复制相近档案 → 选功能 → 填通道与区间 → 核对或受控测试 → 保存个人灯库 → 批量配适”。常规建档不要求先建立完整三维灯具模型。详细研究、编辑器布局、验证规则和分步验收见[灯具定义设计](../../ui-design/fixture-definition-design.md)。

沿用 Rust 核心与 TypeScript 界面，不增加语言或解释执行用户脚本。先完成精确档案契约及迁移／编码测试，再接编辑器。界面框架仍按 UX-006 推进；真实复杂灯具接入与共同指向必须使用经过验证的档案能力，不能把简化原型映射当作通用灯库。

现有 `FixtureLibrary` 等[模块伪 API](../../module-api/README.md)继续作为边界参考，不据此声称服务已实现。本次只记录架构方向，未改变 `0.1.0-draft.1`、Rust 类型、默认值合成或实际播放行为。
