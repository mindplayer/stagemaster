# ADR-032：NOR Flash 播放包双槽存储

2026-09-28；接受并实施。PLAYER-003D，基线 `9ae315a`。

## 参考与实际约束

复用 Rust [embedded-storage NorFlash](https://docs.rs/embedded-storage/0.3.2/embedded_storage/nor_flash/trait.NorFlash.html)、已锁定 [esp-storage 0.10.0](https://docs.espressif.com/projects/rust/esp-storage/0.10.0/esp32s3/esp_storage/index.html) 及 esp-bootloader-esp-idf 的分区解析／NOR 区域，继续采用 ADR-030 的备用槽和完整校验。官方驱动支持 4 字节编程、4 KiB 擦除；未对齐的源缓冲可能增加 4 KiB 临时栈，故模块内部使用对齐小缓冲，不使用会隐式擦整扇区的普通 Storage 写接口。

按 [ESP-IDF Flash 并发约束](https://docs.espressif.com/projects/esp-idf/en/latest/esp32s3/api-reference/peripherals/spi_flash/spi_flash_concurrency.html)，主 Flash 操作涉及缓存及 CPU／中断调度。Rust 路线不能自动继承 IDF 的所有并发配置；不因两槽或异步函数就声称能边播放边擦写。当前只开放可信宿主明确进入维护／停止现场输出后的安装写入口。真实读源租约保护数据，不证明实时刷新不中断。

## 布局 v1

新增独立 `stagemaster-nor-store`，直接承接 `embedded_storage::nor_flash::NorFlash`；无自建文件系统、路径或 GATT。底层必须为已完成物理操作才返回的同步 NOR 驱动，不能传入只写易失缓存的伪驱动。持久检查还需读回一致；实际电源故障验证仍后续。

所有地址相对于宿主给定的专用分区，模块不接收整芯片绝对地址。逻辑元数据区固定各 4 KiB：A 位于 `0..0x1000`，B 位于 `0x1000..0x2000`；载荷 A 从 `0x2000` 开始，载荷 B 从 `0x2000 + slotCapacity` 开始。每槽容量为 4 KiB 倍数、≤2 MiB；分区必须恰好为 `0x2000 + 2*slotCapacity`。物理擦除粒度必须为 256–4096 的 2 的幂且整除 4096；读粒度 ≤16、编程粒度 ≤256，并符合 2 的幂／整除约束，其他几何明确拒绝。

每槽元数据占前 512 字节：描述区 256 字节、最后独立写入的封印区 256 字节。描述区 `0..8` 为 `STMNOR\0\x01`，`8..12` 为槽容量 u32 小端，`12..32` 为零，`32..128` 为既有 96 字节 Commit，`128..160` 为前 128 字节 SHA-256，`160..256` 为 FF 填充。封印区前 8 字节为 `STMDONE1`，余下为零。两区分开编程、分别读回；固定位置避免驱动读写粒度变化改变封印位置。有效但不兼容的描述／布局必须拒绝打开，不得误作空槽自动格式化；损坏描述或封印报告无效，由安装器选择另一完整槽。

两个元数据地址不随槽容量改变。即使配置变化，仍可读到旧的有效布局并拒绝，避免从错误载荷地址开始擦写。未来更大擦除单位、加密扇区或格式升级须显式扩展／迁移；不把未实现的生产加密塞进本轮格式。

公共封套的摘要位置与覆盖范围包含版本字节，未来版本也须保留这个识别规则。只有公共摘要有效的未知版本才阻止打开；擦除中断可能仅改变版本字节，此时应按损坏记录恢复另一槽，不能误报格式升级。

## 擦写与所有权

- 打开默认只读；维护安装必须显式取得写模式，且仍为单存储实例写入。适配器用 `Rc`／内部可失败借用串行化同一执行器的 NOR 访问，不能跨线程直接共享。快照拥有计数租约，可跨安装器释放／重开继续读取；目标槽被占用时先拒绝再做任何擦除。
- 准备先完整擦除并读回目标元数据区，再按需擦除覆盖新包的载荷扇区；每个物理擦除单独完成及读回，不触及另一槽。只擦所需范围，旧尾部不会成为新包的一部分。
- 连续输入任意字节长度；暂存最多一个编程单位尾部，合并后对齐编程，成功后读回比较，每个字在本轮擦除后至多编程一次。不依赖 MultiwriteNorFlash；重复块在安装器层逐字节核对，尾部由 RAM 接收前缀提供。
- 全量接收后，将最后不足单位的尾部填 FF 编程一次、读回封存。验证使用实际声明长度，不把物理容量或填充算入包；重启后的长度来自已校验的提交元数据，未提交载荷无有效长度。
- 既有 Archive 完整验证后，提交先写描述／读回，再写封印／读回。任何失败均可留下目标区撕裂，提交结果仍由 Installer 的待确认／重读处理；上一完整槽不受影响。未知的部分写入使该暂存失败，须取消后重新擦除，不重写同一物理字来“修补”。
- 没有安装时不主动格式化、启动不擦写；仅全 FF 的元数据视为空。所有元数据和包完整性检查继续在运行选择前完成，不自动播放。

## 固件承接与验收边界

为现有 16 MiB 开发板准备独立的分区方案，保留引导／NVS／PHY／应用更新空间。按[官方分区约束](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-guides/partition-tables.html)校验标签、类型、范围、重叠、只读／加密标志；通过官方解析器和受限 NOR 区域接入。新的构建路径仅做只读准备检查，不改变默认诊断镜像或既有刷写命令，不上传新分区。

软件模型严格执行 1→0、每字一次、擦除及缓冲对齐和边界；在每个擦除／编程／读回步骤分别注入部分失败及重启，包含提交前后、旧槽租约、只读拒绝与错误布局。与真实导出包通过同内核重放对照。无线栈、Archive 校验、旧运行计划和调用栈组合预算须单列；128 KiB 内部堆和历史剩余值不是所有档位可同时运行的证明。


## 实现审查补记

DEVICE-002 实板兼容补记：该阶段的自定义 0x40 分区被锁定 Rust SDK 的 FlashRegion 转换拒绝。后续板级类型改为 data／undefined，地址、容量、元数据和包格式不变；原因、严格拒绝旧类型及受控更新规则见 [ADR-037](PRODUCT-ADR-037-installation-worker.md)。本阶段的构建通过不证明自定义类型的实板路径可用。

精确开发板布局采用 `apps/esp32-player/partitions-storage.csv`，末端 `0xa12000`，NVS／PHY／两个 3 MiB 应用区与 2×2 MiB 节目槽不重叠；官方工具二进制往返及本地镜像打包通过。完整 Xtensa 驱动构建已通过，尺寸／堆和实际函数入口栈帧见[接口资源核对](../../module-api/nor-package-store.md)。对齐缓冲并不保证编译器消除驱动分支的整个 4 KiB 栈预留，不能据源码分支估算任务栈。

当前 esp Rust 1.97.0.0／LLVM 21.1.3 在 `2 * slot_bytes + 8192` 代码生成中报 `Cannot select Constant<8192>`，与上游 [esp-rs/rust#275](https://github.com/esp-rs/rust/issues/275) 的移位加大常量问题一致（机制判断，未声称本地定位了 LLVM 根因）。布局构造对固定元数据长度加 `black_box` 优化屏障，使常量经寄存器参与计算；不改变边界、格式或溢出检查。保留原优化级别／Thin LTO／严格检查，完整链接通过。后续工具链升级可以独立复核并移除屏障；仅 `cargo check` 通过不足以验收代码生成。
