# PRODUCT-ADR-123：媒体提供方恢复与时钟重新绑定

状态：accepted，本增量软件及原生静音验收通过。2026-10-03；TIME-001；基线 `9ac9ef9`，main，当前会话单写者。

## 问题与成熟机制

循环增量已经贯通，当前媒体组仍永久绑定首次准备的 Clock。发生解码／输出故障后，后台的 pull 在读取新指令之前反复报告旧错误；即使重建音源也不能把新的时钟代次接入原组。不能靠重启整个灯光后台或把旧观测换时间戳解决。

参考 [GStreamer 的 Clock providers 与 CLOCK_LOST](https://gstreamer.freedesktop.org/documentation/application-development/advanced/clocks.html#clock-providers)：时钟丢失由应用处理，重新选择时钟与暂停／播放生命周期协调。本项目借鉴显式重新准备及新时间映射，继续复用 Rodio／CPAL 和原执行宿主；舞台恢复后保持暂停，由操作者决定继续，避免自动发声。

## 决定

- 固定同步组、工程快照、来源和输出种类保持；同一提供方身份允许严格递增的重启代次。新身份或旧／相同代次拒绝；更换提供方身份属于另一次明确配置，不从数据包推断。
- 重绑定附着在原 Prepared 中：必须是暂停的已准备位置、实际新音源样本和新映射。激活前验证全部条件，然后在原调度线程一次切换提供方 Clock 与播放代次，并交换旧计划供调用端回收。普通观测永远不能改变绑定。
- 旧键、旧时钟、旧映射、旧准备和旧完成不能激活新一代。入口仍固定一个准备槽、最新观测槽、控制请求／完成槽，不建立额外服务或无限队列。端口初始提供方身份保持；其代次只由权威 Session 激活校验。
- 受控恢复沿原控制会话、修订、序号、期限和回执。请求携带明确位置，只能在实际暂停激活后报告完成；播放／定位不得偷偷承担时钟更换。控制失败不能声称音源恢复，更不承诺回滚已发出的声音。
- 应用记录故障并静默，保留原宿主、其他灯光来源与控制权。显式恢复重新读取后台私有资源副本、核对工程内容摘要、重建音源／输出适配，并以实际健康帧重新绑定。恢复失败可再次尝试，不自动循环重启，不回退到另一种输出。准备完成后保持暂停。
- 客户端用能力声明识别；桌面在失败时提供“重新准备音乐”，明确从头准备并保持暂停，成功后由原播放按钮继续。老后台没有能力时不显示不可用操作。用户项目、持久工程和设备包格式不变。

## 验证与限制

核心验证原组失联后新代次激活、旧键／旧时钟／旧映射／过期准备原子拒绝、独立灯光继续。宿主验证旧控制权、替代／超时、仅恢复请求允许重绑定和真实完成状态。实际后台用资源损坏／修复触发恢复，保留自主来源及同一宿主身份；再验共享客户端和桌面入口。

音频线程与灯光线程分离，当前不承诺任意线程 panic 或整个进程崩溃后热恢复。软件时钟／静音验收不代表物理声卡热插拔、蓝牙音箱或实板同步；未来外部提供方可复用相同恢复契约，时钟误差必须提供实际依据。完整 TIME-001、跨进程试听输出权和云端／U 盘交付仍继续。

实际验收、故障注入与限制见 [TIME-001](../tasks/TIME-001-independent-clock-boundaries.md) 的提供方恢复记录；原宿主、其他灯光来源及控制权保持。追加摘要校验拒绝有效但内容被替换的音乐，资源失效时明确提示关闭后台并从原工程重新载入。
