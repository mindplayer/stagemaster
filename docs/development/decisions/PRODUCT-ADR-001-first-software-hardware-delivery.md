## 触发证据与决定

用户确认首次交付包含软件和硬件，先做 **1 路独立 DMX 输出，每路最多 512 个通道**，尽快验证完整链路；已有 **微雪 ESP32-S3-RS485-CAN**。此前“没有电脑也能在盒子选择场景播放”的要求继续有效。

采用现有板作为首台验证样机，暂不增加树莓派。软件负责编排、保存、校验和编译；盒子保存执行包，拥有播放状态、单调时钟和物理输出。首个传输通道选择 USB，Wi-Fi、云端、多路输出和 ARM 档位后续接入。同一份包的安装与激活边界供未来分发复用。

已有板的隔离 RS485、电源和引脚已核对，但尚未刷机或实测；外部 A/B 端子缺少隔离侧公共地引出，须在连接灯具前解决，见[板卡基线](../../hardware/waveshare-esp32-s3-rs485-can.md)。这是开发平台选择，不是成品 DMX 合规或商业可靠性结论。

## 最小交付闭环

1. 软件中完成灯具配适、场景编排、预览及本地保存／重新打开；沿用现有舞台画布与时间线方向。
2. 导出时检查目标能力，生成包含节目／场景名称、稳定身份、配适与执行数据的版本化包；UI 演示数据不能直接成为正式工程格式。
3. 通过 USB 安装到盒子，区分“电脑已保存”“设备已安装”“设备正在使用”。确认完整校验与持久化后，才可显示安装成功。
4. 盒子执行多个场景的选择、执行、任意跳转、线性渐变／延时、顺序循环及释放；初始验证从明确支持的 RGB／Dimmer 档案开始，其他档案逐项加入。超出支持范围的工程在发送前明确拒绝并定位。
5. 电脑退出、USB 数据连接断开后，在**保持独立供电**的盒子上继续播放并选场景／执行。只让设备转发电脑逐帧数据不满足交付要求。
6. 无电脑操作需要小型本地面板（显示当前／待选场景、选择与执行）；现有 BOOT／RESET 不作为交付操作面。具体面板及 GPIO 扩展另立硬件任务，手机控制作为后续入口。

音频波形继续作为编辑参考。脱机盒子首版负责本地灯光，不内置正式音视频播放器，不承诺与已断开的外部音视频继续同步。复杂多步动态效果、多播放通道合成、RDM、激光／特效设备触发、云端与专业预演不进入这次闭环。

## 模块与调用责任

下表是调用意图，**尚非冻结的函数签名、序列化格式或已实现服务**。PLAYER-001 先补精确执行契约，再写相应代码；USB 报文与持久包在各自任务内版本化。

| 模块 | 调用意图 | 归属与约束 |
| --- | --- | --- |
| 编辑与编译 | `compile(projectRevision, targetCapabilities)` → 包／兼容错误 | Rust；完整解析受支持的场景依赖、配适和资源上限；不得静默忽略属性／效果 |
| 包安装与存储 | `stage` → `verify` → `prepare` → `activate` | 盒子；每步回执分开；写入暂存区，提交可恢复索引，失败保留上一完整节目 |
| 播放控制 | `selectCue`、`go`、`gotoCue`、`release` → 已接受／拒绝 | 同一设备状态机处理 USB 与本地面板；选择不发光，执行不因重连重发而多执行一次 |
| 小型执行器 | `step(monotonicTime, orderedCommands)` → 数值状态 | 共享 Rust，有界内存和运算；无 UI、文件、网络、Flash 写入或日志 I/O |
| 配适与编码 | 数值状态 → 指定逻辑输出的完整 512-slot 帧 | Rust；灯具属性与物理地址分离；首版能力为 1 路，不把硬件引脚写入工程 |
| DMX 发送器 | `submit(frame)` → 接受状态；异步报告发送完成／故障 | 板卡适配；固定节拍、UART 和 RS485 协作，完整帧边界切换缓冲 |
| 平台与操作面 | 单调时钟、存储、看门狗、按键／显示、USB | 硬件适配；面板读取权威状态，不直接写 DMX 缓冲 |

优先验证 Rust `no_std`＋`esp-hal` 固件，设备不携带 TS／Node.js。Xtensa 工具链独立锁定，先验证构建、USB、Flash 和 UART；若该组合无法满足要求，评估 Rust＋ESP-IDF。只有具体 SDK／驱动约束成立才局部引入 C/C++，不能复制第二套场景语义。当前静态核心不能直接当作 MCU 执行器刷入。

## 首版必须明确的行为

- **所有权：** 盒子始终拥有活动节目的执行状态。桌面预览不改变现场输出；首版不混入电脑连续推帧模式。USB 和面板命令有确定排序和权限规则，重连先读取设备启动代次、节目代次及当前状态，不自动补发历史执行。
- **时间与中断：** 播放按单调时间求值，USB 到包时间不作演出时间；渐变中再次执行从当前输出过渡。任意跳转使用编译后的完整目标状态，不依赖用户先播放过前面的场景。延时、循环、重复执行、释放和插值舍入由 PLAYER-001 明确定义并用虚拟时间验收。
- **发送：** 求值与物理刷新解耦。发送器只读取完整不可变帧；迟到时不补发积压旧帧，不得拼接半帧。候选目标为完整帧 40 Hz，属于工程目标；准确 Break／MAB、启动顺序和容差须对照标准并用仪器验收。DMX 无普通数据回执，“UART 已发完”不表示灯具已经响应。
- **更新：** 首版节目写入／切换仅在明确的维护状态执行，输出采取已验证策略；不承诺边演出边擦写 Flash。掉电不能把半包认作完整包，激活旧版也必须校验格式与设备能力。节目更新与固件刷写分开。
- **恢复：** 开机进入待机，不重放历史执行。断开控制连接时继续设备已有本地节目；断电是重启场景，不承诺无缝续播。未知或不兼容包不得产生未经定义的输出。熄灯／释放／看门狗复位分别定义，不能统一写成所有通道置零。
- **限制：** 声明包大小、场景数、操作数、队列长度和 RAM 预算。没有实测前不发布最大带灯数和长时间可靠性指标；一条 DMX 线路的 512 是通道数，不是灯具数量。

## 既有代码与扩展

CORE-001／002 的修复和测试保留。R03 未知属性必须在编译入口拒绝；R04 配适耦合不能扩散进新执行器；R05／R07 未支持的类型与合成不进入首个能力档案；R06 活动包固定修订；R08 建立持续执行模型；R09 明确身份与数值边界。通过限定子集绕开未支持功能，不等于关闭这些历史问题。

后续 ARM 复用工程、编译和执行算法，替换平台适配；未来能力更强时扩展执行档案。Web／移动端复用控制契约，云端负责不可变包存储和分发，不参与现场逐帧循环。首版不为这些后续能力预建空服务。

## 审查结论与出口

选择现有 ESP32 样机是最短的验证路径；“先做完整桌面控台再加盒子”推迟关键物理风险，“仅做 USB-DMX 转换器”无法满足离线场景播放。采用小范围纵向贯通，软件参考执行器与板卡验证交错推进，先暴露输出时序／工具链风险，再做深层 UI 集成。

最终必须同时有：软件保存重开与导出证据；主机／设备同语义重放；独立供电下拔 USB 后本地选场景／执行；实际线路的完整帧、刷新间隔和方向控制记录；坏包／超限／重复命令／掉电恢复记录；持续运行压力结果。仅通过 Rust 测试或灯亮一次均不能结项。阶段安排见[执行计划](../execution-plan.md)。
