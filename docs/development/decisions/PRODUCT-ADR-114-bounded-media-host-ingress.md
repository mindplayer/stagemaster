## 问题与选择

原 LiveBackend 只有场景、手动属性和电平命令。准备结果含播放器与资源，不能直接克隆进命令／历史回执，或在调度线程释放被替换的完整计划。音频持续观测也不能借用操作者租约，否则编辑端消失或输入权到期会连带停止后台媒体。

复用原 Host、Authority、Player 与媒体组，不另建控制服务。采用已有实时媒体系统中“控制命令与消费观测分离、准备在外、短交接”的机制；时间职责沿用 ADR-111 的 GStreamer／NTP 参考，不新增第三方调度框架。

## 边界

1. 每个已准备媒体组仅有一个准备槽和一个最新观测槽，组数受原来源上限约束。槽在宿主启动前分配。准备端拥有可信进程内句柄；句柄不是远程认证或商业许可。
2. 开始／定位通过原 Client 的租约、序号、修订、截止时间及业务回执提交不含资源的不可伪造准备票据。停止走同一控制入口。重复命令返回原回执，不二次激活；控制权失效不能消费准备槽。
3. 准备对象驻留槽内；调度仅 try_lock、校验并交换播放器，成功和业务失败都保留对象供准备端取回释放。忙时拒绝或跳过，不等待。未回收不接纳下个准备；明确撤回使尚未执行票据失效，不撤销已发生的执行。准备端丢失时资源最多占一个槽，保持到宿主终止，不在运行中突然释放计划。
4. 连续观测通过固定组入口更新一个最新值，调度每次最多读取一条；新旧身份、时间质量及连续性由原媒体组校验。结果在只读组状态中回报，未处理的中间观测可以被更新覆盖。没有普通操作租约也可继续观测；提供方丢失依原组失联规则处理。
5. 宿主公开只在同进程有效的单调时钟锚点，与实际调度线程使用同一原点和基值。不得以读取快照的时刻重新标记音频旧数据，亦不得将本机 Instant 序列化成跨设备时钟。
6. 准备后允许在调度外沿既有 Player 向前追赶到新实际媒体位置，再把配对的真实采样一同交接。回退须重新准备；不要求准备完成后媒体还停在最初位置，不伪造零延迟启动。

## 验收与范围

使用真实工程、后台线程与原音频消费源验证：自主灯光与媒体组并行，音频观测不依赖编辑客户端，停止／接管／重复回执、准备取消和容量、读取竞争、迟到及错误观测、组失联不停止自主来源。回收必须在调用端进行；无新播放器／无并行输出权。

本增量不改工程、设备包或 HTTP／GATT 协议。完整桌面／独立进程音频入口、提供方重启重绑定、普通试听和临时循环的统一适配、暂停无消费时的健康／状态协调、实际声卡／板卡同步精度继续逐项接通和验收，不能以宿主 API 的存在宣称全部完成。
