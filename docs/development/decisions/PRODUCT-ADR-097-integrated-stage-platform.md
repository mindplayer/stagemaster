## 触发证据与取舍

用户明确完整目标：声光电编排与现场控对标 grandMA3／Avolites，专业预演和展示对标 Depence，配套云端商业化、有线／无线解码器；终端包括电脑、平板、手机与未来专业实体控台。目前先做好框架，不过度深入局部功能。

现有代码已有单列表播放内核、工程事务、基础音频、应用内 UE 和独立安装／设备运行模块；尚不是完整多系统控台。旧总体文档仍含“所有正式音频外部执行”，与 ADR-052 和已实现宿主播放不一致；持续任务也容易依据 AUDIO-020 的旧接续语句继续细化表单。先统一当前依据，再用跨边界用例验证框架，避免增加更多局部功能后再改根基。

保留 Rust 核心、TypeScript 界面／云端、Tauri／React、Fastify／PostgreSQL／对象存储与独立 UE 适配。选择沿现有模块验证和补边界；不重写全系统、不为每端另建业务核心，也不预建完整插件市场或微服务群。参考机制与局限继续复用[能力总表](../../product-capability-plan.md)、[硬件控制面](../../hardware-control-surfaces.md)、[专业预演](../../ue5-professional-previsualization.md)和[媒体设计](../../audiovisual-stage-design.md)，不将竞品宣传视为性能证据。

## 现在必须守住的关系

1. **共享内容、分别部署。** 工程保存可编辑意图；编译器按目标能力闭合依赖生成执行包。ESP32 只接纳其预算内的灯光执行内容；具备能力的 ARM／控台可另外部署音视频资源。云端灯效模板保留语义、版本和依赖，经过灯具能力绑定才产生通道值。
2. **三类设备连接不能混同。** 控制端到解码器的 USB／以太网／无线承载、解码器本地自主执行、解码器到灯具的 DMX／网络灯光输出分别建模。无线不必等于逐帧无线 DMX，有线也不必依赖电脑持续在线。下载控制与实时帧传送具有不同的背压、顺序、时效与断线策略；不强套一个通用收发队列。现有 BLE GATT 是首个适配，星闪仍是候选。
3. **统一控制语义、区分时间域。** 灯光、音频、视频和机构不共享一个无单位时间字段，也不由界面刷新驱动。每同步组有明确时间来源、定位代次和失联策略；输入控制权、物理输出权、内容许可各自校验。多执行器贡献合成和远程接管需要显式仲裁；控制连接中断不等于节目停止。
4. **音视频执行可本地、可外部。** 已实现的基础本机音频继续保留；未来视频基础播放可作为独立能力接入，具体后端另选。专业混音、DSP、视频合成／融合及激光扫描继续优先成熟外部系统。节目输出、监听监看、参考素材和三维模拟分别标明来源，不把模拟成功当真实输出成功。
5. **预演可以成为独立使用方式。** 无物理输出的工程预演、读取外部控台状态的专业展示、与本机执行并行的观察共享中立场地／设备语义；外部输入的归一化适配另验收。画面嵌入应用不要求 UE 与核心同进程；图形质量按设备分级，手机／平板不强制本地运行完整 UE。
6. **多端复用不等于照搬界面。** 电脑／平板侧重完整编排，手机优先遥控与快速编辑，专业控台突出多执行器和硬件操作；这些是初始职责分配而非永久功能限制。远程 API 经宿主验证后调用相同应用服务，Tauri 只作本机适配。实体控台反馈来自权威状态，保留拾取、临时操作结束和断开后的控制权规则。
7. **商业化具备离线边界。** 账号登录、设备稳定身份、已发布资源、播放许可与网络连接分别管理。按后续 [ADR-101](PRODUCT-ADR-101-commercial-security-boundaries.md)，保留身份、许可和内容／通信保护职责，具体加密授权方法以后确定，暂不实施限时或到期收尾策略。AUTH-001 的生产保护仍须独立验证。云端不可用时，按设备已验证的许可与本地内容决定可执行范围。
8. **机械与特效保留专项安全边界。** 机构动作使用带单位、范围和设备能力的类型化意图；就绪、互锁、急停／故障状态由合适的设备控制层承担。灯光停止／默认值不能直接当作机构安全策略，预演定位也不自动重放不可逆外部动作。此处固定职责，不提前设计具体电机控制算法。

## 代码基线与优先验证

| 主题 | 基线实际证据 | 下一道边界验收 |
| --- | --- | --- |
| 跨端／执行宿主 | `stagemaster-playback`／`runtime` 是 no_std 模块；桌面 `Session` 与音频／预演仍由 Tauri 宿主组装，`SharedSession` 共用锁 | 先用无界面宿主验证不可变计划和独立运行生命周期；客户端关闭／重连与执行分离，慢保存／预演不阻塞输出。不能称现有桌面已实现专业后台引擎 |
| 有线／无线替换 | 安装、运行、会话已有独立 crate；`device-host::Service<B: Transport>` 可注入，但当前 Transport 带扫描、20 字节诊断和安装通知形状，桌面固定 `Service<Ble>` | 以第二种软件承载验证端点发现与会话／安装分离、连接代次／回执一致；实际 USB／以太网／无线各自再实测，不仅更换类名 |
| 多执行器／控制面 | 受限单列表及设备单控制者已实现，专业混合与硬件映射仍是设计 | 先验两路执行贡献加手动／硬件接管：优先级、释放、定位与旧指令失效明确；编辑和现场状态分开 |
| 声光电同步 | `stagemaster-audio` 复用播放调度内核；本机音频源发布消费游标，UE 观察同源状态 | 两个独立时间域下验证准备、开始、定位、漂移与失联；未来外部媒体／机构按能力声明降级，不能以本机音频卡点证明跨设备同步 |
| 专业展示 | `stagemaster-previs` 中立投影与桌面独立渲染桥已存在；应用内 UE 和真实空间编辑有局部验收 | 验证独立只读预演角色、外部控制状态入口及渲染重启；仿真精度、光学库、预算和专业展示质量单独验收 |
| 云端交付／商业化 | 本地不可变执行包、安装事务与开发安全会话已有实现；云目录／分发主要是契约草案 | 发布、下载、安装、准备、激活、播放和授权逐项可对账；离线许可及可信时间另验，开发密钥不当生产方案 |

上述是当前审查发现与待验收要求，不是新增功能已完成的列表。已有回归仅证明各工单记录的范围。契约细化遵循“状态归属／时间／权限／版本／失败／资源预算”，具体字段和方法签名在对应验证工单中确定，不再扩充一份脱离实现的巨型伪 API。

## 实施顺序与本轮结论

2026-10-02 用户进一步明确：本大轮持续完善框架，具体功能与交互细节以后迭代，不追求一步到位。每个增量遵循现状核对、问题／范围、最小实现、相关检查、集成与状态维护；优先处理影响数据、执行稳定性、职责边界和主路径的明显缺陷。尚未进入实际调用的细节保持待定，架构通过少量代表性跨边界用例逐步验证，不一次铺开全部平台、协议和失败策略，也不把所有远期能力当作当前完成条件。

先收敛跨端执行宿主与传输替换的可运行边界，再按依赖推进多执行器／多时钟、专业预演角色、云端交付与许可；许可需求与安全设备政策现在进入约束，不能拖到全部功能完成才补。GDTF／MVR 等标准导入继续复用既有研究，不以导入器代替内部语义和能力验证。

AUDIO-020 已提交的核心／原生音源／运行控制保持；可视区段编辑及完整原生验收仍未完成，优先级后移。持续目标仍 active，接续以本决定和执行计划为准。PLAN-003 本轮只做架构收敛、代码边界核对与开发依据更新；完成这一轮不表示上述框架缺口全部关闭。
