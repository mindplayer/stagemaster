# ADR-029：工程容量与排版解耦

2026-09-28；接受。PROJECT-002，基线 `21f3306`，main，当前会话直接实施。

PLAYER-003A 原生验收发现：同一合法 7,002 场景工程，紧凑文件为 5,414,064 字节，缩进编码为 11,171,569 字节。读取只限制原文件 8 MiB，编辑／保存却限制缩进结果，导致已打开工程不能继续使用。恢复检查点复用同一编码，因此也受影响。

依据 [RFC 8259 §2](https://www.rfc-editor.org/rfc/rfc8259#section-2)，结构字符周围空白不改变 JSON 语义；复用已锁定的 [serde_json 流式编码](https://docs.rs/serde_json/1.0.151/serde_json/fn.to_writer.html)，不自研 JSON、不引入压缩格式或依赖。原有重复键／深度／领域校验继续生效。

- 原始输入仍最多 8 MiB。打开、新建与编辑另外检查**完整规范紧凑编码＋必要修订空间**不超过 8 MiB，按 UTF-8 实际字节及转义后的编码计数，不能用字符数估计。容量检查通过有界计数写入器进行，不分配排版后的整份副本。
- 现行 UUID 固定为 36 字符；空父修订列表首次成为单父修订列表最多增长 38 字节。空父列表预留这 38 字节，已有父列表无需预留额外空间。修订和父修订语义不变，不以省空间为由删修订、业务字段或资源。
- 极限外部输入即使原始文件不超过 8 MiB，如果规范编码或必要修订空间超限，也在打开时给出容量错误；不先接受再于保存时意外失败。8 MiB 是当前编辑器限制，不更改通用工程 Schema。将来改变修订格式必须一起修订此预算。
- `Document::encode()` 优先保留原有缩进与尾换行；缩进超限时改为完整紧凑 JSON。紧凑内容有余量才加尾换行，文件始终不超过 8 MiB。编码器有界写入，缩进尝试到达上限立即中止，复用缓冲区写紧凑内容。
- 编辑在提交前完成同一容量验证；失败保留文档、历史、版本与已有恢复记录。保存仍由 DiskFile 创建新修订并原子提交，恢复仍嵌入完整原始 JSON。两者不各自实现容量规则。
- 缩进与紧凑输出可由同一读取器处理，不改格式版本、公共命令或 Schema 字段。播放包来源摘要继续采用 ADR-028 的无换行规范紧凑 JSON 流，不依赖文件展示排版。

验收：小工程编码保持；大型紧凑工程真实编辑、保存重开、恢复和来源保护；UTF-8／转义与精确容量边界；父修订增长／后续保存；容量失败整批回滚且不消耗历史；已有存储、恢复及包摘要保护测试。结果记录于 PROJECT-002 工单。
