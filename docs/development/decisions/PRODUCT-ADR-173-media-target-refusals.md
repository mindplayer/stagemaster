# PRODUCT-ADR-173：受控媒体陈旧目标的拒绝分类

状态：2026-10-05当前实施会话审定，先记录再修复；关联[AUDIO-022](../tasks/AUDIO-022-short-loop-exit-refusal.md)、[ADR-162](PRODUCT-ADR-162-adapter-refusal-receipts.md)、[ADR-122](PRODUCT-ADR-122-background-audio-loops.md)。仅细化既有诊断字符串与显示，不改变播放／时间／控制权语义，不新增协议字段、播放器或依赖。

## 实际证据与不确定性

`logs/audio-022-original-probes.log`真实独立宿主／原WAV／一秒持续区段，1项诊断测试通过，七个原始探针在`data/AUDIO-022/original-probes.json`。原pass1在同一音源实际进入pass2并暂停后，提交一次旧目标得到HTTP200／原会话complete／rejected／invalid；音源、PCM、组及最近已应用音乐请求不变。同一音源的错实例／错区段、错代次同样invalid；非法范围和零遍次保持invalid，带前导零的整数在HTTP422拒绝，随后原未消耗网络序号可用于另一明确合法请求。

旧遍次拒绝是正确保护，**把它和真正格式错误合并为同一提示是已证明的诊断缺陷**。PREVIS-012原生失败没有原写入载荷／HTTP正文，不能把本次独立复现追认为原失败或历史循环rejected根因。启动采样显示测试进程尚在`_dyld_start`，同一原句柄等待后真实测试2.62秒通过，不改变产品期限或重启来掩盖系统加载等待。

## 决定与失败行为

1. 格式与容量检查、未知音乐组、零音源／零遍次、超128区段范围继续invalid，解析期HTTP422和网络序号接纳边界不变。对已知音乐组，合法格式但组代次不再一致，返回既有Failure／complete／rejected，诊断`mediaTargetChanged`：“音乐运行目标已变化，请核对当前状态后重新操作”。合法音源／区段／遍次但不匹配权威当前目标，诊断`loopTargetChanged`：“循环播放目标已变化，请确认当前区段和遍次后重新操作”。
2. 仍在原适配层、向Runtime提交之前拒绝；沿ADR-162保留code／message与控制绑定，消耗原网络序号而不创建音乐请求或消耗Runtime意图序号。响应仍HTTP200完成回执，不把Failure内部conflict状态伪称成外层HTTP409。客户端code本来是诊断字符串，新增两个值不新增成功种类、字段或协议版本；旧客户端仍可显示原message。
3. 不读取一个“更新目标”来替换调用方动作，不自动重发、开始、定位、暂停或转交下一遍。只读刷新仍走原入口，用户下一次明确动作才使用其所见目标；准确实例／区段／遍次、控制权／修订／原期限与完整帧再次核验保持。适配后才跨界的迟到操作仍由原提供方拒绝／Failed，不冒充这里提前拒绝或Applied。
4. 界面不能在新的rejected／unknown或尚未对应同一音乐请求时，用上一条音乐Applied显示“最近音乐操作已完成”。复用既有MediaRequestIdentity／mediaSeekReceipt和原状态，在音乐控制附近表达拒绝／未确认，保留原草稿、播放位置和控制权；不增加数据所有者、定时器或隐式恢复。
