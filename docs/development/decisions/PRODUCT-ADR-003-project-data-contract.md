## JSON 与 YAML 的选择

依据 [JSON RFC 8259](https://www.rfc-editor.org/rfc/rfc8259)、[YAML 1.2.2](https://yaml.org/spec/1.2.2/) 和 [JSON Schema 2020-12](https://json-schema.org/draft/2020-12)。下表的适用性是针对本产品的工程判断。

| 比较点 | JSON | YAML |
| --- | --- | --- |
| 手工编辑 | 标点较多，标准语法无注释 | 支持注释、块文本，适合手写配置 |
| 数据解释 | 类型／语法范围较小，但仍要限制数字、重复键等 | 还需约束版本、类型解析方案、标签、锚点／别名等 |
| 跨端工程 | 适合以软件读写为主的统一正文 | 可以采用严格子集，但会额外增加规范和解析验收工作 |
| 共享对象 | 通过明确的稳定 ID 引用建模 | 锚点名称属于序列化细节，不能替代持久业务身份 |
| 体积／性能 | 须以实际样例测量，不能仅凭格式名保证 | 同样须实测，排版较短不等于总包或运行内存较小 |

采用**严格 JSON 作为工程正文的首版编码，配套 JSON Schema 结构约束和 Rust 领域校验**。首版仅一种正式正文编码，不同时维护 JSON／YAML 两套工程读写链。YAML 不纳入当前工程格式；以后确有手写配置需求时在独立用途评估。

JSON Schema 校验字段、类型与范围等结构；预设存在性、引用类型、循环、配适碰撞、可编译性等由 Rust 校验。工程对象引用不是 JSON Schema 的 `$ref`。结构契约须有单一维护来源及一致性检查，具体生成工具在实施时验证，不手工维护互不校验的 Rust、TypeScript 和 Schema 三份规则。

工程 JSON 使用 UTF-8；拒绝重复键、非有限数值和超出声明边界的输入。对象 ID 用字符串；精确时间和大整数不能无约束经过 JavaScript Number。数组保存有意义的顺序，对象成员排版顺序不参与业务含义。注释性业务说明用正式字段保存。具体字段、时间单位／精度和摘要规则在 PROJECT-001 固定，不能把现有 UI 浮点秒或原型通用归一化值固化为全部语义。

## 工程模型、文件与播放器的边界

| 表示 | 负责内容 | 依赖边界 |
| --- | --- | --- |
| 内存工程模型 | Rust 维护对象、引用、编辑规则及修订 | 编辑命令修改模型，业务模块不各自读写原始 JSON |
| 持久工程正文／交换包 | 保存指定修订，读取时校验／迁移并恢复模型 | 编码转换与存储独立；不能直接把当前 Rust 结构体布局当长期标准 |
| 编译计划／设备播放包 | 从固定工程修订和目标能力生成执行内容 | 独立版本化；播放器不每帧重新解析原工程 |

读取链为“文件 → 解码／迁移／结构与领域校验 → 工程快照”，编辑和编译基于模型。保存链将指定快照持久化；文件保存不会自动改变现场计划。编辑、保存、编译、激活及云端同步分别确认。

JSON 正文、文件容器和工作存储分别选择：小型自包含样例先验证正文；需要带素材交换时评估“清单＋正文＋独立资源”的封装。音频、模型等二进制不默认塞进一个巨大 JSON；可重建缓存与正式素材分开。未来增量保存或事务数据库可留在存储边界，不要求每次编辑都重写整个交换包。设备包继续按目标预算编译，不受主机工程编码影响。

## 最小标准必须先解决的内容

1. **身份与关系：** 工程／对象稳定身份、修订、复制／导入的重映射；名称、显示编号、列表位置和 DMX 地址不作为永久引用。
2. **对象与行为：** 逻辑灯具、档案／模式、逻辑配适、编组、预设、场景／列表，以及明确支持的时间表达；值类型、单位、缺省／继承／释放及预设引用不能混同。
3. **版本与演进：** 结构、执行语义、档案和播放包分别版本化；未知必需能力禁止编译。未知可选内容只有能完整保留且不破坏依赖时才可编辑重存，否则只读或拒绝。不能只添加一个扩展字典就宣称前后兼容。
4. **资源可移植：** 固定档案版本和内容摘要，并能获得对应内容；工程不能只依赖某台电脑的绝对路径。缺失必需资源应明确诊断，不能静默换成最新版本。
5. **保存正确性：** 指定修订形成一致快照，失败不覆盖最后完整工程，旧保存不能覆盖新结果；实际提交点通过中断测试验证。首批不以持久撤销历史、自动恢复日志或多人协作为前置条件。

逻辑配适可保存；到具体 USB／串口／网口的现场绑定独立版本化、按需附带。本机运行句柄、正在输出的帧、拖动中的临时状态和账号凭据不放入节目正文。界面偏好与节目语义分区，需要恢复的会话另有契约。
