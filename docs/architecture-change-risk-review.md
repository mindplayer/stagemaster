# 架构变更风险审查：避免后期大范围返工

日期：2026-09-10。范围：架构 v0.2 与当时声光视频补充中的设计假设；本轮没有新增实现或设备测试。当前权威设计入口为[架构 v0.5](architecture.md)。此前已复现的代码问题仍见[代码审查](architecture-review.md)，不因文档修订视为解决。

2026-09-11 范围更新：本文保留历史审查及 B01–B09 编号；其中“内置媒体／音频总线／正式音视频输出”已由[外部控制与监听方案](audiovisual-stage-design.md)取代，相应验收改为外部逻辑目标、监听接收和现场绑定。硬件适配另外包括[双向控制面](hardware-control-surfaces.md)。通用的版本、资源、时序和能力校验要求继续适用。

## 判断与优先级

系统方向成立，但“任何主板只增加音视频输出适配层”表述过强。应追求：**工程语义、编辑规则与大部分执行逻辑保持复用，目标平台按能力重新构建、适配、编译节目并验证。** 目标不具备的解码能力、内存、接口或运行环境，不能由一个输出接口补出来。

下面 H01–H09 应在对应的持久格式或公开接口定型前明确；H10 是把设计变成证据的门槛。无需同时实现所有功能。首期可以支持少量类型和一个写入者，但不能把“目前只支持一种”编码成“永远只能有一种”。

## H01 · 硬件适配范围和能力声明过粗

原有文档对 ARM 的描述容易被理解成换音视频出口即可。实际适配至少有四个边界：

| 边界 | 职责 | 不进入其中的业务 |
| --- | --- | --- |
| 平台服务 | 单调时钟、线程／调度、文件与持久化、进程生命周期、设备发现 | Cue、Preset、跟踪规则 |
| 媒体后端 | 解码、GPU／帧内存、音频设备时钟、视频呈现与格式协商 | 节目对象和灯光效果语义 |
| 输出传输 | RS485、USB、网络、音频端点、显示／专用视频输出 | 工程编辑和素材引用 |
| 目标能力与接纳 | 必需功能、格式／速率／通道组合、容量、资源预留和验证记录 | 凭主板名称猜测支持能力 |

这些是分开的接口族，可以共用一个平台实现包；避免一个持有所有业务状态的万能 `Platform` 对象。

`supportsVideo=true` 不足以判断节目可运行。还要检查编码配置、分辨率、帧率、色彩／像素格式、并发流、音频声道与采样率、输出模式、可调度时间和缓冲要求。标称能力、当前设备探测结果与已验证运行组合分别记录；单路各自支持不代表同时运行都支持。

视频帧也不总是 CPU 可直接读取的字节数组。GStreamer 的 DMA buffer 文档说明，缓冲共享依赖格式、内存布局与上下游协商，CPU 映射还可能不可用或成本很高；这是媒体后端需要隔离的硬件差异。[官方设计说明](https://gstreamer.freedesktop.org/documentation/additional/design/dmabuf.html)

完整桌面／Linux 系统与受限固件目标分档验证。Rust 的 `std` 和无完整系统服务的 `no_std` 环境存在依赖边界；不能仅因都使用 Rust 就认定现有工作区直接运行。[Embedded Rust Book](https://docs.rust-embedded.org/book/intro/no-std.html)

**验收 B01：** 同一工程交给完整媒体目标和灯光专用目标，分别得到可执行计划或精确的能力拒绝；前者更换媒体后端不修改工程语义。模拟能力测试不能替代真实板卡验证。

## H02 · 工程格式、逻辑计划与硬件执行产物需要进一步分开

工程用于长期编辑，逻辑计划用于固定节目行为，目标执行产物用于运行。若把内存结构、GPU 句柄、操作系统路径或某个编译器生成物直接当作永久工程格式，后续换平台和升级引擎会被锁住。

增加明确的两级编译边界：`工程修订 → 逻辑计划 → 目标执行计划`。开始可以是同一编译器中的两个步骤，不必立即公开一种新的中间文件格式。

工程保存稳定对象身份、单位、意图、源素材及引用；目标计划可包含紧凑索引、预计算结果和目标素材。运行时句柄在准备阶段建立，不作为可移植持久数据。跨 CPU 数据的字节序、整数精度与格式版本需要显式定义。

schema 迁移解决“如何读取”，执行语义版本解决“读取后是否仍是同一节目”。例如改变 LTP 或效果曲线，即使文件字段完全相同，也可能改变演出。引擎应声明支持的语义范围；不兼容时提供差异／迁移报告或拒绝激活，不静默按新规则播放旧节目。

**验收 B02：** 同一工程生成两种目标计划，核心逻辑结果一致；旧语义样例在新版本中得到明确兼容结果。已运行计划不因后台灯具库更新改变。

## H03 · 节目内容与现场安装绑定仍需独立版本

目前档案、配适、路由、校准已有逻辑区分，但缺少可独立管理的“现场绑定”契约。同一个节目换场地、换声卡或搬到盒子时，不应重写所有 Cue 的引用。

保留节目中的编程灯具／子灯、音频总线、视频 Surface 等逻辑身份；以 `DeploymentBindingRevision` 映射实际设备、端口、场地校准和素材存储位置。它是完整、可查询的一份绑定版本，不引入层层隐式覆盖。

普通控台用户仍可直接给具体灯具编程，无需先学习抽象角色。更换实际灯型、安装方向或空间位置需要换灯／校准与影响检查，不能用绑定层伪装成无需检查的等价替换。

激活清单同时固定工程修订、逻辑／目标计划、现场绑定、档案与素材版本。路径是运行环境中的定位信息，内容哈希才是素材身份。控制凭据保存在设备配置，不进入可分享节目。

**验收 B03：** 只更换声卡端口、视频显示端和 DMX 接口后，Cue／媒体对象身份不变；缺失的实际端点明确显示未配适，不自动选第一个设备。

## H04 · 一个全局 epoch 会把无关操作绑在一起

v0.2 用 `epoch` 表示计划切换，媒体补充又用它表示 Seek。若实现为一个全局编号，定位背景视频可能使音乐与灯光命令失效；无关编辑也可能冲掉待执行的 Go。

| 身份／代次 | 何时变化 | 失效范围 |
| --- | --- | --- |
| RuntimeInstanceId | 引擎重新启动 | 旧进程的控制与运行句柄 |
| PlanGeneration | 对应执行域激活新计划 | 该域旧编译索引与计划绑定工作 |
| TransportGeneration | 某同步组定位／重新开始等不连续变化 | 该组旧时间位置下的预定事件与帧 |
| ClockEpoch | 某时钟映射失效／重新建立 | 依赖该时钟映射的调度 |
| OutputLeaseGeneration | 物理端点控制权交接 | 旧所有者尚未提交的发送 |

每个代次都有作用域 ID。跨域同步还可有一次激活协调 ID，但它不能替代这些不同含义。命令只绑定其必要的前置条件；使用旧紧凑索引的命令必须拒绝，稳定对象 ID 的命令是否可以映射到新计划需按命令类型明确。

同步组的主从关系应无循环，每组在同一时刻只有一个有效时间映射权威。参数调速、暂停与 Seek 对代次的影响分别定义；不能把每次正常时钟推进都看成新代次。

适配器可以丢弃尚在自己队列中的旧帧；已经进入设备缓冲或物理线路的内容未必能撤回。切换政策需纳入排空、截止时间与反馈能力，不能只凭软件标签承诺瞬间清除旧输出。

**验收 B04：** 背景视频 Seek 不影响独立音乐／灯光；同时切换配适时，旧计划帧不能按新映射发送；引擎重启后旧客户端命令不意外生效。

## H05 · 现场参数、工程事务与控制权需要不同通路

若把所有变化都送入“编辑 → 保存 → 编译 → Apply”，现场推杆、Programmer 和效果速度会受存储与编译延迟影响。若全部直接改运行对象，又会失去记录与重放能力。

不可变计划固定结构和语义；允许动态控制的参数以有类型、有范围的槽位声明，运行时通过有界命令更新。Programmer、Playback level、效果 Size／Rate 等走现场通路；保存引用、改变对象结构和 Record／Update 走编辑事务。现场 Override 的撤回、保存及作用域可查询。

控制器接入权限与最终 HTP／LTP 合成是两个层次。编辑单写者、同一执行器的控制租约、多个合法 Playback 的贡献合成都应分别定义。电脑、手机和实体推杆争用同一个控制量时，需要明确接管／拾取与反馈；“最后一个网络包赢”不作为默认控制权规则。

协调器失败时各执行器如何继续、停止同步组由谁授权、端口租约何时撤销都要显式；不靠永久在线的全局服务给每个灯光 tick 发许可。

**验收 B05：** 后台编译／保存期间推杆继续响应；手机接管后旧控制端不能夺回同一执行器；其他合法 Playback 的混合不被错误禁止。

## H06 · 状态、动作和反馈不能统一成一个“值”

灯光亮度这类可持续求值的状态、播放一次音效这类离散动作，以及设备实际反馈应采用不同契约。Seek 和断线恢复可以重建持续状态，但不自动重做经过的全部动作。

离散动作声明作用对象、有效期、顺序、去重范围、是否允许重放／补偿和反馈级别。外部设备可能只确认收到命令，也可能完全没有反馈；执行结果未知时不能无条件重试并声称恰好一次。

每条反馈带源设备、采集时间、质量／新鲜度与相关命令。区分“期望值”“已计算”“已发送”“设备观测”，诊断图不能把前者冒充后者。普通 DMX 属性合成不承担全部设备的动作语义。

**验收 B06：** 跨过一次性动作定位、断线重连与消息重试不会导致隐式重复触发；未知反馈保持未知，持续属性按恢复策略重建。

## H07 · 媒体缓冲和资源生命周期缺少足够具体的契约

分进程并不能隔离 GPU 显存、磁盘带宽和系统内存。若视频预览无限排队或复制大帧，仍可能拖垮同机输出。API 不能只返回“某个帧”，还应说明拥有者、有效期、格式、时戳、跨进程传递方式和消费完成通知。

分开控制消息、状态订阅、诊断日志和媒体数据通路。媒体缓冲支持声明的内存类型与消费栅栏，跨平台通过适配协商；共同内存复制可作为有预算的回退路径，不强求所有目标零复制，也不把 GPU 指针放进通用协议。

每条队列声明容量、消费者掉线与过载政策。预览可丢过期画面；Go 等动作需明确接纳／拒绝；音频欠载按音频策略处理，不能套用“只保留最新样本”。准备计划时预算 CPU／GPU／内存／磁盘／解码实例，运行中监测组合负载。

正在播放、待激活与仍被缓冲引用的计划／素材必须被固定持有；缓存清理与云端垃圾回收不能删除它们。旧计划退出后再按引用和完成通知回收，核心运行线程不执行大对象释放。

**验收 B07：** 预览消费者停滞、视频过载与缓存清理时，资源保持有界；正在运行的音频／灯光不等待预览；不会释放仍在使用的帧或素材。

## H08 · 保留未知字段不等于可以安全编辑整个工程

手机保存时原样保留不认识的效果节点，只能防止直接丢字段。如果该节点引用了灯具，而手机允许删灯，引用仍会损坏。任意嵌套原始 JSON 也不自动具备可查询依赖。

扩展块必须带命名空间、版本、必需／可选标志，并以标准化元数据声明外部引用和所需能力；扩展处理器提供可验证的结构变更规则。未知扩展的引用信息可信度仍需校验，不能当成可执行指令。

客户端通过核心报告的“允许操作”做受限编辑；不知道依赖或迁移规则时，对可能影响该扩展的删除／克隆／重映射保守拒绝，并说明原因。支持的局部操作可以继续，避免静默损坏高级内容。公共云导入和旧版客户端都遵守同一规则。

**验收 B08：** 含未知效果节点的工程在简化客户端修改名称后保持原数据；删除其引用灯具时被明确阻止或由理解该扩展的服务完成验证转换。

## H09 · “已修改”“已保存”“已生效”的提交点需要精确

v0.2 写了“提交修订 → 写恢复日志”，同时允许内存成功与持久化状态分开。设计尚未规定何时可以向用户显示已保存，也未约束异步结果乱序。

定义独立确认点：内存事务已应用；本地持久提交已完成；编译已完成；对应运行域已激活；云端已同步。显示与回执带修订 ID，后完成的旧编译不能覆盖新计划，晚到的旧保存不能覆盖新文件。保存为 durable 的确认必须在所选存储协议的持久提交完成之后。

保存失败可保留内存变更并明确显示未保存，依然运行已准备节目；不能因为保存慢而阻塞现场参数，也不能把未保存变更标记成功落盘。恢复日志、快照和素材引用需形成一致恢复点。基于对象的云冲突处理需保留共同基准和删除记录，避免旧离线客户端把已经删除的对象复活。

**验收 B09：** 模拟保存失败、中断和编译乱序，最后完整版本可恢复；客户端能看出当前编辑、磁盘和现场各自是哪一版。

## H10 · 文档需要由跨边界实例证明

上面是设计修正，尚未验证。继续增加文档不能代替穿过所有边界的小型节目。保留一个易读的参考求值器，按明确业务例子计算期望结果；优化执行器与它做对照，但不把同一个实现生成的结果当成唯一正确答案。

先建立身份／类型／引用／时间／命令的契约样例，再推进保存和 UI。以 B01–B09 为跨边界验收，使用虚拟时钟、模拟适配器、故障注入和旧格式样例。目标硬件随后实测，只有通过的组合进入支持清单。

建议最早验证的四个组合：

1. 多单元灯具＋Preset 引用＋多 Cue 跟踪＋现场 Override，检查身份与值模型；
2. 主音乐与独立背景视频，定位其中一组，检查代次和控制范围；
3. 同一节目更换现场绑定及受限目标，检查可移植性与能力拒绝；
4. 播放中编辑／保存／编译乱序＋未知扩展，检查不会错版、丢数据或静默改变现场。

上述验收现在均为待实现，不计入现有 10 项单元测试。

## 开发约束

稳定的承诺优先放在身份、单位、语义版本、状态所有权和可迁移格式上。线程数、模块物理数量、容器格式、驱动和渲染实现保持可替换；不预建庞大的空模块、全局事件总线或要求所有目标采用同一低层实现。

本轮修改仅涉及架构与交接文档。未来仍会有演进和迁移；这里的目标是把变化限制在可识别的边界，提供可验证的兼容与恢复路径，而非承诺永远没有重构。
