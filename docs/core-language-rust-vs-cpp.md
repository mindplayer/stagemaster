# 核心语言复评：Rust 与 C++26

日期：2026-09-11。依据：用户明确要求核心不采用 TS 一类依赖托管运行时的实现，核查当前工具链、官方语言／编译器资料及本项目边界。结论为继续使用 Rust 主核心；这是工程适配判断，没有 Rust／C++ 对照性能测试，也不以现有少量代码形成迁移包袱。

## 1. 结论及适用范围

**StageMaster 的工程权威语义、编译、Cue／效果求值、现场状态机、调度和 DMX 编码继续采用 Rust；TypeScript 用于界面、客户端流程、接口类型和 Fastify 云端业务。** 输出关键路径不经过 JS／TS 回调、WebView 或云服务。UE、特定厂商 SDK 和控制面固件按能力在明确边界内选择 C／C++ 等实现。

Rust 与 C++ 都是高级的系统编程语言，比较重点是原生代码、内存管理、并发正确性、目标平台与依赖成本。C++26 是一个 C++ 标准版本，不是一个自动比 Rust 更低层或更快的执行引擎。

docs/module-api 下的 `.ts` 是接口草案、客户端类型与调用示例；它们的类型检查不表示引擎由 TS 实现。当前实际领域、Show、执行及 DMX 原型位于 Rust crates，仍是待完善的静态原型。

## 2. 对本项目的比较

下表的适用判断属于本项目分析，不是语言性能排行榜。

| 维度 | Rust | C++／采用 C++26 特性 | 对 StageMaster 的判断 |
| --- | --- | --- | --- |
| 性能与内存控制 | 可编译为原生代码；可预分配、使用紧凑布局，不依赖追踪式 GC | 同样可用原生代码、RAII、预分配与紧凑布局，不要求 GC | 两者都有满足核心需求的条件；实际速度、尾延迟和体积必须测量 |
| 内存／并发正确性 | 所有权与借用检查在编译期约束生命周期和共享写入 | RAII、智能指针、规范与工具可提高正确性；仍需管理指针、别名和同步规则 | 新建且长期变化的复杂核心更适合优先利用 Rust 的默认检查 |
| 实时性 | 分配、锁、析构、panic、系统调用仍可能破坏预算 | 分配、锁、析构、异常、系统调用同样需要约束 | 选语言不能代替有界运行设计、驱动时序和故障测试 |
| Tauri 与两种主语言 | 原生宿主和核心直接沿用 Rust | 保留 Tauri 时通常增加 Rust 宿主到 C++ 核心的接口与构建边界 | 当前选择 Rust 更符合减少主要维护边界的要求 |
| 厂商 SDK／UE | 可经 C ABI 或独立进程适配，部分 SDK 需额外封装 | 对直接提供 C++ API 的 SDK 和 UE 接入更直接 | 这是局部采用 C++ 的理由，不必让 UE 或 SDK 决定整个核心语言 |
| 桌面／ARM／MCU | 主机目标与受限固件分别评估；支持等级和依赖不相同 | 同样取决于编译器、标准库、BSP 和 SDK，不能默认 MCU 支持全部 C++26 | 核心与固件分工，按确切目标验证，不承诺一份二进制通吃 |
| 长期维护 | 类型设计和借用规则有学习成本；避免泛型、宏和共享状态过度复杂化 | 成熟团队及已有库可能显著降低成本；需持续执行内存与并发纪律 | 本项目未发现必须复用的大型 C++ 核心，Rust 的结构约束更有价值 |

事实依据：Rust 用编译器检查的所有权管理内存；Safe Rust 在安全抽象正确的前提下排除数据竞争，但不排除死锁、一般竞争条件和业务错误。[Rust 所有权](https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html)、[数据竞争与一般竞争](https://doc.rust-lang.org/nomicon/races.html)。C++ 的 RAII 与并发规范同样可用于构建可靠代码，不能将现代 C++ 等同于到处手写裸指针。[C++ Core Guidelines](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines)

Tauri 的原生核心进程采用 Rust；因此保留现有宿主路线时，用 Rust 实现我们的引擎可减少一层跨语言集成。这是对项目构建成本的推断，不是 Tauri 禁止 C++。[Tauri 进程模型](https://v2.tauri.app/concept/process-model/)

## 3. C++26 的价值与当前成熟度

不能再简单说“C++26 还没完成设计”。2026-03-29 的委员会会议报告说明，其技术工作已完成，进入最终文件、国际批准投票和编辑流程；报告列出反射、标准库加固、contracts 与 std::execution 等重要变化。本次不将技术完成等同于已核实 ISO 最终出版状态，也不把这些改进当成完整内存安全保证。[委员会参会者报告](https://herbsutter.com/2026/03/29/c26-is-done-trip-report-march-2026-iso-c-standards-meeting-london-croydon-uk/)

截至本次查询，Clang 的 C++26／C++2c 支持仍标为部分实现；GCC 的 C++26 支持页仍有实验性说明，标准库实现也有单独进度。因此不能把“开启 C++26 编译选项”当成 macOS、Windows、Linux、ARM 和 MCU 全部具有同一能力的证据。[Clang 状态](https://clang.llvm.org/cxx_status.html)、[GCC 状态](https://gcc.gnu.org/projects/cxx-status.html)、[libc++ 状态](https://libcxx.llvm.org/Status/Cxx26.html)

若未来采用 C++ 模块，按实际编译器／标准库／SDK 建立特性白名单；可先用共同验证过的 C++20／23 子集，逐项引入确有收益的 C++26 特性。C++20／23 也不能只凭标准名假定所有特性完整支持。反射或新的并发框架有工具价值，但灯光输出稳定性不依赖必须使用它们。

## 4. Rust 需要面对的真实限制

Rust 不会自动生成合适的架构。错误的 `unsafe`、FFI 或底层库会破坏安全保证；业务状态、时序、权限和设备故障仍要自行验证，内存安全不等于演出正确。[Rust 未定义行为与 FFI 边界](https://doc.rust-lang.org/reference/behavior-considered-undefined.html)

MCU 工具链必须具体核实。Espressif 当前文档说明，ESP32／S2／S3 的 Xtensa 路线需要专用 Rust 编译器分支，部分 RISC-V 目标可使用上游稳定工具链。因此不能把“Rust 支持嵌入式”理解成所有主板都是相同开发成本。[Espressif 工具链说明](https://docs.espressif.com/projects/rust/book/getting-started/toolchain.html)

专业主机的引擎与输入 MCU 可以采用不同实现：主机承担完整节目语义；MCU 承担扫描、去抖、本地电机控制和接口时序。若某 MCU 的厂商 C／C++ 工具链更合适，限定在固件，遵守共同协议；它不需要重新实现一套 Cue／Phaser 语言。Rust 的 std 与 no_std 依赖也必须分开评估。[Embedded Rust no_std](https://doc.rust-lang.org/stable/embedded-book/intro/no-std.html)

MCU 也可承担[受限的独立 Cue 播放](standalone-cue-player.md)，不只作为输入或输出外设。此时优先验证共享 Rust 小型执行算法，工程编译留在主机；`esp-hal` 与社区维护的 ESP-IDF Rust 绑定分别核查所需服务和支持状态。换成 C 宿主不会消除内部 Rust 模块的工具链要求，不能把它当作绕开 Xtensa 编译器的办法。

与 C／C++ 库互操作时，优先评估窄 C ABI 或版本化进程接口，明确缓冲所有权、错误、线程和释放责任；不在实时路径反复转换大对象。标准 C++ 对象布局不直接作为跨语言永久接口。[Embedded Rust 互操作](https://doc.rust-lang.org/stable/embedded-book/interoperability/c-with-rust.html)

## 5. 核心实施约束

以下是本项目对实现的要求，两种语言都须满足：

1. 编译／加载阶段分配和准备资源；灯光 tick 使用已验证计划与有界缓冲。
2. tick 不等待 UI、文件、网络、数据库和不可控锁；队列满有明确拒绝／合并策略。
3. 大对象析构、引用计数归零后的回收和日志格式化移出关键路径，不能仅凭“无 GC”推断耗时上界。
4. 输入与计划边界显式校验；核心避免可恢复错误走 panic／异常，宿主定义不可恢复故障与输出策略。不把 `panic=abort` 或禁用异常当作可靠性证明。
5. 物理 DMX 时序、缓冲与失联行为由目标适配／硬件能力承担并测量；普通桌面 OS 上使用 Rust 或 C++ 都不能自动取得硬实时保证。
6. 主核心采用锁定并验证的稳定工具链与依赖；MCU 专用工具链隔离管理，不因一个外设让全部桌面核心依赖实验分支。
7. 用代表性节目验证多路播放、效果、输入突发、计划切换、监看压力、队列满和重连，记录分位耗时、最大耗时、截止超限、内存和实际帧间隔。无两种等价实现时不声称语言跑分胜负。

## 6. 何时重新选择 C++ 核心

只有出现明确证据才重开主核心选择：必须复用且占主要语义的大型 C++ 引擎；目标平台无法合理支持 Rust；关键厂商接口经窄适配仍不能满足需求；或等价原型显示难以解决的性能／资源问题。单个 SDK 使用 C++、UE 使用 C++、或者标准年份更新，都不足以单独推翻主核心选择。

同一核心语义暂不维护 Rust／C++ 两份实现。保留中立工程、消息、数值帧和设备接口，为必要的局部替换提供边界；将来替换仍有验证和迁移成本，不承诺零成本换语言。

本机核查结果：rustc／Cargo 1.97.1，Apple Clang 21.0.0；项目 Cargo 声明 Rust edition 2024、rust-version 1.97。这只证明当前工具版本，不证明完整 C++26 支持或实时性能。本轮没有安装新工具链、改变产品语言或增加原生依赖。
