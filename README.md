## 用户已经明确的方向

- 产品未来用于商业销售。当前首先面向灯光师本人，建设专业灯光编排与控制系统；让客户通过简单操作使用专业灯光效果，是在这个基础上扩展的后续产品能力。
- 长期对标 grandMA3（MA3）或老虎控台，建设专业单机编程与现场控制系统，再持续扩展；首次交付范围按下面的软件＋播放盒闭环收敛。不能沿用“专业控台工作流程不属于本产品”的旧定位，也不要求首版一次实现全部能力。
- 对标成熟控台的能力与工作方法，具体对标项与实现顺序继续细化；不等于首个版本一次性达到全部功能对等，也不以解析、破解其专有工程文件或复制其实现作为路线。
- 用户要求当前会话主动吸收优秀软件的重要、必要能力，不只等待用户想到后再添加。以[能力总表](docs/product-capability-plan.md)维护覆盖和落位，优先确定会影响后期扩展的数据／模块边界；界面沿用按需组件，每次实现一个真实可用增量。
- 用户于 2026-09-21 将首次交付明确为“软件＋独立播放盒”，先贯通一个受限但完整的编排、下发、离线播放与 1 路 DMX 链路；专业单机是持续扩展目标。云端、更多控制入口与其他产品形态后续扩展；保留工程版本、素材、发布包与设备激活的边界。不要把旧项目的空间安装优先队列自动带过来。
- 逻辑上分开“灯／设备、控、编、设置／管理／工具”，产品形态可以整合，也可以独立，不强制拆成四套软件。
- 设备初期以 DMX512 为主，不限于灯具，也包括具有相应通道协议的窗帘、烟雾机、泡泡机、撒花机等设备。
- 专业单机端应支持灯光师编程和现场操作所需的工作流程。客户只需少量简单操作、复杂效果提前编排的要求，适用于后续简化控制产品，不能用来限制当前专业单机端的能力。
- 编排首个可用版本仍应认真考虑音频、波形图卡点、灯具编组和基础时间线；这些能力与专业控台基础工作流程一起确定优先级。
- 首次交付把多个场景下放到盒子，让 DMX 播放稳定并独立运行；用户于 2026-09-26 要求优先 BLE GATT 直连，诊断连接已实测；USB 保留开发与恢复。未来 API、Web 与云端入口接入同一控制边界，不介入逐帧执行。
- 用户提出利用手机／平板／电脑处理完整工程、选取片段无线下发，并要求独立评估。采用主机编译与盒子受限执行；节目在预算内可整场下发，不强制切片。当前先验证 GATT，后续按实际包大小和传输预算接文件下发；局域网仍可作为传输适配，不能把蓝牙或 16 MB 存储上限固定为整个产品的约束。
- 没有电脑时，盒子仍需本地选择场景播放。用户现有微雪 ESP32-S3-RS485-CAN 已作为首台样机，先做 1 路；固件框架与容量待验证，本地面板另行实现。复杂节目后续采用 ARM64 Linux；不以 ESP32 上限限制专业单机，也不承诺任意原始工程直接装入 MCU。软件生成目标执行包，盒子校验并自主运行。
- 首先实现单机编排与控制。未来专业实体控台已是用户明确目标：电脑加扩展翼、一体控台和网络控制面共享核心与双向接口；具体面板、主板及固件分阶段选型验证。
- 用户预计未来灯光编排主力是 iPad，但已明确当前没有 iPad，仍先在苹果笔记本上开发。现在做好 MacBook 桌面与键鼠／触控板体验，保持核心规则、工程格式、编辑命令、布局和宿主可复用；未来进入平板阶段再做触控／可选 Pencil 适配，不让未来设备成为当前开发前提。
- 用户看重 Tauri 路线后续复用 Web 页面、远程控制灯具的价值。Web 控制作为明确的扩展方向：共享前端组件与控制契约，桌面宿主接口和浏览器网络接口分别适配，现场引擎负责播放与输出；网页本身不直接承担 RS485／DMX 输出。Tauri 主线现已确认，当前仍先完成单机，不提前实施云端服务。
- 用户本人是灯光师，负责灯光专业判断、业务需求和现场反馈，希望 AI 承担实质性的软件设计、实现、测试和文档工作。
- 用户当前使用 macOS，未来需要适配多种平台，要求通过架构设计保证通用性；macOS 是当前开发与验证入口，不应将核心绑定到 macOS。
- 用户曾建议 C++26，并允许 Rust；随后要求开放评估开发语言，不局限于 C++。经过 18 条框架路线比较及最终判断，现已确认 Rust 核心和 TypeScript 界面，具体能力仍需验证。
- 用户要求广泛调查开源框架，并尽量减少不同开发语言，降低库与运行时体积、集成错误和维护成本。最终评估接受 Rust 与 TypeScript 两种主要业务语言，以共享 Web 界面和独立原生核心取得明确收益；服务器端沿用 TypeScript，不默认叠加其他业务语言。
- 用户补充询问 Fastify＋PostgreSQL 的可行性，并在补充评估后确认整体技术框架；它们承担云端业务 API 与元数据管理，替代此前“云端业务优先 Rust”的建议。工程语义、节目转换和现场执行继续由 Rust 模块维护，需要云端计算时通过任务接口复用；Node.js 与 PostgreSQL 只作为服务器依赖，单机客户端不需要安装。
- 用户再次强调：尽可能复用代码、减少开发语言种类，这是后续选型与实现的明确优先级。跨桌面、手机、平板和 Web 优先共享工程契约、业务模块与界面组件；各端仅按实际需要适配布局、宿主和设备能力。
- 用户最新强调核心不能采用 TS 一类托管实现，并要求重新比较 Rust 与 C++26。专项复评继续推荐 Rust 维护工程语义、编译、场景／效果、调度及 DMX 编码；TS 接口文件只是契约／客户端样例，TS 云端和界面不参与输出关键路径。无 GC 不能替代实时性验证；特定 SDK／UE／固件可在适配边界使用 C／C++，不为每端维护一套主核心。
- 用户认为 UE5 在专业预演上可能有突出价值。已通过独立渲染适配接入应用内三维视窗，完成固定调光／RGB 及[相交正交两轴摇头灯增量](docs/module-api/positioning.md)的编辑与播放闭环；两轴角度、共同点静态对焦和分关节预演已接通，完整光学与持续目标跟随后续。主技术框架保持 Rust＋TypeScript。轻量端与专业端共享中立场景、节目语义和控制契约，渲染实现可不同。

- 用户于 2026-09-29 补充：充分利用设备内存，近期电脑／手机经有线或系统蓝牙向音箱放音，与 ESP32 灯光近似同步；未来有较大存储及音频输出能力的盒子可本地存音频并播放。依 [ADR-052](docs/development/decisions/PRODUCT-ADR-052-memory-and-host-audio-sync.md)，音频执行端按能力选择、素材按目标部署，专业混音／DSP、视频合成／映射继续外部执行；当前 ESP32 不承载音频流。先验证 PSRAM 与时钟／延迟边界，当前未实现该音频路线，K11 具体型号尚未核验。
- 硬件控制面必须双向工作：输入进入同一业务控制服务，权威状态驱动指示灯、灯环、标签和电动推子。驱动／固件、输入映射与 DMX 输出分别解耦；不能把推子实现成直接写 DMX 的特殊通道。
- 工程解析、实时执行及通过 RS485 输出 DMX 的整条链路需要重视稳定性，同时保持各自职责边界。只有目标能力或 SDK 等具体约束确有需要时，才采用额外语言或独立实现，并将其限制在明确的适配模块中。

## 长期开发原则

1. 充分解耦、按业务职责模块化是长期开发要求；模块需要能够独立理解、测试和演进，不能只在目录上拆分。模块化不等于微服务化，不预建大量空壳。
2. 技术服务当前需求，历史投入不构成继续沿用的理由。优先复用已有模块，并尽量减少主要业务语言、运行时、原生依赖和跨语言接口；不能为每个平台或每个功能另起一套技术栈。只有现有方案不能合理满足具体需求、且收益明确时才新增语言或独立实现；不因旧项目限制新项目。
3. 界面、领域规则、应用流程、存储、设备通信和执行器保持明确边界；同一业务规则有明确的权威维护方。每个模块明确数据所有权和允许的依赖方向，通过显式接口与数据契约协作，不直接读写彼此内部状态，不形成循环依赖或共享全局对象造成的隐式耦合。
4. 交流、界面、错误、状态和产品说明统一使用[中文业务术语](docs/product-terminology.md)，例如“场景”“执行”“渐变”“配适”。
5. 实现进展、自动化测试、真实设备验证和商业可交付状态分别说明，不把演示效果当作可靠性证明。
6. 对第三方代码核查来源和许可证。对设备实测、部署、刷机、发布和删除数据另行取得相应授权。

## 模块边界的落实要求

- 编排界面通过应用接口编辑工程、发出播放命令和读取状态，不直接承担执行调度或设备输出。
- 工程解析／校验／发布转换、播放时钟／调度／效果计算、DMX 帧传输／RS485 驱动分别承担明确职责；具体模块粒度在设计时确定。
- 核心执行语义不依赖界面框架、具体存储方案或具体硬件驱动，通过替换适配器支持离线验证与不同输出目标；核心逻辑应能在没有界面和实际灯具的条件下独立运行和验证。
- 可共享的业务代码和界面组件由各端直接依赖同一来源，避免复制后分别维护。界面组件通过宿主接口使用本机或网络能力；平台差异集中在适配层，不把系统判断散布到业务规则中。
- 跨语言、跨进程或跨设备的接口应明确数据格式、版本兼容、时间含义、状态和错误处理。是否采用函数调用、语言绑定或进程通信，按实际边界决定，不强制所有模块独立部署。
- 不同目标可以有不同实现，但共同支持的能力应遵守同一份权威语义规范，并通过契约与一致性测试验证；不支持的能力必须明确报告。
- 跨端与跨设备是模块接口的基础约束：业务组件调用相同的应用代理，传输层处理 IPC／网络；只交换版本化 DTO、命令和回执，不共享远端类实例或硬件句柄。模块交付需包含伪 API、构造依赖、输入输出、错误、权限、生命周期和调用／验收样例。

- 当前以[最终技术评估](docs/final-technology-assessment.md)记录的已确认框架为开发基线：Tauri 2＋Rust＋TypeScript，React＋Vite 共享界面；Rust 领域、编辑、发布与执行模块独立于宿主。云端采用 TypeScript＋Fastify，PostgreSQL 管理结构化数据，对象存储保存文件；需要工程校验或转换时调用共享 Rust 模块。推荐桌面引擎可独立运行，各端仅携带需要的依赖，具体部署与通信方式后续细化。

- 可编辑工程模型与面向执行目标的发布包分离；工程、发布版本和现场正在运行的版本不应混为一体。
- 无界面引擎负责确定的编排／执行语义，桌面与 ARM 可复用；ESP32 可采用能力受限的轻量执行器，通过契约与一致性测试对齐。
- 通过目标能力和资源校验决定能否部署；超出能力应明确拒绝或提示，不能静默丢效果。
- 编辑接口、播放控制接口与物理传输／DMX 输出适配分开，为未来平板、遥控器和实体控台保留接入面。
- 完整专业单机目标包括灯具档案与配适、选灯与编组、属性编辑与编程器、预设、场景／序列、多路播放合成、动态效果、音频时间线、撤销恢复、本地保存和 DMX。首次交付按[首版 ADR](docs/development/decisions/PRODUCT-ADR-001-first-software-hardware-delivery.md)实现受限子集和真实软硬件闭环，其余能力持续迭代，不一次完成所有控台功能。
- 外部播放器、时钟来源、监听返回及 ESP32／ARM 的实际分工，需要通过代表性节目和设备测试决定。监听设备不默认成为节目主时钟；纯灯光节点无需携带媒体接收依赖。
- 不同设备需要不同的停机／失联保护，不能把“所有通道置零”或“保持最后输出”一概视为安全。
- 云端管理、安装出图、销售交付可独立演进，不强制成为本地编排与现场播放的前置条件。
- 云端采用对象存储与 PostgreSQL 元数据管理的职责划分，厂商暂不确定；离线先本地保存，后台同步处理修订冲突。发布包不可变，设备先完整下载、校验与准备，再按明确时机激活；下载版本、当前运行版本与可编辑工程分别管理，软件／固件更新也与节目分发分开。数据库事务不覆盖对象存储，跨存储提交和重试需明确设计。
